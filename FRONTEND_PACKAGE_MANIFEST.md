# Frontend Package Manifest

> Compiler/linker contract draft for `frontend_package_manifest/v1`.
>
> Status: **v1 implementation contract**. Only the capability kinds marked
> `v1-implemented` below belong to the first compiler slice. Other kinds are
> recorded for architectural continuity but MUST NOT be accepted by the v1
> validator until explicitly promoted.

`FRONTEND_EDITOR.md` defines the shared editor architecture.
`FRONTEND_SPEC.md` defines the application authoring file. This document defines
how reusable frontend/editor packages become **provable linker inputs**.

A package manifest answers:

> Which stable capabilities does this exact package build provide, which public
> exports implement them, what other capabilities are required, and in which
> ownership modes may each capability participate?

The manifest is not a second `package.json`, not handwritten package prose, and
not a place for implementation algorithms.

---

# 1. Canonical artifact and export verification

The canonical manifest MUST be generated by the package's own build from its
public TypeScript boundary. A handwritten manifest is not accepted as linker
truth.

Conceptually:

```text
package source
    public index.ts / declared public exports
    + package-local capability declarations
            ↓
package manifest build step
    TypeScript/public-export verification
            ↓
frontend-package-manifest.json
    exact package version
    manifest hash
    verified public exports
            ↓
frontend compiler/linker
```

This establishes the following invariant:

> If a canonical package manifest names an implementation export, that export was
> verified against the package's public surface during the package build that
> produced the manifest.

The frontend compiler MUST NOT attempt fuzzy source inspection to repair a stale
manifest. A missing canonical generated manifest is a build/link error.

Package-local authoring syntax for capability declarations is an implementation
choice of the package build tooling. The compiler consumes only the generated
canonical manifest.

## 1.1 Manifest location

The canonical generated manifest lives with the package and is shipped/resolved
with the exact package build it describes. A central registry may index package
manifests later, but it MUST NOT become a separately maintained source of truth.

## 1.2 Public boundary only

Manifest linkage may name only verified exports from the declared package public
entry point(s). Internal source paths are forbidden.

Good:

```yaml
implementation:
  export: wallCreateCommand
```

Bad:

```yaml
implementation:
  path: src/internal/walls/commands/createWall.ts
```

# 2. Position in the frontend compiler

```text
backend canonical spec
        │
frontend_spec.yaml
        │
resolved package builds
        │
        └── generated package manifests
        │
symbol manifests
        │
        ▼
frontend normalizer/linker
        │
        ▼
validated frontend_ir.json
        │
        ▼
generated imports/registries/wiring
```

`frontend_spec.yaml` requests composition. Generated package manifests prove that
requested capabilities exist and tell the linker how to import/register them.

No fuzzy matching is allowed.

---

# 3. Deterministic package provenance

Every resolved package recorded in `frontend_ir.json` MUST include build
provenance sufficient to make package changes visible before runtime:

```json
{
  "package": "@planner/building-layer",
  "resolved_version": "0.3.4",
  "manifest_schema_version": 1,
  "manifest_hash": "sha256:..."
}
```

The exact package version comes from the resolved package manager/lockfile state,
not from duplicated author input in `frontend_spec.yaml`.

The manifest hash is computed over the canonical generated manifest bytes or a
canonical normalized representation. Rebuilding after a package upgrade must
change `frontend_ir.json` when either the resolved package version or manifest
meaning changes.

This is the minimum v1 reproducibility contract. Capability-level semantic
version negotiation may be added later if real incompatible evolution requires
it.

# 4. Top-level canonical manifest shape

```yaml
kind: frontend_package_manifest
schema_version: 1

package:
  id: "@planner/building-layer"
  role: layer
  resolved_version: "0.3.4"

requires:
  packages: []
  runtime_capabilities: []

provides:
  capabilities: {}
  layers: {}

irregular_exports: {}
```

The generated canonical JSON additionally carries `manifest_hash`; the package
build may add compiler metadata required for provenance, but unknown semantic
fields are rejected by the manifest schema.

Closed package roles for v1:

```text
runtime
layer
renderer_adapter
ui_adapter
```

`integration_adapter` is **declared-for-later** and is not accepted by the first
v1 validator.

Role is coarse metadata only. Exact behavior is determined by capability kinds.

# 5. Capability provider cardinality

Provider cardinality is no longer an open question in v1.

## 5.1 Aggregate kinds

These kinds intentionally aggregate multiple providers:

```text
snap_provider
anchor_provider
hit_test_provider
```

The linker collects all legal active providers in deterministic package/capability
order defined by normalized IR.

## 5.2 Exclusive kinds

These kinds have exactly one resolved provider for a referenced capability ID:

```text
command
projection
selector
validator
tool_behavior
workspace_action
renderer
```

A duplicate provider for the same exclusive capability identity is `BLOCK`.

`renderer` has an additional renderer-slot uniqueness rule in section 10; two
renderers for different projection/family slots are not duplicates merely because
they apply to the same domain entity type.

# 6. Capability-kind implementation status

The manifest language may name future architectural kinds, but the first
validator MUST distinguish implemented schema from reserved vocabulary.

| Kind | Provider cardinality | v1 status |
| --- | --- | --- |
| `command` | exclusive | **v1-implemented** |
| `renderer` | exclusive per renderer slot | **v1-implemented** |
| `snap_provider` | aggregate | **v1-implemented** |
| `hit_test_provider` | aggregate | **v1-implemented** |
| `anchor_provider` | aggregate | **v1-implemented** |
| `projection` | exclusive | **v1-implemented** |
| `workspace_action` | exclusive | **v1-implemented** |
| `selector` | exclusive | declared-for-later |
| `validator` | exclusive | declared-for-later |
| `tool_behavior` | exclusive | declared-for-later |

The v1 validator MUST reject a `declared-for-later` kind. Promotion requires a
real package/case plus schema and linker semantics.

# 7. Common capability fields

Every capability contains:

```yaml
kind: <v1-implemented kind>
implementation:
  export: <verified public export>
requires: []
```

`requires` contains semantic capability IDs used by this capability.

## 7.1 Type names in v1

`input_type` and `output_type` MAY be emitted as documentation/linkage hints when
they are public TypeScript type names, but **they are not independently validated
semantic contracts in manifest v1**.

Rules:

- the manifest linker must not claim type compatibility from matching strings;
- generated TypeScript is typechecked with `tsc`, and that compilation is the v1
  enforcement point for TypeScript-level compatibility;
- a future language-neutral type registry may promote these fields into true
  compiler-checked contracts;
- diagnostics must distinguish `documented_type_name` from a verified canonical
  language-neutral type.

This avoids a false guarantee between manifest validation and TypeScript type
checking.

# 8. Ownership-mode legality by capability kind

`allowed_layer_modes` uses a positive, kind-specific rule.

## 8.1 Mutation-capable kinds

For `kind: command`, `allowed_layer_modes` is **required** and MUST be a non-empty
subset of:

```text
owned
draft
```

`reference` is forbidden for mutation commands in v1.

A command that is truly read-only is not modeled as a mutation command merely to
bypass this rule; use an appropriate read/action capability when that kind is
implemented.

## 8.2 Layer read/projection providers

For the following v1 kinds, `allowed_layer_modes` is optional:

```text
renderer
snap_provider
hit_test_provider
anchor_provider
projection
```

When omitted, legal modes are derived positively as:

```text
[owned, reference, draft]
```

When present, it narrows that set.

## 8.3 Workspace-global actions

`workspace_action` is not layer-scoped in v1 and MUST NOT declare
`allowed_layer_modes`.

Unknown/empty mode declarations are invalid.

# 9. Command and undo contract

A history flag alone is insufficient because the domain layer may be the only
owner capable of reversing a complex edit.

A command declaration therefore uses explicit history and undo semantics:

```yaml
building.wall.node.move:
  kind: command
  implementation:
    export: moveWallNodeCommand
  allowed_layer_modes: [owned, draft]
  history: commit
  undo: inverse
```

Closed `history` registry:

```text
commit
transient
none
```

Closed `undo` registry for `history: commit`:

```text
inverse
snapshot
```

Meaning:

- `inverse` — the command result/command implementation supplies the reversible
  domain edit contract needed to undo the operation; generic `editor-core` stores
  and invokes that inverse contract but does not invent domain reversal;
- `snapshot` — the command declares that history captures/restores the owning
  layer/application state snapshot under the runtime's explicit snapshot policy;
- `transient` and `none` MUST NOT declare `undo`.

For v1, every `history: commit` command MUST declare `undo`.

A building edit such as moving a shared wall node may change multiple walls,
junctions, derived topology, and openings. `editor-core` owns history sequencing,
not the domain-specific inverse calculation.

A future language-neutral edit-patch contract may standardize the `inverse`
payload. Until then, TypeScript command interfaces plus runtime tests enforce the
shared implementation contract.

# 10. Renderer capabilities and renderer-slot uniqueness

Renderer identity must distinguish the projection being rendered from the
renderer family/target.

Example:

```yaml
building.wall.scene2d:
  kind: renderer
  implementation:
    export: wallSceneRenderer
  renderer_slot:
    projection: building.wall
    family: scene2d
```

A second export renderer may coexist:

```yaml
building.wall.export_svg:
  kind: renderer
  implementation:
    export: wallSvgExportRenderer
  renderer_slot:
    projection: building.wall
    family: export_svg
```

The linker uniqueness key is:

```text
(provider-composition scope, renderer_slot.projection, renderer_slot.family)
```

not merely capability ID or domain entity type.

Initial renderer-family registry for the implemented slice:

```text
scene2d
svg_symbol
```

`export_svg`, `export_dxf`, `react_ui`, and other families are
**declared-for-later** until their first real adapter is implemented.

Renderer capabilities do not mutate canonical domain state.

# 11. Aggregate provider kinds

## 11.1 `snap_provider`

```yaml
building.wall.snap:
  kind: snap_provider
  implementation:
    export: wallSnapProvider
  allowed_layer_modes: [owned, reference, draft]
  snap_kinds: [endpoint, midpoint, intersection, axis]
```

Multiple active snap providers are aggregated. The shared runtime owns
collection/ranking/preview. The provider owns candidate derivation from its
layer/domain projection.

## 11.2 `hit_test_provider`

Multiple active hit-test providers are aggregated into the scene picking stage.
The provider supplies semantic candidates; shared selection policy decides final
selection.

## 11.3 `anchor_provider`

Multiple active anchor providers contribute semantic attachment features.
Consumers persist semantic references where domain semantics permit rather than
stale render coordinates.

---

# 12. Projection and workspace actions

`projection` is a pure/read-oriented capability that derives scene/view data from
canonical state and must not become a persistence model.

`workspace_action` is a workspace-global action such as undo, redo, zoom-to-fit,
or cancel-current-tool. It is not layer-mode scoped.

---

# 13. Dependency model and single source of truth

There are two useful dependency levels, but they are not independent truths.

## 13.1 Capability-level requirements are canonical

Each capability declares the semantic capabilities it directly requires:

```yaml
building.wall.create:
  kind: command
  requires:
    - geometry.snap.resolve
```

These edges are the canonical semantic dependency graph.

## 13.2 Package-level requirements are derived/closed

Top-level `requires.runtime_capabilities` contains only package-wide runtime
requirements that are not attributable to one provided capability.

The package build computes the full semantic requirement set as:

```text
union(all provides.capabilities[*].requires)
+ requires.runtime_capabilities
```

The generated manifest MAY include the normalized union for diagnostics, but it
must be derived. A handwritten duplicate list is forbidden.

Likewise, `requires.packages` contains only real package-level runtime/type
package dependencies that cannot be represented as semantic capability edges.
It is verified against the resolved package build metadata.

The linker rejects a canonical manifest whose normalized dependency summary does
not match the capability-level graph.

---

# 14. Package dependency cycles

`frontend_package_manifest/v1` unconditionally forbids cycles in
`requires.packages`.

The package dependency graph MUST be a DAG. A cycle is `BLOCK`.

If a future runtime genuinely needs cyclic composition, that requires a new
explicit dependency mechanism/version rather than an exception hidden in v1.

Capability edges may point across the DAG but cannot be used to recreate a
runtime package cycle indirectly.

---

# 15. Layer declarations

A reusable planner layer declares named layer definitions:

```yaml
provides:
  layers:
    building:
      implementation:
        export: buildingLayerDefinition
      supported_modes: [owned, reference, draft]
      default_capabilities:
        projection: building.scene.project
        renderers:
          - building.wall.scene2d
        hit_test:
          - building.wall.hit_test
        anchors:
          - building.wall.anchors
        snap:
          - building.wall.snap
```

The linker proves:

```text
requested frontend layer mode ∈ supported_modes
```

and then applies every bound capability's kind-specific mode rule.

The package manifest does not decide whether a particular planner loads the
layer as `owned`, `reference`, or `draft`.

---

# 16. Draft persistence belongs to `frontend_spec`, not package manifest

A reusable package can support draft editing without deciding whether a host
application persists that draft locally.

Therefore the package manifest MUST NOT encode host-private draft persistence.
That decision belongs to each `frontend_spec.yaml` layer instance.

`FRONTEND_SPEC.md` defines the v1 field:

```yaml
layers:
  plumbing:
    provider: "@planner/plumbing-layer"
    mode: draft
    draft_persistence: host_private
```

Closed registry:

```text
none
host_private
```

Rules:

- `draft_persistence` is REQUIRED when `mode: draft`;
- it is forbidden for `owned` and `reference`;
- `host_private` means the host application may persist the overlay only through
  its own explicitly declared backend/application operation;
- it never grants access to the foreign owning planner backend;
- the actual persistence operation is resolved from canonical
  `browser_contract_ir`, not invented by the layer package.

---

# 17. Irregular public exports

Irregular exports remain an explicit escape hatch:

```yaml
irregular_exports:
  special_room_overlay:
    export: specialRoomOverlay
    kind: scene_extension
    reason: "Experimental visualization not represented by manifest v1"
```

Rules:

- `reason` is mandatory;
- `export` is build-verified public API;
- irregular exports are never selected by capability inference;
- `frontend_spec.yaml` references the owner explicitly;
- irregular behavior does not acquire persistence/backend authority;
- repeated irregular shapes trigger review for promotion into a capability kind.

# 19. Canonical linker IR

The normalized IR records exact package provenance and resolved capability graph:

```json
{
  "packages": {
    "@planner/building-layer": {
      "resolved_version": "0.1.0",
      "manifest_schema_version": 1,
      "manifest_hash": "sha256:abc...",
      "requires_packages": ["@factory/editor-core"],
      "provided_capabilities": ["building.wall.create", "building.wall.scene2d"]
    }
  },
  "capabilities": {
    "building.wall.create": {
      "provider": "@planner/building-layer",
      "kind": "command",
      "export": "wallCreateCommand",
      "layer": "building",
      "layer_mode": "owned",
      "history": "commit",
      "undo": "inverse"
    }
  }
}
```

This graph is suitable for deterministic import planning, diagnostics, package
change diffs, and affected-set analysis.

# 20. Fail-closed validation

The v1 linker rejects at least:

1. unknown manifest `kind` or `schema_version`;
2. package role not implemented by v1;
3. package manifest not generated/verified by the resolved package build;
4. duplicate package IDs in one resolved composition;
5. cycles in `requires.packages`;
6. unresolved required packages;
7. unresolved capability requirements;
8. a `declared-for-later` capability kind;
9. fields not permitted for a capability kind;
10. implementation export not verified in the generated package manifest;
11. duplicate provider for an exclusive capability ID;
12. duplicate renderer slot `(projection, family)` in the same composition scope;
13. missing required `allowed_layer_modes` on `command`;
14. `reference` in a command's `allowed_layer_modes`;
15. illegal/empty layer-mode declaration;
16. application layer mode unsupported by `supported_modes`;
17. command bound into a layer mode it does not allow;
18. `history: commit` without `undo: inverse|snapshot`;
19. `undo` present for `history: transient|none`;
20. unknown implemented snap/renderer/history/undo registry value;
21. duplicate aggregate provider record where the same provider/capability is accidentally registered twice;
22. normalized package dependency summary inconsistent with capability-level `requires` + package runtime requirements;
23. frontend-spec capability reference with no exact provider;
24. irregular export without `reason`;
25. internal source path encoded as linkage;
26. frontend package claiming backend endpoint/auth/persistence authority;
27. `draft` layer without explicit `draft_persistence` in `frontend_spec`;
28. `draft_persistence` on a non-draft layer;
29. manifest provenance/version/hash missing from normalized IR;
30. generated TypeScript failing `tsc` after linkage.

TypeScript type incompatibility is enforced by item 30 in v1; manifest string
fields do not pretend to prove it earlier.

Validation failure blocks emission. There is no LLM fallback for invalid IR.

# 21. Deterministic emitter contract

The manifest gives the emitter only linkage facts:

```ts
import {
  buildingLayerDefinition,
  wallCreateCommand,
  wallRenderer,
  wallSnapProvider,
} from "@planner/building-layer";
```

and deterministic registrations.

The emitter does not generate domain algorithms, undo inverses, renderer
algorithms, snap derivation, or backend persistence logic.

# 22. Exact v1 implementation subset

The first implementation MUST NOT implement the whole architectural vocabulary.

Implement now:

```text
roles:
  runtime
  layer
  renderer_adapter
  ui_adapter

capability kinds:
  command
  renderer
  snap_provider
  hit_test_provider
  anchor_provider
  projection
  workspace_action

other:
  generated public-export verification
  package version + manifest hash provenance
  package DAG
  layer supported_modes
  command allowed_layer_modes
  history + undo
  renderer slots
  exact capability resolution
```

Declared for later and rejected by the first validator:

```text
role:
  integration_adapter

capability kinds:
  selector
  validator
  tool_behavior

features:
  capability-version negotiation
  language-neutral type checking
  export renderer families
  symbol-catalog capability linking
  cross-package optional feature negotiation
```

A later implementation PR must explicitly promote a declared-for-later item and
add its schema/linker/runtime evidence.

# 23. First implementation order

1. Define the package-side manifest generation API/tool.
2. Generate/verify manifests from public TypeScript exports for `editor-core` and
   `building-layer`.
3. Compute canonical manifest hashes and carry resolved package versions.
4. Validate the package DAG.
5. Implement only the v1 capability kinds listed in section 22.
6. Implement aggregate/exclusive provider rules.
7. Implement layer-mode and `draft_persistence` cross-validation.
8. Implement history/undo validation.
9. Link one Room Planner `frontend_spec.yaml`.
10. Emit registrations and run `tsc` as a mandatory compilation gate.
11. Prove negative fixtures for stale/missing exports, duplicate providers,
    package cycles, illegal modes, missing undo, and package upgrades.

The first milestone is successful only when a package/API change becomes a
compile-time diff/error rather than a runtime surprise.

# 24. Remaining open questions

Only questions not needed to make v1 deterministic remain open:

1. What package-local authoring API is most ergonomic for generating the
   canonical manifest from verified exports?
2. What canonical serialization is used before computing `manifest_hash`?
3. When should TypeScript `input_type`/`output_type` be replaced by a
   language-neutral type registry?
4. What exact shared inverse-edit interface should `undo: inverse` standardize
   after the first building commands exist?
5. When should capability-level semantic versions be introduced beyond package
   version + manifest hash?
6. Which declared-for-later capability kind should be promoted first from real
   case evidence?

Until those questions have evidence, v1 remains a deliberately small, strict
linker contract.
