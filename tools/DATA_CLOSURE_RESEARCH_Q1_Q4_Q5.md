## Q1. Ранний запуск `data_closure`: после notes одного модуля, до сборки

### Проверенные факты

#### Откуда берётся множество LLM-модулей

1. **Решение принимает только Factory.** Множество модулей, которые
   генерирует модель, получается вызовом
   `deterministic_emission_kind(spec, module)` из Factory внутри
   `_PROMPTS_SCRIPT` (`tools/factory_slice_workbench/service.py:213–232`).
   Функция получает **сырой** `global_spec.json` из временного каталога
   (`service.py:272`) и имя модуля. Своего аналога в Workbench нет.
2. **Классификация Workbench её не заменяет.** Stage 8.1 размечает
   детерминированность по функциям, а не по модулям
   (`tools/module_review_workbench/service.py:60–104`, `deterministic_callables`).
   Эксперимент на `cabinet-kernel` (`build_slice` для 18 модулей):
   - `models` — 0 детерминированных функций из 331;
   - `data_provider` — 0 из 40;
   - `store_persistence` — 1 из 2;
   - `clock` — 2 из 2.

   При этом в `81_module_review_status.json` все четыре модуля помечены
   `deterministic_backend`. По функциям Workbench отличил бы от LLM-модулей
   только `clock`. Решение «весь модуль эмитится без модели» живёт только в
   Factory.
3. **`generation_mode` — данные проекта, а не вывод инструмента.** Поле
   `81_module_review_status.json` → `generation_mode` пишется на Stage 8.1:
   `grep generation_mode` по `tools/` на `main` ничего не находит. Для Stage 7
   это артефакт из будущего.
4. **Factory отвечает за все модули сразу.** `module_prompts` отказывает
   целиком, если Factory не может построить промпт хотя бы одного модуля
   (`factory_slice_workbench/service.py:277–279`). Сломанный соседний модуль
   останавливает и ранний запуск по готовому модулю.

#### Что нужно от Stage 8

5. **Проекция накладывается на существующий `global_spec.json`.**
   `_project` читает его (`spec_projection_workbench/service.py:351`) и
   отказывает при отсутствии (`:33–34`). Ни один инструмент на `main` не
   создаёт `global_spec.json` с нуля. Файл пишут только `export_to_factory`,
   `migrate_spec_v2`, `propagation`, сама проекция и временная копия в
   `factory_slice_workbench`.
6. **Проекция переносит не всё.** `SPEC_PROJECTION_WORKBENCH.md` («Owned
   projections», «All other sections are preserved») перечисляет, что она
   владеет: `config`, `rules.*` из data closure, `persistence`, `properties`,
   `determinism`, `contracts`, `function_order`, принадлежность внутри
   `module_functions`, `rules.persistence_backend`, `rules.http_router_backend`.
   По коду ещё `models` из `60_model_closure_*.json`, `module_order`,
   `module_paths` и экспорт моделей в `imports` (`service.py:356–424, 508–531`).
   **`notes` проекция не переносит.**
7. **Notes переносит `propagation`.** Перенос считается как дельта
   `80_notes.md` против базового ref (`propagation.py:170–200`,
   `DEFAULT_SOURCE = "80_notes.md"`, `:26`). `plan()` и `propagate(write=False)`
   возвращают отчёт и ничего не пишут (`:434–470`). Другие файлы
   `80_notes*.md` propagation не читает.
8. **Проекцию можно получить в памяти.** `_project(project)` возвращает
   `(current, projected, findings, checks)`, ничего не записывая. На
   `cabinet-kernel` @ `b3bee2e`:
   - 0,69 с, 0 блокирующих находок;
   - `projected` равен закоммиченному `global_spec.json`;
   - `verify` даёт `ready=True, in_sync=True` (7 из 7 источников).
9. **Правка note проекцию не меняет.** В копии изменена одна note
   (`80_notes.md:145`, модуль `store`). `_project` по-прежнему равен файлу,
   потому что notes не проецируются. Рассинхрон виден только
   `_spec_out_of_sync`, который сравнивает notes из `80_notes.md` со спекой
   (`questions_workbench/service.py:371–377`).

#### Привязка notes к модулям и инвалидация

10. **Привязка однозначна.** Все 507 authored notes (`language.authored_notes`,
    `notes_workbench/language.py:216–258`) однозначно привязываются к модулю
    через `module_functions`. Префикс метода `Class.method` берётся по имени
    класса. Непривязанных и неоднозначных notes 0.
11. **Инвалидация локальна.** При той же правке `:145` дайджест notes, собранный
    по модулям, изменился только у `store`. Из authored-артефактов affected-set
    по модулям считается точно.

### Варианты

| | A. Как у contradictions | B. Виртуальная сборка | C. Своя классификация в Workbench |
|---|---|---|---|
| Суть | Запуск только на собранном синхронном `global_spec.json` (`service.py:403–407`) | В памяти `_project` + `propagation` (`write=False`) → временный `global_spec.json` → `module_prompts`/`deterministic_emission_kind` Factory. ### Риски

- **B, сломанный сосед.** Все модули решаются за один раз (факт 4): незаконченный
  соседний модуль останавливает ранний запуск. Чинить это нужно на стороне
  Workbench через вызов Factory по модулям: срез и
  `deterministic_emission_kind` по отдельности, без `build_prompt` остальных.
  Для этого понадобится новый скрипт в `factory_slice_workbench`, логика
  Factory при этом не повторяется.
- **B, дельта notes.** `propagation` считает дельту против `HEAD`. Если notes
  правились после коммита, результат зависит от базового ref (факт 7). Значит,
  в запись раунда нужно класть дайджест полученного `notes`, а не ref.
- **B, только `80_notes.md`.** `propagation` и `_spec_out_of_sync` смотрят
  только этот файл, а `authored_notes` — все `80_notes*.md` (Q12 основного
  документа).
- **C.** Противоречит правилу §2.8 контракта и `FACTORY_SLICE_WORKBENCH.md`:
  «the probe re-implements none of their rules».

### Как сохранить корректную инвалидацию

Вердикт привязан к дайджестам входов (контракт, §8): фрагменты, узлы по
адресам, просмотренные пространства имён. Виртуальная спека детерминирована и
совпадает с той, что даст `apply` (факт 8). Поэтому результат раннего запуска
останется действительным и после настоящей сборки, если дайджесты не
изменились. Повторять раунд после Stage 8 не нужно, если входы те же.

Дополнительно в запись раунда кладутся:

- `virtual_spec_sha256`: дайджест временной спеки;
- commit Factory: его решение о множестве модулей — тоже вход;
- множество модулей: если оно изменилось, охват пересчитывается (§7.3
  контракта).

### Рекомендация

**Вариант B, с вариантом A как частным случаем.** B не дублирует Factory,
не пишет в проект и не требует гейта `state8_assembly`, вершин решений
(`decision_witness_resolution`) и Stage 8.1. Обязательными остаются три
условия:

1. базовый `global_spec.json` существует;
2. `_project` проходит без блокирующих находок;
3. есть Factory.

Если условие 1 или 3 не выполнено, раунд не идёт (DC-F2/DC-F3 контракта), и
режим не подменяет решение Factory своим. Чтобы ранний запуск не зависел от
соседних модулей, стоит отдельно добавить вызов Factory по одному модулю.

### Что решает владелец

- Допустим ли ранний раунд на виртуальной спеке, или closure засчитывается
  только на собранной (A)? Если B, засчитывается ли ранний результат
  автоматически при тех же дайджестах?
- Что делать с проектом без базового `global_spec.json`: ждать первой сборки
  или ввести создание каркаса спеки — это новый инструмент?
- Нужен ли вызов Factory по одному модулю, чтобы незаконченные соседи не
  блокировали ранний запуск?

## Q4. Исследовательская среда Codex: пакет или инструменты

### Проверенные факты

#### Как `CodexCliProvider` запускает модель сейчас

1. Команда: `codex exec … --ephemeral --skip-git-repo-check
   --ignore-user-config --sandbox read-only`, рабочий каталог — пустой
   временный каталог (`provider.py:139–150`). Файлы для чтения кладутся в
   `later/` (`:120–137`).
2. Модели запрещено читать что-либо **только инструкцией**: «Do not run
   commands or read files» (`provider.py:115`) и «read nothing else, change
   nothing» (`:125`).

#### Что на самом деле разрешает sandbox (проверено на 0.162.1)

3. **`read-only` запрещает запись, но не чтение.** Команда в sandbox, запущенная
   из пустого каталога `/tmp/.../work`, прочитала
   `/home/user/spec-workbench/AGENTS.md`; запись в `/tmp/...` вернула
   `Read-only file system`. Изоляция от репозитория и домашнего каталога
   держится на пустом cwd и на инструкции, а не на sandbox.
4. **Код в sandbox выполняется.** Внутри sandbox `python3` импортировал
   `spec_projection_workbench.service._get` из Workbench и разрешил адрес в
   `global_spec.json` копии. Исследовательские скрипты можно отдавать модели
   вместе с пакетом, и они будут выполняться без права записи.
5. **Сеть.** Из sandbox сеть была недоступна (`URLError`). Причину — sandbox
   или прокси среды — я не разделял.

#### MCP в `codex exec`

6. **Подключение одной командой.** MCP-сервер можно задать для одного вызова
   через `-c mcp_servers.<name>.command=…` и `…args=[…]`, и это работает вместе
   с `--ignore-user-config`. Проверено фиктивным stdio-сервером: Codex
   отправил `initialize`, `notifications/initialized`, `tools/list` до
   обращения к модели. `codex mcp get` подтверждает ключ
   `enabled_tools` — allowlist инструментов.
7. **MCP-сервер вне sandbox.** Тот же фиктивный сервер записал файл в `/tmp`,
   пока сама сессия была `read-only`. Только-чтение для MCP обеспечивает сам
   сервер, а не Codex.
8. **Готовый сервер Workbench.** `tools/workbench_mcp/server.py` — «read-only
   slice … There is no write tool» (`server.py:1–7`), 6 инструментов:
   `list_workbench_cases`, `workbench_state`, `design_provenance`,
   `closure_diagnostics`, `notes_language`, `design_context`. Данные он читает
   из git ref (`service.py:52–62`, `git show`). Инструментов разрешения
   адресов, индекса значений и поиска отсутствия (M1, M2, M4 контракта) у него
   нет.
9. **Схема ответа.** `codex exec` поддерживает `--output-schema <FILE>`, то
   есть JSON Schema финального ответа, и `--json` — поток событий JSONL. Сейчас
   провайдер не использует ни то, ни другое: ответ разбирается вручную через
   `_json_object` (`service.py:49–53`).

#### Размеры пакета на `cabinet-kernel`

10. Замеры:
    - §15 — 47 257 байт;
    - блоки спеки: `models` 57 351, `rules` 53 386, `config` 990,
      `contracts` 31 896 байт;
    - notes модулей-кандидатов: `canonical_values` 5 883, `sandbox_runner`
      7 673, `store` 26 351, `surface` 31 678 байт;
    - модели, названные в notes `surface`, — 87 штук, 15 529 байт.

    Полный пакет одного модуля — **§15 + все блоки данных целиком + notes
    модуля** — меньше примерно 225 КБ. Все блоки данных проекта помещаются в
    пакет целиком, и вырезать нужный фрагмент не требуется.

**Вариант 3: пакет + read-only скрипты в sandbox, с `--output-schema`.**

- Вход раунда остаётся одним дайджестом. На этом стоит модель `STALE`
  (контракт §8).
- Запись запрещает sandbox, а не добросовестность сервера.
- Модель может исследовать неожиданные связи вычислениями, а не только
  поиском. Все блоки данных и так помещаются в пакет целиком.
- `--output-schema` убирает класс ошибок DC-F6.

MCP (вариант 2) оставить для интерактивной работы оператора: уже есть
`workbench_mcp`. В механизм вердиктов его не включать. Ограничение корней
чтения для `codex exec` проверить до реализации. Если оно недоступно, решение
по изоляции принимает владелец (см. ниже).

### Что решает владелец

- Достаточно ли изоляции чтения «пустой cwd + инструкция», или нужен запуск в

- Допустимо ли, что модель исполняет код Workbench (скрипты пакета) внутри

- Модель для `data_closure`: Codex через ChatGPT-логин (как в QUESTIONS.md) —

- Включать ли в пакет проектную прозу State 0–5? От этого зависит, увидит ли

### Наименьший используемый узел и ссылка на родителя

- **§15.3** требует, чтобы ссылка указывала на «наименьший узел, который
  потребитель использует целиком».
- **§15.3.1** перечисляет законные адреса: `= models.*` («перечисление или
  схема модели»), `= rules.<backend>.*` («лист IR зарегистрированного
  детерминированного backend-а»), `= config.persistence.<имя>_table_name` и
  `…storage_schema_revision`. Константа поставщика называется символом, а не
  адресом.
- **Вывод из эксперимента (факт 5).** Для `models` наименьший используемый
  целиком узел — сама модель: перечисление потребляется как тип. Правило
  «только лист» дало бы ложный дефект на всех 22 адресах проекта. Значит,
  «наименьший» нельзя вычислять как «лист дерева JSON». Его определяет вид
  узла по §15.3.1.
- **Ссылка на родителя** — это адрес, который является собственным префиксом
  законного узла и сам законным узлом не является. Примеры:
  `= rules.data_provider_backend`, `= config.persistence`. По тексту §15.3.1
  это решается **закрытым реестром потребляемых узлов**, без анализа
  потребления. Factory (`_overlaps`) по матрице считает такую ссылку
  законной. Gate Workbench её случайно отвергает (`config.persistence`) или
  случайно принимает (любой потомок).

### Риски

- **A.** Наследует допуск ссылки на родителя и пробелы в `models`, то есть
  `CLOSED` получали бы нарушения §15.3. Без исходников Factory это
  подтверждено только матрицей.
- **B.** Ещё один, шестой разборщик адресов. Это прямо то, о чём говорит
  вопрос 8 в `STANDARD_OPEN_QUESTIONS.md`.
- **C.** Работает до тех пор, пока Factory отвечает. Без Factory режим
  остаётся fail-closed (DC-F3), и результат не хуже A. Если Factory позже
  начнёт отвергать родителей, расхождений станет меньше — без правки
  Workbench.

### Рекомендация

**Вариант C.** Один модуль Workbench (M1) с точным обходом и закрытым
реестром потребляемых узлов из §15.3.1. Его используют `data_closure` и, по
решению владельца, notes gate вместо `_address_resolves`. Каждый прогон
сверяется с резолвером Factory через существующий механизм
`factory_slice_workbench`.

Почему C:

- только он закрывает оба найденных дефекта gate (факт 5);
- правило о родителе становится проверяемым;
- расхождение с Factory не прячется, а превращается в находку.

Перед реализацией нужно сверить номера строк Factory с исходниками.

### Что решает владелец

- **Определение «наименьшего узла».** Утвердить: закрытый реестр
  потребляемых узлов по §15.3.1, где модель целиком — законный узел для
  `= models.*`. Альтернатива — вычислять, что потребитель использует, но для

  пропускает несуществующих потомков и отвергает `config.persistence` (факт 5).
  Это отдельный PR, не часть `data_closure`.
