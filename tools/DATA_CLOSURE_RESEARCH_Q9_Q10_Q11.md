последовательность членов в ней механически сравнима с объявленной. Если
не заявляет, несовпадение порядка ничего не значит.

### 2.4 Ложные срабатывания

1. **Обычные слова.** Члены-слова (`value`, `file`, `one`, `open`, `read`,
   `status`, …) — 988 из 1 324 одиночных совпадений.
2. **Имена полей и записей, совпадающие с членами.** `FilterField.status`,
   `RecordType.run` и `RecordType.flow` совпадают с именами полей и
   сущностей, о которых говорит note. M2 контракта уже исключает имена
   полей; для членов enum нужна та же оговорка.
3. **Одинаковые члены в разных enum.** `succeeded` есть в `RunStatus`,
   `SandboxOutcome`, `ServiceOutcome` и `NodeExecutionStatus`;
   `contract_violation` — в трёх перечислениях. Определить, о каком enum
   говорит note, по одному слову нельзя.
4. **Перечисление отвергнутых значений.** Отвергнутые значения — тоже
   список, но не повтор допустимых. Пример: `:121` перечисляет
   `$ref, pattern, format, oneOf, anyOf, allOf and not` как не
   поддерживаемые (§4.2).

## 3. Q10 — ключи сортировки `content_identity` и `record_change`

### 3.1 Факты

**Notes:**

- **`80_notes.md:114`** `content_identity: [DETERMINISM_OR_ORDERING]`:
  «ports by (direction, name), flow nodes by node_id, flow edges by (to_node,
  to_port, from_node, from_port), flow constants by (to_node, to_port), all
  compared as text by Unicode code point; every other list keeps its order».
- **`80_notes.md:135`** `record_change: [DETERMINISM_OR_ORDERING]`: «in the
  order content_identity sorts them before hashing — ports by (direction,
  name), …, flow constants by (to_node, to_port) —». Note ссылается на
  `content_identity` по имени **и** повторяет список. Повтор совпадает с
  `:114` дословно: 25 общих 10-грамм.
- **`80_notes.md:297`** `prove_version`: «Every order compares identifiers as
  strings by Unicode code point; … the edge order is by to_node, to_port,
  from_node, from_port».

**Источник в дизайне:**

- правило A01-1 — `02_rules_functions.md:20–24` («Lists whose order carries
  no meaning are sorted before hashing — ports by (`direction`, `name`),
  nodes by `node_id`, edges in the edge order of A05, constants by
  (`to_node`, `to_port`)»);
- правило A05-1/2 — `02_rules_flows.md:25` (порядок рёбер),
  `02_rules_flows.md:53` (сравнение по code point).

**Спека:**

- ключи — это имена полей моделей `Port` (`name`, `direction`), `FlowNode`
  (`node_id`), `FlowEdge` (`from_node`, `from_port`, `to_node`, `to_port`,
  `guard`), `FlowConstant` (`to_node`, `to_port`, `value`);
- метаданных порядка в моделях нет;
- в `global_spec.rules` есть только `data_provider_backend`,
  `time_source_policy`, `persistence_backend`, `system_clock_backend` —
  backend-а рецепта дайджеста (§6 `:460–463`) нет.

**Тотальность ключей:**

| Список | Уникальность ключа | Источник | Итог |
|---|---|---|---|
| Порты | `name` уникально в пределах владельца и направления | `01_models.md:44` | Ключ тотален |
| Узлы | `node_id` уникален в версии | `01_models.md:657` | Ключ тотален |
| Константы | «a port with a constant has no other constant» | `02_rules_flows.md:39–40` | Ключ тотален |
| Рёбра | Два ребра в один порт допустимы, если оба охраняются одним guard-портом одного источника с разными `guard_value` | `02_rules_flows.md:65–67` | **Ключ не тотален**: два ребра с одинаковыми `(to_node, to_port, from_node, from_port)` и разными `guard` упорядочены не однозначно |

Это совпадает с прошлой блокирующей темой `round-01 canonical_values:T16`
(контракт, §12.5).

### 3.2 Классификация по §15

1. **§15.2.** Значения нет: ключ — это имена полей формы и способ сравнения.
   - Проверка 0 (форма → `models`) подошла бы, но в DSL `models` нет
     конструкции порядка, а §15.4 говорит только о порядке ключей.
   - Проверки 3–4 (`config`/`rules`) не подходят: смена ключей требует
     правки кода и меняет все идентичности. По операционному критерию
     `:1932–1935` это не политика.
2. **§15.3.** Не применим: нет блока данных, содержимое которого note
   воспроизводит.
3. **§15.9.** Литералов значений нет. Имена полей модель и так видит в
   срезе.
4. **§15.11.** Порядок операций канонизации — это «последовательность
   операций», которая запрещена как **значение** спеки (`:2327`), то есть
   остаётся поведением.
5. **§4 / §2.** Стандарт прямо отводит значимому порядку note класса
   `[DETERMINISM_OR_ORDERING]` или property (`:1739–1740`) и сам даёт пример
   ключа сортировки в note (`:2452`).
6. **Q6.** `DERIVED` невозможен: зарегистрированного backend-а нет.

**Итог по действующему стандарту:**

- `:114` — `NOT_DATA` (`algorithm_step`), законная алгоритмическая
  семантика в предписанном стандартом месте;
- `:135` — тоже не данные, а повтор алгоритма другого модуля (Q11, §4);
- `:297` — согласован с A05.

Нетотальный порядок рёбер (§3.1) — **алгоритмический** пробел: другое
поведение, а не неразмещённое значение. К `data_closure` он не относится.
Его поле — semantic review / contradictions, а также решение State 2 (A05).

### 3.3 Если владелец решит, что это данные

Единственный законный дом по действующему тексту — IR зарегистрированного
детерминированного backend-а: `= rules.<canonical_digest_backend>.recipes.*`
(§6 `:460–463`, §15.3.1 `:1976`). Это означает:

- новый backend и правку стандарта;
- перевод `content_identity` из LLM-модуля в детерминированно эмитируемый.

В рамках `data_closure` пометить `:114` как `DEFECT` нельзя: дефект, для
которого стандарт не даёт дома, неисправим авторским действием.

| Тип повтора | По §15 | Блокирует? |
|---|---|---|
| Повтор **данных** без структурного дома (R1) | §15.11 (inline allow-list) + §15.2 (нет дома). Повтор — отягчающее обстоятельство: две копии обязаны совпадать, а §15.4 `:2021–2023` требует для таких значений один дом. | Да: `DEFECT/missing_structure` в единице `global`, с указанием обоих мест |
| Повтор **алгоритма** (R2, R3, R4, R5, R8, R9) | Не данные: §15.3, §15.4 и §15.9 не применяются | Нет: `NOT_DATA`. Но единица `global` фиксирует «restated_algorithm» с местами. |
| Повтор, в котором копии **расходятся** | — | `UNRESOLVED`: это противоречие между модулями, которое `contradictions` не видит (он смотрит промпт одного модуля) |
| Повтор адресованных констант (R6, R7) | §15.3.1 соблюдён | Нет: `CLOSED` |

## 5. Правила для будущего `data_closure`

### 5.1 Механические правила (без модели)

| # | Правило | Вход | Исход |
|---|---|---|---|
| M-E1 | Совпадение с членом enum само по себе ничего не значит. Сигнал M3 создаётся, только если в note **≥3 члена одного enum**, и ни один не является именем поля или сущности, о которых говорит note. | `global_spec.models`, фрагмент | Сигнал охвата (DC-F8), не вердикт |
| M-E2 | Note содержит `= models.X` и **все** члены `X` без условий между ними (F3) | то же | Кандидат `duplicated_data`; решение — по Q9-a |
| M-E3 | Note содержит «in this order of = models.X» (или «declared order of») и перечисляет члены `X` | то же | Порядок ≠ объявленному → `UNRESOLVED/evidence_failed` (противоречие с моделью). Совпадает → без находки. |
| M-E4 | Note перечисляет ≥3 члена `X` без адреса `= models.X` | то же | Сигнал `unaddressed_enumeration` для судьи (F5–F7) |
| M-E5 | Член, общий для нескольких enum, не учитывается при выборе `X`, если в note нет адреса или имени типа | то же | Подавление ложного срабатывания (§2.4-3) |
| M-D1 | Общий отрезок прозы ≥10 слов в notes **разных** LLM-модулей | все фрагменты | Находка единицы `global` с местами |
| M-D2 | Для M-D1: списки, извлечённые из общего отрезка (идентификаторы через запятую или «and», кортежи в скобках), различаются | то же | `UNRESOLVED`: копии разошлись |
| M-D3 | Для M-D1: отрезок содержит ≥3 литерала, не являющихся ни адресом, ни именем поля, ни членом enum (как ключевые слова JSON Schema в R1) | то же | Кандидат `missing_structure` для судьи |
| M-D4 | Note называет функцию другого модуля и пересказывает её правило (`:135` → `content_identity`) | фрагменты + `module_functions` | Совет: «назвать, а не пересказывать»; не блокирует |
| M-O1 | Note класса `[DETERMINISM_OR_ORDERING]`, ключи сортировки — только имена полей объявленных моделей | фрагмент + `models` | `NOT_DATA` подтверждается механически (§3.2) |
| M-O2 | Для M-O1: тотальность ключа нельзя доказать из объявленной уникальности | `models` + правила | Вне `data_closure`: передаётся в semantic review / contradictions, не вердикт режима |

## 6. Решения владельца

- **Q9-a. Порядок `values` в enum.** Стандарт не придаёт ему смысла (§1).
  - Если порядок нормативен: это правка §5, и тогда скобка в `:125` —
    `duplicated_data`.
  - Если не нормативен: «declared order of = models.X» ничего не доставляет,
    а скобка становится **единственным** носителем порядка. Тогда это
    упорядоченный список в прозе — кандидат `missing_structure`.

  Оба ответа меняют вердикт `:125`, а также `:119` и `:226`, которые
  опираются на тот же порядок.
- **Q9-b. Отображение enum → enum** (F6, `:407`). Требовать ли
  `models … kind: mapping`, или считать частью алгоритма? По операционному
  критерию §15.2 это таксономия.
- **Q9-c. Категории-подмножества** (F7, «методы с телом»). Нужен ли дом в
  `models`, если категория используется в одном модуле? А если в
  нескольких?
- **Q10.** Подтвердить: ключи сортировки в `[DETERMINISM_OR_ORDERING]` — это
  `NOT_DATA` по §4 `:1739–1740`. Перенос в backend-рецепт — отдельная правка
  стандарта и backend-а, не `data_closure`. Отдельно: нетотальный порядок
  рёбер (`02_rules_flows.md:65–67`) — вопрос State 2 (A05).
- **Q11-a.** Повтор алгоритма между LLM-модулями (R2–R5, R8, R9): не
  блокирует при совпадающих копиях (рекомендуется) или блокирует всегда?
- **Q11-b.** Повтор данных без дома (R1) — блокирующий `DEFECT` в единице
  `global`? Рекомендуется да.
- **Q11-c.** Кто ловит расхождение копий между модулями (M-D2):
  `data_closure` (единица `global`) или отдельное расширение
  `contradictions` за пределы одного промпта?
