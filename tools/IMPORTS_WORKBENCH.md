# Замыкание импортов: проект инструмента (2026-11-02)

> Статус: **шаги 1–3 из §12 сделаны** (2026-11-02/03): отчёт фабрики с
> `--code-root` (code-factory #164), пакет `tools/imports_workbench` (#137) и
> его подключение — фаза `imports_closure` для всех проектов, поле
> `module_internal` у проектора, проверка сборки `imports` и допуск FA022.
> Шаг 4 (cabinet-kernel) идёт в `agent/cabinet-kernel`. Решения владельца —
> §13; что уточнила реализация — §14 и §15.

`imports.module_internal` — единственный источник внутренних импортов модуля
(SPEC_STANDARD §7, code-factory `42bb8ade`): полный и минимальный список
символов проекта, которые код модуля называет напрямую. Сегодня это поле
никто не ведёт: проектор его сохраняет, а у cabinet-kernel его один раз
сгенерировал скрипт эксперимента эвристикой фабрики по тексту. Инструмент
делает поле выводом из явной таблицы решений автора и закрывает его гейтом,
который нельзя обойти.

## 1. Почему не «помощник»

Инструмент, который подсказывает импорты, а решает молча, проваливается:
автор на него полагается, а он пропускает случаи. Так уже было:

- скелет cabinet-kernel отбрасывал клаузы notes со словами *never*,
  *without*, *must not* и символ `SANDBOX_TRAPPED_WITHOUT_ARGUMENT`;
  `effects` остался без `clock.kernel_now`, `runs` — без
  `store.record_change` (`81_module_review.md`, «tool defects»);
- гейт State 7 (`notes_workbench/language.py`) видит только вызовы `name(`;
- сверки с фабрикой (`obligation_workbench`, `obligations`) берут
  «заявленное» из того же `module_internal`, работают на уровне модулей,
  без `models`, и молча пропускаются без фабрики.

Отсюда принципы:

1. **Инструмент не решает, он закрывает.** Каждый кандидат из любого
   источника получает решение автора — принять или отклонить с причиной.
   Кандидат без решения блокирует фазу.
2. **Покрытие видно.** У каждого источника доказательств есть состояние:
   работал, недоступен, не применим. Недоступность — блок или явный статус,
   никогда не зелёный гейт.
3. **Поле — вывод, а не правка.** `module_internal` выводится только из
   таблицы; ручная правка расходится с выводом и ловится.
4. **Известные дыры — тесты.**

## 2. Что можно знать заранее, а что нет

Замер на cabinet_kernel: 166 символов проекта, которые использует принятый
код, но не заявляет спека (отчёт фабрики `python -m tools.slicer report
--code-dir`).

| Источник в спеке | Находит нужных из 166 | Лишних кандидатов |
| --- | --- | --- |
| тип назван в notes операции | 27 | 5 |
| тип поля модели операции, имя поля упомянуто в её notes/контракте | 130 | 464 |
| вместе | 140 | 466 |

- **Порты** (функции и константы других модулей) проектируются заранее:
  State 3 `Knows` и вызовы в notes. Их можно выводить точно.
- **Модели и enum**, которые операция создаёт или проверяет, в нынешнем
  дизайне записаны не полностью; из прозы их не вывести без шума. Поэтому
  таблица делает это **явным фактом дизайна**: у каждой операции —
  что она создаёт, что проверяет, что вызывает и читает. Подсказки помогают
  заполнить факт, код фабрики только сверяет.

Область таблицы — только символы проекта (модели, enum, функции,
константы его модулей). Стандартная библиотека и сторонние пакеты описаны
своими таблицами §7 (`stdlib_by_module`, `third_party_by_module`) и в этот
инструмент не входят.

## 3. Таблица: `examples/<case>/65_imports.json`

Пишется автором (с черновиком от инструмента, §6), State 6 → 7.

```json
{
  "schema_version": "spec_workbench_imports.v1",
  "scopes": {
    "functions.add_captured_trial_case": {
      "basis_sha256": "…",
      "uses": [
        {"symbol": "TrialCase", "provider": "models", "as": "creates",
         "basis": "contract"},
        {"symbol": "TrialCaseOrigin", "provider": "models", "as": "inspects",
         "basis": "note:functions.add_captured_trial_case#2"},
        {"symbol": "record_change", "provider": "store", "as": "calls",
         "basis": "note:functions.add_captured_trial_case#1"}
      ],
      "rejected": [
        {"symbol": "Part", "provider": "models", "candidate": "field_name",
         "reason": "the operation copies inputs, it never reads a part"}
      ]
    },
    "functions": {
      "basis_sha256": "…",
      "uses": [],
      "rejected": []
    }
  }
}
```

- **Скоуп** — операция (`<module>.<callable>`, по одному на каждый контракт
  модуля) или сам модуль (`<module>`: код уровня модуля, константы,
  общие помощники). Каждый контракт обязан иметь скоуп, даже с пустым
  `uses`: пустой список — тоже решение.
- **`as`** — закрытый набор: `creates` (конструирует модель), `inspects`
  (сравнивает с членом enum, проверяет тип или вариант, читает поле как
  значение типа), `calls` (вызывает функцию поставщика), `reads` (читает
  константу), `annotates` (тип только в аннотации).
- **`basis`** — почему: `contract` (сигнатура), `note:<адрес клаузы>`,
  `knows:<модуль>` (State 3), `code` (отчёт фабрики), `author:<текст>`.
  Слабый кандидат (§5, «имя поля») принимается только с `basis`,
  указывающим на клаузу notes или код: пачкой подтвердить нельзя.
- **`basis_sha256`** — хеш контракта операции и её скоупных notes в момент
  решения. Изменился контракт или notes — скоуп устарел (§7).

## 4. Вывод `module_internal`

```text
module_internal[m][p] = ⋃ { u.symbol : u ∈ scope.uses, scope ∈ m, u.provider = p }
```

- Типы из сигнатур контрактов (`basis: contract`) входят тоже: стандарт
  разрешает их перечислять, а таблица остаётся полной картиной.
- Проектор (`tools/spec_projection_workbench/service.py`, `build_plan`)
  получает адрес `imports.module_internal`, источник — `65_imports.json`.
  Ручная правка `global_spec.json` даёт расхождение в
  `design_spec_projection.py --verify`.

## 5. Кандидаты: откуда инструмент их берёт

Кандидат — символ проекта, который скоуп, возможно, использует. Ни один не
попадает в таблицу без решения; ни один не пропадает молча.

| Код источника | Что | Сила | Состояние покрытия |
| --- | --- | --- | --- |
| `contract` | тип в сигнатуре операции или её заявленного поставщика | структурный | всегда |
| `note_mention` | экспорт другого модуля или модель, названные **целым словом** в любой клаузе notes скоупа, **включая отрицательные** (помечаются `negative: true`, не отбрасываются) | сильный | всегда |
| `note_call` | вызов `name(` в notes (то, что ловит State 7) | сильный | всегда |
| `knows` | модуль из State 3 `Knows`: хотя бы один его символ должен оказаться в `uses` модуля или ребро — в `rejected` с причиной | сильный | всегда |
| `field_name` | тип поля модели из `uses`/сигнатуры, если имя поля названо в notes или контракте скоупа (до 3 уровней) | слабый | всегда |
| `variant` | вариант discriminated union модели из `uses` | слабый | всегда |
| `code_used` | символ проекта, который использует принятый код модуля и которого нет в `uses` (`code_imports` отчёта фабрики) | доказательство | `available` / `unavailable` / `not_applicable` (§8) |

`code_used` относится к модулю, а не к операции: автор кладёт символ в
нужный скоуп или в скоуп модуля.

## 6. Черновик

`design_imports.py <case> --draft` пишет (или дополняет) `65_imports.json`:
скоуп на каждый контракт; в `uses` — кандидаты `contract`; остальные
кандидаты — в `pending` со всеми основаниями. Для проекта с кодом в фабрике
`code_used` уже разложен по модулям. Черновик ничего не принимает за автора:
`pending` не пуст — фаза закрыта не будет.

## 7. Гейт

`python tools/design_imports.py examples/<case> --coverage [--json]` →
`coverage(project)`, `fence.enforce` (предупреждений нет, вейверов нет).

| Находка | Когда |
| --- | --- |
| `imports_scope_missing` | у контракта нет скоупа |
| `imports_candidate_undecided` | кандидат ни в `uses`, ни в `rejected` |
| `imports_scope_stale` | `basis_sha256` не совпадает с текущими контрактом и notes |
| `imports_symbol_unknown` | символа нет в спеке |
| `imports_provider_wrong` | символ не принадлежит указанному поставщику |
| `imports_edge_forbidden` | ребро против порядка State 3 / политики слоёв / образует цикл |
| `imports_weak_without_basis` | слабый кандидат принят без `basis` на клаузу или код |
| `imports_knows_uncovered` | модуль из `Knows` не дал ни одного символа и не отклонён |
| `imports_code_undeclared` | код использует символ, которого нет в `uses` |
| `imports_code_unused` | символ в `uses` (кроме `contract`/`annotates`), который код не использует; закрывается решением `{"code_outdated": "<причина>"}` на строке |
| `imports_factory_unavailable` | у проекта есть цель в фабрике (`90_factory_target.json`), но фабрика или её отчёт недоступны |
| `imports_table_missing` / `imports_table_invalid` | таблицы нет или у неё не та форма (остальные проверки молчат) |
| `imports_scope_unknown` | в таблице скоуп, которого нет в дизайне |
| `imports_use_invalid` | строка `uses` без `symbol`/`provider`/`basis` или с `as` вне набора |
| `imports_basis_invalid` | `note:` не клауза этого скоупа, `knows:` не из `Knows`, `code` — а код символ не называет, неизвестная форма |
| `imports_rejection_without_reason` | отклонение без причины |
| `imports_decision_conflict` | символ одного поставщика в одном скоупе и принят, и отклонён |

`summary`: `scopes`, `pending`, `stale`, `code_evidence`
(`available`/`unavailable`/`not_applicable`), `handoff_ready`,
**`strict_ready`** — `true`, только когда код доступен и находок `code_*`
нет: тогда проекту можно включать строгий режим фабрики.

## 8. Доказательство из кода

Гейт запускает отчёт фабрики так же, как `factory_slice_workbench`
запускает её CLI (`subprocess`, `cwd=<factory root>`):

```bash
python -m tools.slicer report --spec <база проекта в фабрике> --code-root <дерево продукта> --json
```

Спека — базовая `global_spec.json` проекта фабрики, дерево — каталог проекта
(`project_index/structure.json`): код написан по ней, а `code_imports` от
спеки зависит только путями модулей.

- Корень фабрики — `--factory-root` или `SPEC_WORKBENCH_FACTORY_ROOT`,
  проект — `90_factory_target.json`. Названный корень окончателен: если в нём
  нет `tools/slicer`, доказательство `unavailable`, а не другой чекаут,
  найденный выше по дереву. Соседний `code_factory` ищется, только когда не
  названо ничего. Файл цели, который не читается или не несёт
  `factory_project`, — ошибка ввода, а не «цели нет».
- Отчёт, который не уложился в 600 с, вернул не JSON или не форму
  «поставщик → символы», — `unavailable`.
- Нет цели в фабрике (новый проект) → `code_evidence: not_applicable`;
  гейт может закрыться, но `strict_ready: false` видно в статусе.
- Цель есть, а фабрика или дерево недоступны → блок
  `imports_factory_unavailable`, как у проверки срезов, а не пропуск, как у
  `factory_parity`.
- **Сделано в фабрике** (шаг 1): `--code-root` находит файл модуля по
  `modules.<m>.path`, и отчёт каждого модуля несёт `code_imports` — символы
  проекта, которые код называет напрямую: импорт `from`, использованный по
  имени, или атрибут импортированного модуля. Фабрика без `code_imports`
  даёт `unavailable` («predates --code-root»), а не пустой список.
  На cabinet_kernel: 181 символ, который код называет, а `module_internal`
  не заявляет (166 из §2 — только те, что билдер ещё и угадал), и 140
  заявленных, которых код не называет.

## 9. Как шаг нельзя пропустить

1. **Фаза конвейера** `imports_closure` в
   `skills/spec-authoring/authoring_sequence.json` между
   `decision_witness_resolution` и `state8_assembly`; вызов `coverage()` в
   `design_authoring_next._imports_step` (из `_post_state5_step`). `authoring next` отдаёт её,
   пока она не закрыта; до сборки State 8 не дойти.
2. **Проектор владеет полем** (§4): без таблицы `module_internal` пуст, сборка
   не проходит; ручная правка ловится `--verify`.
3. **Проверка сборки** (`assembly_workbench`, `CHECK_ORDER`):
   `imports_projection_drift`, если поле в `global_spec.json` не равно выводу.
4. **Допуск FA022** (`factory_admission_workbench`): экспорт в фабрику
   отказан, если замыкание, пересчитанное при допуске, не закрыто или
   `global_spec.json` не несёт его проекцию (§15).
5. **Устаревание** (§3, `basis_sha256`): правка контракта или notes снова
   открывает скоуп.
6. **Без лазеек:** `fence` поднимает всё до ошибок; вейвер при допуске —
   блок; проектные ветки не могут менять `tools/`
   (`tools_ownership_check.py`).
7. **Вторая линия — фабрика:** в строгом режиме незаявленный символ ломает
   генерацию, находка `SLICE_IMPORT_UNDECLARED` (`repair_class: spec`)
   возвращает задачу в спеку.

Механика заставляет принять решение, но не делает его продуманным: можно
принять всё подряд. Это ловят `imports_code_unused` (при наличии кода) и
`imports_weak_without_basis`.

## 10. Тесты на известные дыры

Каждая — фикстура в `tests/test_imports_workbench.py`:

- символ назван только в отрицательной клаузе → кандидат с
  `negative: true`, не потерян;
- символ, содержащий `WITHOUT` / `NEVER` в имени;
- символ, используемый только в аннотации, в строковой аннотации;
- проверка члена enum (`Cardinality.MANY`) без упоминания типа в notes;
- вариант union, не перечисленный в полях;
- константа, названная без скобок; вызов без `name(` (через атрибут);
- модуль из `Knows` без единого символа;
- фабрика недоступна при наличии цели; цели нет;
- ручная правка `module_internal` в `global_spec.json`;
- правка контракта после закрытия скоупа;
- слабый кандидат, принятый без `basis`.

## 13. Решения владельца

Решено владельцем 2026-11-02:

- **I1. Фаза для всех проектов сразу.** Шаг нельзя «не включить»; активные
  проекты блокируются до заполнения таблицы (шаг 3).
- **I2. Скоуп — операция плюс модуль**, как в §3: `basis_sha256` устаревает
  точечно.
- **I3. `imports_code_unused` закрывается решением `code_outdated`** с
  причиной на строке `uses`: код может отставать от новой спеки.

## 14. Что уточнила реализация

- **Откуда инструмент читает кейс** (`case.py`). Каталог символов — кто чем
  владеет и что экспортирует, контракты, модели, константы бэкендов — это
  `spec_projection_workbench.projected_spec`: ровно та спека, которую соберёт
  State 8 и получит фабрика. Экспорт — `imports.internal` поставщика: символ
  из `module_functions`, которого нет в экспорте, — `imports_symbol_unknown`.
  Notes — авторские клаузы `80_notes*.md`; адрес клаузы —
  `note:<скоуп>#<n>`, n — номер среди клауз скоупа в порядке файлов.
  `Knows` — `30_modules.md`: только ведущий список имён в обратных
  кавычках (с пояснениями в скобках) и строка «delegates to». Проза не
  разбирается: «every module except `x`» и «the `now` `runs` passes» не
  называют коллабораторов. Список `value_flow_workbench` брал любое имя в
  обратных кавычках и на cabinet-kernel давал почти обратный список для
  `surface` и ложное `run_graph → runs`.
- **Скоупы.** Модуль `models` эмитится детерминированно и не оценивается;
  контракт, который эмиттер опускает из закрытого IR
  (`notes_workbench.gate._load_deterministic_callable_scopes`), не получает
  скоупа; модуль без единого такого контракта не оценивается. Каждый такой
  модуль назван в `out_of_scope` с причиной — молча ничего не выпадает.
  На cabinet-kernel: 134 скоупа, вне оценки `models`, `data_provider`,
  `clock`, `store_persistence`, `store_spool`.
- **Отклонение ребра `Knows`** — строка `rejected`
  `{"symbol": "*", "provider": <модуль>, "candidate": "knows", "reason": …}`.
- **Отказ от символа из кода** — строка `rejected` с `candidate: code_used`:
  новая спека может отказаться от того, что называет старый код. Только она
  отвечает на доказательство из кода: отклонение того же символа как
  кандидата notes (`note_mention` и т. п.) его не снимает, иначе любое
  отклонение в любом скоупе модуля глушило бы `imports_code_undeclared`.
- **`negative`** ставится, только если отрицание управляет самим символом:
  стоит перед ним в той же части клаузы (части разделяют запятые и
  подчинительные слова) или сразу после него («X is not called»).
  «MUST raise X when the reference does not exist» не отрицательна.
- **`knows:<модуль>`** обосновывает только символ этого же поставщика.
- **`imports_code_unused`** судит каждую строку `uses` своего скоупа: освобождённая
  строка (`contract`, `annotates`, `code_outdated`) одного скоупа не прощает
  такую же строку другого.
- **Черновик не выбирает поставщика**: тип сигнатуры принимается, только если
  его даёт ровно один поставщик и порядок State 3 разрешает ребро; иначе
  он в `pending`.
- **Кандидаты растут вместе с решениями.** Принятый `calls` приносит типы
  сигнатуры вызываемого (`contract:<символ>`), принятая модель — свои поля и
  варианты. Поэтому `--draft` запускают снова, пока `pending` не опустеет;
  он хранит решения и идемпотентен. Символ, который называет код и который
  уже ждёт решения в скоупе операции, черновик отмечает там (`code_used`),
  а не повторяет в скоупе модуля.
- **Без таблицы** гейт даёт одну находку `imports_table_missing`, проверки
  модулей молчат.
- **`derive` даёт только рёбра таблицы.** Модуль вне оценки (`clock`,
  `store_persistence`, `store_spool` у cabinet-kernel) скоупов не имеет, и
  `derive` для него пуст — это не значит, что его рёбра пусты. Их сохраняет
  проектор (§15): например, модуль репозитория импортирует вложенные модели
  кодека через `module_internal` (SPEC_STANDARD §6), и эмиттер без них
  остановится.
- **`derive` и `drift`** готовы для шага 3: `derive` — вывод §4, `drift` —
  расхождение `module_internal` спеки с выводом; сейчас их никто не вызывает
  как гейт.
- **Слепое принятие ловится.** Прогон на cabinet-kernel, где принято всё из
  черновика: 129 `imports_code_unused`, 98 `imports_weak_without_basis`,
  426 новых кандидатов от принятых решений, и
  `EDGE_DELIVERY_RULES`: код `run_graph` его называет, `data_provider` его
  не экспортирует.

## 15. Что уточнил шаг 3

- **Проектор** (`spec_projection_workbench._project_module_internal`) пишет
  `imports.module_internal` модулей, у которых есть скоуп в таблице, ровно из
  их `uses` (`derive`). Модули вне таблицы (`models`, модули эмиттеров)
  сохраняют свои рёбра: их пишет не автор. Исключение — модуль построителей
  записей (`wiring.module` в `70_record_construction_closure.json`): его рёбра
  проектор выводит из IR, ровно те, что называет SPEC_STANDARD §6.13 (к
  поставщику данных — каждая `constant`, к владельцу каждой вызываемой функции —
  её имя). Адрес входит в план проектора,
  поэтому ручная правка — изменение в `--verify` и FA016.
- **Без таблицы проекция блокирует** (`imports_table_missing`). Закрыта ли
  таблица, проектор не спрашивает: гейт читает кейс через ту же проекцию, и
  вопрос был бы круговым. Загрузчик кейса гейта проецирует с
  `imports=False` — иначе `--draft` не смог бы создать таблицу, которой ещё
  нет. Закрытость обеспечивают фаза, проверка сборки и FA022.
- **Фаза** без таблицы не заблокирована (`blocked: false`, действие —
  `--draft`), с нерешёнными кандидатами — заблокирована. Ошибка чтения кейса —
  блок с причиной.
- **Проверка сборки `imports`** — гейт плюс `imports_projection_drift`:
  `module_internal` в `global_spec.json` не равно выводу таблицы, по модулям
  таблицы. Стоит между `witness` и `flows`; в реестре обязательств — тип
  `imports_undecided` (convergence).
- **FA022 пересчитывает замыкание при допуске**, а не сравнивает хеш,
  записанный при закрытии фазы, как предполагал §9: правка контракта или notes
  после закрытия и так открывает свой скоуп (`basis_sha256`), а хранимое
  значение нечем подделать, потому что его нет. PASS говорит, разрешает ли
  код строгий режим (`strict_ready`).
- **I1 для всех проектов** значит: каждый кейс без закрытой таблицы не
  проецируется, не собирается и не допускается. Это касается и канонических
  кейсов Cabinet в CI workbench (`cabinet-backend`, `cabinet-web-backend`,
  `agent/cabinet-web-card-persistence`), снятых с разработки.
