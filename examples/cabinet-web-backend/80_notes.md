# State 7 — Cabinet Web Backend generation notes

## Browser and source transport

accept_source_upload: [SECURITY_BOUNDARY] MUST accept only the authenticated browser-owner context with valid same-origin and CSRF evidence, then pass the still-bounded stream to source custody; never treat a filename, media declaration, handoff identifier, or browser control as storage-path or authorization evidence.
accept_source_upload_handler: [ORCHESTRATION] MUST read multipart UploadFile content incrementally under the 30 MiB limit, preserve only the safe display filename, verify the handoff secret without logging it, enforce CSRF before consumption, and delegate one BinaryUpload without buffering or interpreting the whole document.
issue_upload_handoff: [BEHAVIOR] MUST under one authorization decision, verify the exact Card, logical source, and expected current revision before issuing a new 900-second single-use handoff; persist only the verifier and return the bearer value once without placing it in Card data or logs.
store_original_source: [PROVENANCE] MUST lock the exact handoff, identify an accepted content format from bounded bytes, stream to private candidate storage while calculating size and content hash, atomically commit immutable custody and consume the handoff, and make equal replay idempotent while rejecting conflicting bytes.
retrieve_original_source: [SECURITY_BOUNDARY] MUST resolve only the authorized Card/source pair to its immutable verified content reference, reopen a private regular file beneath the configured store, recheck integrity, and return a bounded SourceDownload with no filesystem path or credential.
serve_source_download: [PATH_OR_ARTIFACT_POLICY] MUST emit the verified source as a non-inline attachment using an encoded safe display filename and verified media type, disable active-content interpretation, and never expose the internal storage reference in headers, body, logs, or errors.

## Authentication, authorization, and application composition

authenticate_request: [SECURITY_BOUNDARY] MUST select exactly one credential verifier by channel, apply indistinguishable failure handling and the configured abuse throttle, compare protected verifiers timing-safely, and return only an active principal of the expected kind without retaining the presented secret.
authorize_capability: [BEHAVIOR] MUST re-evaluate the active principal, exact closed capability, channel, entity scope, and current lifecycle state on every call; return a scoped decision or raise AuthorizationDeniedError without granting prefix, suffix, cross-channel, or identifier-only authority.
enroll_principal: [PROVENANCE] MUST at the protected operator boundary, create one stable principal plus one channel-bound credential atomically, return the reusable secret exactly once, and persist only its protected verifier and secret-free audit evidence.
rotate_credential: [SECURITY_BOUNDARY] MUST lock the principal and active credential set, issue the replacement, activate it and revoke the prior credential in one transaction, preserve business identity, and never return or recover the old secret.
revoke_credential: [BEHAVIOR] MUST revoke only the selected active credential, make exact repeated revocation idempotent, preserve its principal and audit history, and reject any later authentication with that credential immediately.
extract_plugin_credential: [SECURITY_BOUNDARY] MUST accept only one well-formed Bearer value on the private plugin route namespace, reject missing, duplicated, oversized, or wrong-scheme headers uniformly, and never log or echo the value.
extract_local_node_credential: [SECURITY_BOUNDARY] MUST accept only one well-formed Bearer value on the synchronization route namespace, reject missing, duplicated, oversized, or wrong-scheme headers uniformly, and keep it distinct from the plugin credential scope.
extract_browser_principal: [SECURITY_BOUNDARY] MUST accept only the TrustedEdge owner assertion injected by the private nginx hop after Basic Auth; reject direct or duplicated assertions, and rely on deployment enforcement that strips the client-supplied header before injection.
resolve_plugin_principal: [SECURITY_BOUNDARY] MUST authenticate the plugin credential as the configured single owner principal and reject machine, browser, revoked, or absent identities without an anonymous fallback. Credential source precedence is the single plugin Bearer value; on any missing, ambiguous, or failed resolution it MUST raise AuthenticationRequiredError, otherwise it MUST return one AuthenticatedPrincipal.
resolve_browser_principal: [SECURITY_BOUNDARY] MUST resolve the trusted-edge assertion only to the configured active owner principal and reject every other label; this resolver never validates Basic Auth itself or accepts a public listener. Principal source precedence is the single trusted-edge assertion; on any missing, ambiguous, or failed resolution it MUST raise AuthenticationRequiredError, otherwise it MUST return one AuthenticatedPrincipal.
resolve_local_node_principal: [SECURITY_BOUNDARY] MUST authenticate the credential only as one enrolled active local_backend node supporting the reciprocal contract and reject owner, operator, revoked, incompatible, or cross-installation identities. Credential source precedence is the single local-node Bearer value; on any missing, ambiguous, or failed resolution it MUST raise AuthenticationRequiredError, otherwise it MUST return one CabinetNodeIdentity.
resolve_capability: [DETERMINISM_OR_ORDERING] MUST match the requested dotted value by exact equality against the closed A16 catalogue, return its single typed operation class in catalogue order, and reject unknown or affix-confused names without dynamic dispatch.
create_app: [DEPENDENCY_BOUNDARY] MUST preserve the application composition boundary and require all thirteen explicit module services, bind them to private application state, install only the accepted plugin, browser, and sync routers plus empty-body exception mappings, and fail startup when protected configuration or any required service is unavailable.

confirm_chatgpt_effect: [SECURITY_BOUNDARY] MUST verify that the owner explicitly confirmed the exact proposal digest, target revision, capability, and effect identity before expiry; any mismatch, ambiguity, decline, or stale revision produces no authorization and no mutation.
report_composite_outcome: [RETURN_SHAPE] MUST return separate typed Card, original-source custody, and local-synchronization outcomes with bounded safe codes, preserving partial or unknown states instead of collapsing them into a single success flag.
begin_effect: [BEHAVIOR] MUST reserve one principal-scoped idempotency identity before mutation, return the prior compatible reservation or committed result on replay, reject conflicting payload reuse, and preserve outcome_unknown for read-only reconciliation.
commit_effect: [PROVENANCE] MUST preserve the effect journal boundary and atomically bind the exact durable operation result and completion time to the existing effect reservation; reject absent, conflicting, or already-differently-committed effects and never rewrite prior evidence.
reconcile_effect: [BEHAVIOR] MUST read the exact reserved effect and its durable result evidence without issuing the mutation again, returning committed, rejected, or outcome_unknown truthfully and leaving all domain state unchanged.

## Canonical Card and Invoice operations

commit_card_revision: [PROVENANCE] MUST preserve the revision effect boundary and under a Card-identity lock, require the expected current content hash, accepted type-specific validation, and immutable successor content; append the revision and move the head atomically, rejecting stale or conflicting commits without rewriting history.
search_provider_cards: [DETERMINISM_OR_ORDERING] MUST apply only the closed bounded Provider criteria, encode external text as data, order equal matches by stable Provider Card ID, cap results at the configured search limit, and perform no mutation.
list_project_cards: [DETERMINISM_OR_ORDERING] MUST return authorized canonical Project summaries in the accepted stable ordering with an opaque bounded cursor, never substituting Registry snapshots for Project Card master facts.
get_card_revision: [BEHAVIOR] MUST return only the exact Card ID, type, and content-hash revision requested for package assembly; never silently substitute the current or newer revision and report absence or type mismatch explicitly.
search_invoices: [DETERMINISM_OR_ORDERING] MUST apply only closed bounded Invoice criteria, return exact revision identities in stable date and Invoice ID order, and never change duplicate, payment, archive, or source state.
get_invoice: [BEHAVIOR] MUST return the authorized current revision only when content_hash is absent, otherwise return exactly the pinned immutable revision; include source and synchronization status as separate projections without rewriting the Card.
find_invoice_duplicates: [BEHAVIOR] MUST compare the supplied or stored Invoice against accepted deterministic candidate signals, return stable ordered candidates with reasons, and never merge, archive, confirm, or choose a duplicate automatically.
prepare_invoice_draft: [BEHAVIOR] MUST normalize supplied facts into InvoiceCardV1 draft form, compute deterministic totals from explicit monetary inputs, preserve missing values and validation issues, and return a proposal without persistence.
validate_invoice: [RETURN_SHAPE] MUST return the normalized candidate, deterministic totals, structured errors and warnings, exact revision context, and duplicate signals; a model confidence value never suppresses a validation error or becomes confirmation evidence.
create_invoice_draft: [BEHAVIOR] MUST require exact capability authorization and a command bound to one idempotent effect, validate the proposed InvoiceCardV1, append the initial draft revision atomically, and return replay-safe mutation evidence without confirming it.
update_invoice_draft: [BEHAVIOR] MUST require the exact expected draft content hash, reject confirmed, archived, stale, or invalid targets, append one validated successor revision under the same Invoice ID, and preserve the predecessor unchanged.
confirm_invoice: [BEHAVIOR] MUST require exact confirmation binding for the reviewed draft revision, revalidate it under the current InvoiceCardV1 rules, append the confirmed successor atomically, and reject stale confirmation without modifying either revision.
record_invoice_payment: [PROVENANCE] MUST require the exact Invoice revision and explicit payment evidence, validate currency and transaction identity, append a successor revision plus audit provenance, and make equal replay idempotent without inferring payment from totals.
attach_invoice_source_metadata: [BEHAVIOR] MUST bind one stable logical source identity and supplied provenance to the exact Invoice revision, append a successor revision, keep byte custody pending until M14 proves storage, and never derive a storage path from metadata.
archive_invoice: [BEHAVIOR] MUST require explicit confirmation for the exact current Invoice revision, append or record the archived lifecycle transition without deleting revisions, sources, receipts, release evidence, or duplicate history, and make exact replay idempotent.
