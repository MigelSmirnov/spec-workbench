## Исправления

### `registry_a18_retention_cutoff_exact_to_microsecond` — исправлен
- Было (черновик): копии ровно в 03:00:00.000000 и второй прогон на +1 мкс. Мутант, усекающий обе стороны до секунды или до миллисекунды, проходил в части «ровно на отсечке», а мутант «усечение только мгновения записи» не отличался от верного.
- Стало: все копии с долей секунды .250000; первый прогон ровно на отсечке первой копии, второй — на .250001, на 1 мкс позже отсечки второй копии. Ловятся усечение до секунды и до миллисекунды с любой стороны и `<=`.
- Основание: A18 rule 4 («to the microsecond … neither rounded nor truncated», Required test 7: «a record instant with a non-zero fraction of a second»).

### `registry_a18_record_matches_snapshot_mismatch_deleted` — исправлен
- Было: после трёх созданий без стирания номер записи совпадал и со счётчиком M12, и с числом записей журнала. Мутант, пишущий число записей, проходил.
- Стало: перед второй копией владелец стирает журнал до 2026-01-07 (A15 rules 3, 4, 6): в журнале одна запись № 4, счётчик 4; запись копии должна сказать 4.
- Основание: A18 rule 1 («the last audit sequence number its store ever wrote — kept apart from the entries (M12) … whatever the log now holds»).

### `registry_a18_backup_during_write_is_one_snapshot` — усилен
- Было в замысле: только параллельная нагрузка, ловящая мутанта M1 лишь при удачном чередовании.
- Стало: детерминированный шлюз копии (`backup_snapshot_gate`) после первого чтения снимка, запись во время шлюза с таймаутом (ловит и M3 «запись ждёт копию»), затем фаза нагрузки как дополнительная.

- Время прогона: первый взгляд в 03:00 (`BACKUP_DAILY_TIME_UTC`) даты, которую более ранний взгляд того же процесса видел до 03:00 (A18 rule 1; State 5 `run_daily_backup_if_due` Enforces).
- Срок: `BACKUP_RETENTION_HOURS` = 720, одна отсечка на шаг, сравнение до микросекунды (A18 rule 4).
- Префиксы `registry-backup-`/`registry-tmp-` (A18 rule 5).
- Запись — первая строка файла, JSON-объект пяти полей; `record_version` = 1; `release_version` = `registry-2.0.0`; `key_digest` = `sha256:` + hex SHA-256(`registry-backup-key-digest-v1` ‖ 0x00 ‖ ключ) (State 6 «A backup file»).
- Номера журнала: одна запись на принятое создание проекта (`OWNER_AUDIT_ACTIONS`, A14 rule 1), первая — 1 (M12: 0 у нового хранилища); стирание оставляет свою запись и не понижает счётчик (A15 rules 4–6).
- Отказ Kernel для незарегистрированной сессии: `not_found`, стадия (2), `agent_call_refused` (State 5 «Closed set of refusal codes»).

## Оставшиеся формальные / ограничения
- Часы фикстуры не идут сами, поэтому мутант, читающий часы для мгновения записи не при первом чтении снимка, а позже (или отсечку шага 3 — для каждого файла отдельно), не отличим: все чтения дают одно мгновение. Ловить это можно только часами, сдвигающимися между чтениями, — такой возможности в поверхности нет.
- Удаление нечитаемых файлов под kept-префиксом и обработка файлов, которые нельзя удалить (A18 rules 4, 5), не проверяются: тест не пишет в место резервных копий сам («a test never writes them directly»). Обязательных тестов на это в A18 нет.
- «Сообщено» (Required test 4) показано числом новых строк диагностики; содержание строки («names the failure») не проверяется — ни State 5, ни State 6 не фиксируют её текст.
- Новые вызовы поверхности (`backup_bytes`, `read_backup(key=)`, `diagnostics`, `faults.fail_next_backup_check`, `backup_snapshot_gate`, `restore`) ещё не внесены в `RUNTIME_SURFACE.md`.
