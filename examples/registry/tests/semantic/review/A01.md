## Исправления

### `registry_a01_equal_repeat_answers_existing_project` — усилен
- Было: только «одна запись, ответ равен». Мутант, который отдаёт сохранённый request id в ответе (нарушение A01 rule 9), проходил.
- Стало: `request_id not in json.dumps(first)` и то же для повтора.
- Основание: A01 rule 9; State 5 Conventions «What answers never carry».

### `registry_a01_publish_retry_returns_same_pointer` — усилен при написании
- Повтор проверяется ещё раз после того, как новая версия вытеснила первую: мутант, отвечающий повтором только «опубликованному» указателю (или переводящий его обратно в `published`), иначе проходил. Основание: A01 rule 4 «answers the pointer whatever its status now».

### `registry_a01_concurrent_creates_make_one_record` — усилен при написании
- Кроме одновременных владельца и Kernel добавлен последовательный повтор вторым сеансом Kernel: «another principal or session» (A01 rule 6).

### `registry_a01_repeat_outside_session_set_not_found` — усилен при написании
- Ответ сравнивается целиком с ответом на несуществующий проект (A10 rule 3, A10-2), а не только по коду: мутант, отличающий «вне набора» от «нет такого» по пути или виду, падает.

### Выравнивание по итоговой RUNTIME_SURFACE.md (2026-11-24)
- `test_former_request_id_after_anonymisation_makes_new_project`: было `old["view_kind"] == "anonymised"`; стало `set(old) == {"project_id", "status"}` — вложенные виды на проводе без `view_kind` (State 5 `serve_service_request`). Строгость та же: форма анонимизированного проекта узнаётся по полям.

### Сторонняя проверка Codex judge-checks (2026-11-24)

Мутант «повтор/конфликт в гонке что-то пишет» (вторая строка, лишняя запись аудита, переписанная строка) теперь ловится. Добавлена пара Kernel-публикаций одного сеанса с одним request id и разными `uri` на отдельном проекте: одна принята (версия 1), другая — `refused`/6/`conflict` (A01 rule 5).

## Оставшиеся формальные / ограничения
- **Гонка (test 12).** Поверхность не даёт способа удержать одну транзакцию, пока идёт вторая; два вызова из двух потоков через `Barrier` пересекаются лишь вероятностно. Registry без сериализации (A01 rule 7) может пройти тест, если вызовы фактически не пересеклись; кроме того, уникальный индекс `create_request_id` в `70_persistence_closure.json` превратил бы такую гонку в `internal_error`, который тест ловит. Детерминированного свидетеля для rule 7 на этой поверхности нет.
- **Новая возможность** `configure_release(**constants)` (та же, что запрашивает `test_a09_service_rights.py`) с `stop()`/`start()`/`sign_in()` нужна тестам 11 и 14 (удалённый тип, `ARTIFACT_TYPE_OWNERS=[]`); её нет в RUNTIME_SURFACE.md. Релиз без единого типа (`[]`) взят как буквальное «release that removes a type» (A22 rule 4); если старт такого релиза запрещён, координатору нужно решить, какой тип объявить вместо.
- **Поток вызовов из двух нитей.** Тест 12 требует, чтобы `owner` и `service` фикстуры можно было вызывать одновременно из двух потоков (владельческий вызов — в одной открытой сессии, открытой до потоков).
- **Стадия (3) для Kernel недостижима:** удаление проекта целиком снимает его со всех наборов (State 5 `erase_project` → `drop_project_from_sessions`), так что Kernel получит стадию (2). Случай (3) теста 14 показан повтором владельца.
- **Форма отказа.** RUNTIME_SURFACE.md описывает отказ плоско (`code`, `stage`, `failures` на верхнем уровне), State 6 `RefusedAnswer` вкладывает их в `refusal`. Тесты следуют RUNTIME_SURFACE.md.
- `store_rows` сравнивается только снимками «до/после» целиком: формат строки в RUNTIME_SURFACE.md не задан.
