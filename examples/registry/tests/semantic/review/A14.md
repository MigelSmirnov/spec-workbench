## Исправления

### `registry_a14_failed_store_leaves_no_change_no_entry` — исправлен
- Было: только `fail_next_write_transaction`. Мутант M2 (изменение и запись в двух транзакциях подряд) проходил: сбой попадал в транзакцию изменения, и запись мутант не писал.
- Стало: вторая попытка с `fail_next_audit_append` — сбой ровно на записи журнала; при M2 изменение уже закоммичено и осталось бы.
- Основание: A14 rule 1 «in the same transaction as the change: if the change is not stored, neither is the entry, and the reverse».

### `registry_a14_accepted_change_writes_one_entry_in_transaction` — исправлен так же (для ограничения Customer).

### Выравнивание по итоговой RUNTIME_SURFACE.md (2026-11-24)
- `fail_next_write_transaction()` → `faults.fail_next_commit()` (2 места); `fail_next_audit_append()` → `faults.fail_store_call("insert_audit_entry_row")` (2 места), метод `StoreRepository` из `70_persistence_closure.json`. Смысл каждой половины теста прежний. У `fail_next_commit` нет опоры в State 5/6 (см. `CAPABILITIES.md`). Строки таблицы не меняются.

## Ожидаемые значения
- Действия записей и их субъекты: `OWNER_AUDIT_ACTIONS`, M09 «the subject … fixed by the action»; принципал владельца `{"principal_kind": "owner", "service": null, "session_id": null}` — State 6 `ActingPrincipal`, A13 rule 7.
- `confirmation_id` только у подтверждаемых действий (`ConfirmedAction`) — A14 rule 5; `erased_before` только у стирания — M09.
- `release_version` `registry-2.0.0`, `contract_version` `registry-contract-2` — `RELEASE_VERSION`, `CONTRACT_VERSION`.
- `internal_error` без стадии с видом `transaction_failed` — State 5 closed set; `stale_revision` стадия 5; `unknown_project` стадия 3; `outside_service_rights` стадия 1.

## Оставшиеся формальные / ограничения
- «Не чеканит id подтверждения» наблюдаемо только как «нет записи»: ни один ответ State 6 не несёт `confirmation_id`. Мутант, который чеканит id и выбрасывает его, не ловится — и снаружи неотличим.
- Нужны две новые возможности сбоя (`fail_next_write_transaction`, `fail_next_audit_append`), обе ниже поверхностей, как `store_rows`.
- Импорт в `_every_audited_action` использует `export_file(projects=[…])` с полями формата импорта (State 6 «The import file»); форма аргумента `export_file` в RUNTIME_SURFACE.md не уточнена.
