# Registry — Project Identity & Trusted Context

**Статус:** Draft — для рассмотрения и принятия в Spec Workbench  
**Дата:** 27 октября 2026  
**Назначение:** требования к Registry как доверенной точке входа в agent-native платформу с подготовкой к независимому GDPR-аудиту.

## 1. Цель продукта

Registry — минимальный сервис, который хранит идентичность клиента, объекта и проекта, обеспечивает жизненный цикл проекта и предоставляет другим сервисам проверяемый рабочий контекст.

Registry не является CRM, ERP, бухгалтерской системой, оркестратором или хранилищем данных других сервисов.

Цели:
- Владелец самостоятельно вводит и изменяет персональные данные.
- Владелец выбирает рабочий проект через простой защищённый интерфейс.
- Агент получает минимально необходимый контекст проекта.
- Сервисы обмениваются данными через объявленные операции.
- Cabinet Kernel позволяет агенту создавать функции и собирать flow без изменения Registry.
- Архитектура допускает независимую проверку соблюдения GDPR.

## 2. Границы ответственности

**Registry владеет:** идентичностью проекта; карточкой клиента и объекта; их связями; жизненным циклом проекта; ссылками на артефакты других сервисов; выбором рабочего контекста владельцем.

**Registry не владеет:** фактурами, расходами и фондами Cabinet; сметами и ценами PresuPro; содержимым клиентских публикаций; функциями и flow Kernel; исходным кодом и развёртыванием сервисов.

Каждая бизнес-сущность должна иметь одного авторитетного владельца.

## 3. Модель данных

### 3.1 Project
- `project_id` — стабильный непрозрачный идентификатор.
- `status` — состояние жизненного цикла.
- `created_at`, `updated_at`.
- `revision` — версия записи.
- Ссылки на клиента и объект.

Допустимые состояния и переходы определяются спецификацией. Архивирование не удаляет историю.

### 3.2 Client
- Имя или наименование.
- Тип клиента: физическое или юридическое лицо.
- Контактные данные, если необходимы.
- Налоговые реквизиты, если необходимы.
- Дополнительные сведения только при обоснованной потребности.

Персональные данные не должны дублироваться без необходимости.

### 3.3 Object
- Идентификатор объекта.
- Адрес.
- Тип объекта.
- Необходимые технические характеристики.
- Связь с проектом.

Адрес и технические характеристики классифицируются с учётом возможности идентификации человека.

### 3.4 ProjectArtifact
- `project_id`
- `owner_service`
- `artifact_type`
- `artifact_ref`
- `version`
- `content_digest`, если применимо.

Registry хранит ссылку, но не содержимое чужого артефакта. Список типов расширяется через спецификацию и проверяемый релиз.

## 4. Единая идентичность проекта

В production существует один авторитетный Registry. Один проект имеет один канонический `project_id` для Cabinet, PresuPro и Client Portal.

Тестовые экземпляры используют отдельное пространство идентичностей. Перенос проекта между экземплярами требует явного сопоставления, импорта или восстановления идентичности. Запрещено молча объединять UUID по похожим имени или адресу.

Миграция существующих данных требует проверки соответствий, сохранения связей и возможности восстановления.

## 5. Интерфейс владельца

Предпочтительны простые серверные HTML-формы поверх существующих операций Registry, без обязательного сложного клиентского JavaScript.

Минимальные экраны:
1. Список проектов.
2. Создание проекта.
3. Просмотр и редактирование карточки.
4. Выбор рабочего проекта.
5. Архивирование с подтверждением.

Обязательны: аутентификация владельца; защищённая сессия; HTTPS при удалённом доступе; CSRF-защита для изменений; серверная валидация; защита от перезаписи новой ревизии; отказ в доступе по умолчанию. Персональные значения не должны попадать в URL и необязательные диагностические логи.

HTML-интерфейс — доверенная поверхность владельца, не инструмент LLM-агента.

## 6. Выбор рабочего проекта

Владелец выбирает проект в Registry. Выбор формирует ограниченный рабочий контекст для агента:
- Непрозрачная ссылка на проект.
- Состояние активности.
- Версия контекста.
- Разрешённая область использования.
- Срок действия, если используется временный токен.

Выбор не предоставляет автоматически права на чтение персональных данных или любые операции. Контекст привязывается к авторизованной сессии либо иной проверяемой авторизации. Подмена `project_id` не позволяет переключиться на другой проект. Агент может запросить смену проекта, но не подтверждает выбор вместо владельца.

## 7. Взаимодействие с Cabinet Kernel

Registry публикует операции через доверенный платформенный манифест. Агент изучает возможности, предлагает operation bindings, создаёт чистые функции, собирает и запускает flow через Kernel, получает только разрешённые результаты.

Kernel независим от бизнес-модели Registry. Registry не хранит функции и flow.

Прямой доступ операционного агента к production-БД Registry запрещён. Его рабочие операции проходят через Kernel с агентскими полномочиями. Другие доверенные сервисы могут обращаться к Registry через собственные авторизованные API.

## 8. Классификация и раскрытие данных

Применяются классы Kernel: `open`, `business_confidential`, `personal_data`.

- Каждая операция с данными имеет проверенный контракт раскрытия.
- Персональные значения не возвращаются агенту как открытые.
- Смешанный ответ не может быть `open`, если содержит персональные данные.
- При прохождении функции класс сохраняется или повышается по правилам Kernel.
- Идентификатор проекта не считается автоматически анонимным.
- Неверная классификация выявляется контрактными и семантическими тестами.
- Для смешанных данных предпочтительны раздельные выходы или специализированные проекции.

## 9. Доверенный манифест

Используется существующий формат `platform/manifest`. Для операции должны быть описаны:
- Имя, назначение, канал, маршрут.
- Схемы входов и выходов.
- Классы раскрытия.
- Класс эффекта и предусловия.
- Идемпотентность и поведение при повторе.
- Версия контракта и известные ограничения.

Манифест соответствует реализации. Существующий `platform_surface_gate` сохраняется; дополнительные тесты подтверждают семантические свойства, не доказываемые сопоставлением маршрутов и имён. Манифест не даёт прямой доступ к БД.

## 10. Интеграции

### Cabinet
Фактуры, платежи и распределение расходов принадлежат Cabinet. Registry предоставляет канонический `project_id`. Привязка фактуры к проекту проверяема; распределение строк между несколькими проектами остаётся финансовой операцией Cabinet.

### PresuPro
Сметы принадлежат PresuPro. Registry хранит идентичность проекта и допустимые ссылки на опубликованные сметные артефакты.

### Client Portal
Client Portal остаётся на VPS, использует каноническую идентичность Registry и собственную авторизацию клиентов. Передача персональных данных допускается только по разрешённым контрактам. Недоступность домашней платформы не должна приводить к раскрытию данных или неконтролируемым изменениям.

### Capability Box
Registry не заменяет передачу пакетов. Пакеты содержат проверяемые ссылки на проект и исходные ревизии; получатель проверяет соответствие проекту перед применением.

## 11. Надёжность

Требуются атомарные изменения, контроль конкурентных обновлений, проверяемые миграции, резервные копии и испытанное восстановление, целостность ссылок, предсказуемое поведение при недоступности зависимостей, разделение production и тестовых данных. Повторный запрос не должен незаметно создавать дубликат или повреждать проект.

## 12. GDPR и управление данными

Система должна поддерживать принципы законности, прозрачности, ограничения целей, минимизации, точности, ограничения хранения, целостности, конфиденциальности и подотчётности.

Документируются категории данных, цели и правовые основания, получатели, передачи AI-провайдерам, сроки хранения и удаления, обработка запросов субъектов, технические и организационные меры, реагирование на инциденты и необходимость DPIA по оценке рисков.

Должны поддерживаться доступ, исправление и предусмотренное законом удаление или ограничение обработки с учётом обязательств хранения документов.

## 13. Журналы и доказательства

Для значимых операций фиксируются время, действующий субъект/сервис, тип операции, идентификатор проекта, результат, версия контракта/релиза и идентификатор подтверждения при необходимости.

Не журналируются пароли, токены, полные карточки и необязательные персональные значения. Устанавливаются сроки хранения, права доступа и защита целостности журналов. Аудит опирается на воспроизводимые технические свидетельства.

## 14. Проверки Code Factory

**Identity:** устойчивые ID, разделение экземпляров, сохранность связей при миграции.

**Access:** отказ неавторизованным запросам, разделение владельца/агента/сервисов, защита от подмены идентификатора.

**Disclosure:** запрет раскрытия персональных значений агенту, правильные классы, отсутствие понижения класса в смешанных ответах и утечек в диагностике.

**Integrity:** повторы, дубликаты, конкурентные обновления, архивирование, ссылки.

**Integration:** совместимость с Kernel, Cabinet, PresuPro, Portal и единым `project_id`.

**Operations:** резервное восстановление, миграции, production-конфигурация, соответствие манифеста реализации.

Отчёты связываются с конкретными версиями спецификации, кода и релизного артефакта.

## 15. Развёртывание

Registry развёртывается в доверенной среде. Операционный агент не имеет прямого административного доступа к production-серверу, БД, секретам и механизму развёртывания. Релизы проходят отдельный контролируемый процесс. Изменения политик доступа, классификации, хранения и доверенных интерфейсов требуют усиленной проверки. Registry не управляет деплоем.

## 16. Критерии готовности

1. Один авторитетный production Registry и канонические ID.
2. Защищённые создание, редактирование и выбор проектов владельцем.
3. Разрешённые операции агента через Kernel.
4. Отсутствие раскрытия персональных значений через контролируемую агентскую поверхность.
5. Манифест соответствует реализации.
6. Согласованные идентификаторы в Cabinet, PresuPro, Portal.
7. Проверенные восстановление и миграции.
8. Пройдены обязательные автоматические проверки.
9. Подготовлены документы обработки данных, оценка рисков и эксплуатационные свидетельства.
10. Независимая проверка возможна без избыточного доступа аудитора к реальным данным.

## 17. Явные исключения

Registry не становится универсальным бизнес-хранилищем, финансовым движком, оркестратором flow, средой исполнения агентского кода, менеджером деплоя или общей системой прав всех сервисов. Новые обязанности — только через отдельное архитектурное решение.

---

**Принцип продукта:** Registry хранит идентичность и предоставляет доверенный контекст. Сервисы владеют своими данными. Cabinet Kernel исполняет процессы. Агент комбинирует разрешённые возможности без избыточного доступа к персональным данным.

**Примечание:** документ — проект требований, не подтверждение соответствия GDPR. Независимая проверка должна учитывать фактическую конфигурацию и организационные процедуры.
