## canonical_values

fit_port_value: [DEPENDENCY_BOUNDARY] Like every function of its module it is pure: it reads no file, no clock, no environment and no store, writes nothing, and decides nothing about what a failed fit or a refused value means for its caller.
canonical_bytes: [BEHAVIOR] MUST parse json_text as one JSON value and emit its RFC 8785 (JCS) canonical form encoded as UTF-8: object members sorted by the UTF-16 code units of their names, numbers written in the ECMAScript shortest round-trip form (an integral double without a fraction or exponent, so a number written 1.0 becomes 1), strings escaped exactly as JCS prescribes, and no whitespace; it applies no Unicode normalization, so two texts that differ only in normalization give different bytes.
canonical_bytes: [VALIDATION_ERROR] MUST first, before json_text is parsed, raise NonCanonicalValueError with a reason naming the depth when json_depth of the UTF-8 bytes of json_text — encoded with the surrogatepass error handler, so that a lone surrogate never makes the encoding fail and is refused below — exceeds the imported RELEASE_CEILING_JSON_DEPTH_MAX constant, so no parse recurses deeper than that constant; otherwise MUST raise NonCanonicalValueError, with a reason naming the first offending item in text order, when json_text is not one well-formed JSON value, when an object repeats a member name at any depth, when it holds a non-finite number (NaN, Infinity or -Infinity tokens, which the default Python parser would accept and therefore MUST be rejected explicitly), when a number written without a fraction or exponent lies outside plus or minus (2 to the power 53 minus 1) and fails both of two tests — the IEEE double nearest to it holds it exactly; it is written exactly as that double's ECMAScript shortest round-trip form —, or when a string holds a lone surrogate. Passing either test accepts such a number and only a spelling that passes neither is refused: 100000000000000000000, which a double holds exactly, passes the first, and 18014398509481990, the form JCS writes for 1.801439850948199e+16, passes the second although that double does not hold it exactly; so canonical bytes always parse again to the same bytes.
canonical_bytes: [RETURN_SHAPE] Returns the canonical UTF-8 bytes only; the length of these bytes is the size of the JSON value wherever the kernel measures a value.
json_depth: [BEHAVIOR] MUST return the depth of the JSON text json_bytes holds — a scalar 0, an array or object one more than its deepest element or member value and 1 when it has none, a member's name adding no level — as the greatest nesting of opening brackets and braces outside strings, found in one pass over the bytes that counts each [ and { as one level in and each ] and } as one level out, a string running from a double quote to the next double quote not escaped by a backslash; it parses nothing and does not recurse. The bytes are scanned as given, without decoding, since the characters it counts never occur inside a multi-byte UTF-8 sequence.
json_depth: [RETURN_SHAPE] Returns the depth as an int and never raises: a text that is not well-formed JSON is measured the same way and left to whoever parses it to refuse.
content_identity: [BEHAVIOR] For every content variant of IdentitySubject (contract_version, implementation, trial_case, flow_version, stored_value, corpus) MUST build one JSON object whose members are exactly the variant's fields keyed by field name, subject_kind included, with nested models as objects keyed by field name, tuples as arrays, enum members as their value text, None as null and JSON-text fields such as value_schema kept as JSON strings, take its canonical bytes with canonical_bytes and return the lowercase hexadecimal SHA-256 of those bytes.
content_identity: [DETERMINISM_OR_ORDERING] Before hashing, lists whose order carries no meaning MUST be sorted so that the same content in another order has the same identity: ports by (direction, name), flow nodes by node_id, flow edges by (to_node, to_port, from_node, from_port), flow constants by (to_node, to_port), all compared as text by Unicode code point; every other list keeps its order, in particular trial_case_ids of a corpus (corpus order is meaningful) and the elements of any JSON value.
content_identity: [BEHAVIOR] For the idempotency_key variant MUST build one JSON object with one member per entry of fields, named by the entry's port and holding the JSON value its canonical_json encodes, so the order of the fields does not change the key, and return the hexadecimal SHA-256 of its canonical bytes; a field whose value is null is kept as null, not dropped.
content_identity: [BEHAVIOR] For the json_text variant MUST return the hexadecimal SHA-256 of the canonical bytes of json_text, and for the bytes variant the hexadecimal SHA-256 of content exactly as given, without any canonicalization; this is the digest of a file and of a value's bytes.

fit_port_value: [DETERMINISM_OR_ORDERING] MUST judge the candidate against the port with the checks in exactly this order and stop at the first that fails: presence (candidate is None), carriage, schema, size; within one check the elements of a list are judged in list order and the reason names the index of the first failing element.
fit_port_value: [BEHAVIOR] Carriage fits when a port of = models.Carriage value receives a json candidate, a file port of = models.Cardinality one receives a file candidate, and a file port of cardinality many receives a file_list candidate; any other pairing fails the carriage check.
fit_port_value: [SCHEMA_CONSTRAINT] The schema check of a value port parses the port's value_schema and the candidate's canonical_json; for cardinality many the candidate MUST be a JSON array and every element MUST fit the schema, for cardinality one the whole value MUST fit it. Supported schema keywords are only — each optional, type included, an absent keyword constraining nothing — type (one of null, boolean, integer, number, string, array, object, given as one string), enum (non-empty array of distinct scalars), const (one scalar), properties and required for objects, additionalProperties given as true or false only, items (one schema) for arrays, minItems, maxItems, minLength, maxLength, minimum and maximum; integer means a number without a fraction; a schema that is not a JSON object or uses any other keyword ($ref, pattern, format, oneOf, anyOf, allOf and not among them) fits no value, so the schema check fails.

## store

record_change: [DEPENDENCY_BOUNDARY] Its module is the only code that opens the SQLite database, begins, commits or rolls back a transaction, or touches the data directory; callers never open, name or pass a transaction, and every module reaches records and bytes only through this module's functions.

## run_graph

plan_run: [DEPENDENCY_BOUNDARY] MUST trust the run, context, flow version, node ports, trace and now it is given and write nothing; it ignores the Run's stored status, outputs and waiting points and derives them again; the context serves only to ask operation_element_conclusion; a node's ports are the NodePorts runs passes for it, one per flow node, and plan_run reads no contract version and no binding; it reads value bytes with read_value_bytes and reads no clock: every time a draft names is the given now.
plan_run: [DETERMINISM_OR_ORDERING] A function element's conclusion, an ElementConclusion, is built from its latest NodeExecution and the row of the imported EXECUTION_STATUS_CONCLUSIONS constant whose status is that record's status: ElementSucceeded with the record's outputs when the row's conclusion is succeeded, otherwise ElementFailed with the record's status and detail_code; wherever a rule below reads an element's or a node's conclusion in the imported NODE_CONCLUSION_EFFECTS constant, ElementSucceeded reads as succeeded, ElementWaiting as waiting and ElementFailed as failed, except an ElementFailed whose status is skipped_by_guard or upstream_failed, which reads as that status; an operation element's is operation_element_conclusion of its element under the context — ElementFailed is failed whatever its status — operation_failed, operation_refused, outcome_unknown or another —, except an ElementFailed whose status is skipped_by_guard or upstream_failed, which answers such a record and concludes as the record does; ElementWaiting waits and its dependants wait, ElementNotReached is not concluded; an operation element is judged by that answer alone, not by its NodeExecution status, which stays outcome_unknown after the owner's resolution; a skipped_by_guard or upstream_failed record, which runs writes only for a node none of whose elements executed, concludes the whole node so at once, mapped or not — the rule that a mapped node concludes only when every element concluded is for a node whose elements execute —, a function node and an operation node alike — for an operation element through the ElementFailed with that status operation_element_conclusion answers, as said above: skipped_by_guard concludes the node skipped and upstream_failed concludes it upstream_failed; a run with any refused_by_owner NodeExecution has status refused, no drafts and no next node, whatever else could be derived or be ready, and none of the status rules below applies to it. Records written together are sorted by (node_id, map_index) with an absent map_index before index 0, identifiers compared by Unicode code point.
plan_run: [DETERMINISM_OR_ORDERING] The next node is the ready node with the smallest node_id; a node is ready when every input port holds its value: flow inputs delivered along every enabled edge from them — a flow input or output endpoint is the node_id empty string (A05 rule 2) —, constants to their port — a FlowConstant's value is the value_id composition wrote —, and outputs of a concluded succeeded node along every enabled edge. A mapped node, once selected, takes its elements in list order, every element that has no concluded record and does not wait; a node none of whose elements without a concluded record can execute is not ready, so the next ready node is selected among the others; a waiting or failed element does not stop the elements after it, and a concluded element is never taken again.
plan_run: [BEHAVIOR] MUST give each EdgeState the delivery of the one imported EDGE_DELIVERY_RULES row whose source_succeeded equals whether the edge source concluded as ElementSucceeded, whose guard_present equals whether the edge has a guard and whose guard_matches equals the following computed fact: false unless both source_succeeded and guard_present are true, and otherwise whether the canonical JSON text of the source's guard_port value equals its guard_value. A flow input counts as ElementSucceeded from the start; every other ElementConclusion variant makes source_succeeded false, guard_matches false and its guard value is not read. It MUST then derive a node skipped_by_guard when one input port can no longer receive a value because every edge into that port has delivery disabled or comes from a node concluded skipped_by_guard, even when its other input ports receive theirs; a node with an input from a node whose conclusion has fails_dependants in its row of the imported NODE_CONCLUSION_EFFECTS constant concludes upstream_failed, which wins over skipped_by_guard. Such drafts are derived only from records already written and carry exactly: the run's run_id, the node's node_id, status skipped_by_guard or upstream_failed, no executed, no map_index — such a record is written only for a node none of whose elements executed, so it stands for the node —, no inputs, no outputs, failure_detail, detail_code and resources_used None, and started_at and ended_at both the given now.
plan_run: [BEHAVIOR] A mapped node's elements are the positions of a non-empty list delivered to its map_over port, counted from the JSON array its StoredValue holds — read with read_value_bytes of a StoredValueSource naming its value_id, or the canonical_json of an AssembledValueList not yet written — or the files of its SpooledFilesRef; a list with no position gives no element, and a mapped node over an empty list is instead ready with over_empty_list and one element without map_index, which stands for the node and is no position of the list, whose sources are the node's inputs as delivered — its map_over port's source is the source of the empty list itself, a RecordedSource or a MappedListSource, never a ListElementSource, which exists only for an element with a map_index; a mapped node concludes only when every element concluded, succeeded only when all succeeded. For a succeeded mapped node with elements, the lists an edge takes to a node or a flow output are asked of assemble_mapped_lists, an output no edge takes being asked nothing: ListsOverCeiling makes the node failed for its dependants, which conclude upstream_failed, with no record of its own and every element record staying as it is.
plan_run: [BEHAVIOR] Each element's sources are one per input port in port name order: a RecordedSource for a flow input's PortRef as Run.inputs holds it — a StoredValuesRef, or a SpooledFilesRef for a file port —, a constant's StoredValuesRef or the output ref of an unmapped succeeded node on the enabled edge — from its NodeExecution or its ElementSucceeded outputs —; a MappedListSource with the AssembledList of a mapped node's output; a ListElementSource for a mapped element's map_over port, with the element's map_index and, as its list, the very RecordedSource or MappedListSource that delivers the list to that port, unchanged — a StoredValueSource or a SpooledFileSource only names bytes to read and is never a ListSource. A guard's source node is never mapped (flows' proof), so a guard reads a written StoredValue, with read_value_bytes of a StoredValueSource naming its value_id. A flow output's source is formed the same way; an output reached by an edge straight from a flow input is a RecordedSource of that input's PortRef as Run.inputs holds it (A13 rule 3).
plan_run: [BEHAVIOR] When nothing is derived and no node is ready, the status is: when any element waits, the resting_status of the row of the imported WAIT_REASON_RESTING_STATUSES constant whose reason is a waiting element's reason, awaiting_approval winning over pending when the waiting elements' rows give both, with one WaitingPoint per waiting element — a mapped operation node's elements being the positions of its delivered list; when nothing waits, succeeded when every node's conclusion has lets_run_succeed in its row of the imported NODE_CONCLUSION_EFFECTS constant and failed otherwise, a mapped node whose delivered list is over the ceiling counting as failed. While a draft is derived or a node is ready the status is running, except for a run with a refused_by_owner record, which is refused. A run whose status has ended — refused included — has no waiting point, whatever its elements still wait for (A14 rule 1). The outputs are those produced so far, whatever the status (A13 rule 7), each named by its flow output port; once the status has ended (= models.RunStatus: succeeded, failed or refused here) every other flow output is a MissingOutput with reason skipped_by_guard when every edge into it was disabled or comes from a node concluded skipped_by_guard and not_produced otherwise (= models.OutputReason).
plan_run: [RETURN_SHAPE] Returns RunPlan with every element's ElementState in (node_id, map_index) order, every edge's EdgeState in the flow version's edge order, the derived drafts, the next ReadyNode or None, the waiting points in (node_id, map_index) order, the produced outputs and missing outputs in flow output port name order, and the status.

continue_after_resolution: [ORCHESTRATION] After either resolution MUST advance the run with advance_run: after applied the element is concluded, after not_applied it is not reached, so the advance reaches it and reach_operation_element requests its fresh approval even where a grant exists; advancing runs every element that becomes ready and sends its requests under the authority each has; returns the run's answer.

## surface


serve_kernel: [ORCHESTRATION] MUST call run_start_sequence with config_path, the process's one command-line argument, and open the MCP entrance — MCP over streamable HTTP at the mcp_listen_address of the returned Installation, one tool per catalogue operation — only after it returned; while serving it reads one HTTP request at a time, takes the presented token from its Authorization header in the Bearer form (None when the header is absent or not in that form), passes the body bytes and that token to answer_request and writes back the bytes it returns.
serve_kernel: [VALIDATION_ERROR] When run_start_sequence raises, which has already written the failing step's name, MUST write the exception's reason to standard error — a kernel module's reason holds no token, credential value or configuration content (translate_failure's note), and an exception no kernel module raised is written by its type alone — never a stack trace, open no entrance and return a non-zero exit code; there is no partial start and no retry. Ending the process releases the store lock; nothing the steps already committed is rolled back, and the next start runs the whole sequence again from those records. Binding the listener at mcp_listen_address is the last start step and fails the same way, the step named open_entrance, when the address cannot be parsed as a host and port or the socket cannot be bound; a listener lost while serving ends the process with a non-zero exit code, without retry.
serve_kernel: [BEHAVIOR] MUST read at most one byte more of a request body than the imported RELEASE_CEILING_SURFACE_REQUEST_BYTES_MAX constant allows, so an oversized request still reaches answer_request and is refused there; when answer_request raises StopRequiredError or any other failure it let propagate because its answer is internal_error, MUST first send and flush that request's internal_error answer built by translate_failure, without detail, then leave request serving and return a non-zero process exit code before another request is read, so the next start derives every run that has not ended. This required-stop path closes the request connection and listener and still ends with a non-zero exit code if writing or flushing the error answer fails. It MUST NOT call the blocking HTTPServer.shutdown from the thread serving that request: the serving loop must be able to leave without waiting for itself, and the sequential HTTPServer boundary is preserved.
serve_kernel: [DETERMINISM_OR_ORDERING] Requests are handled strictly one at a time, each to its end, run advancement included, before the next one is read (A18 rule 3).
serve_kernel: [RETURN_SHAPE] MUST return a non-zero process exit code after a failed start, a required stop, or any failure answer_request lets propagate as the internal_error member of = models.RefusalCode. During a request the required-stop path first attempts to send and flush the error answer without detail; a failed write or flush still stops the process. A required stop never becomes a normal return from the serving loop. Return zero only when serving ends normally.
serve_kernel: [ORCHESTRATION] When the surface module is run as a script, python -m cabinet_kernel.surface <config_path>, which is how the host starts the kernel, it MUST call serve_kernel with that one argument and exit with the status serve_kernel returns (decision 25).
serve_kernel: [DEPENDENCY_BOUNDARY] The entrance is the standard library's http.server.HTTPServer, which serves one request at a time, never a threading or forking server; the surface imports nothing outside the CPython 3.12 standard library except BaseModel from pydantic, the one third-party package, pinned by the release in the imported RELEASE_PYTHON_DEPENDENCIES constant, on which the models and the store repository are emitted and which the surface uses to recognise and serialise models (60_contracts.md decisions 22, 25 and 27).
serve_kernel: [BEHAVIOR] Only a POST to the path equal to the imported MCP_ENDPOINT_PATH constant reaches answer_request; any other method on that path is answered 405, any other path 404, and a request carrying an Origin header 403, each without a body and without calling answer_request; no Mcp-Session-Id header is ever sent, one presented is ignored, and no event stream is opened.
serve_kernel: [FIELD_PROJECTION] An empty result of answer_request is answered 202 without a body; any other result is answered 200 with Content-Type application/json and the result as the body. The internal_error answer sent before the process ends is the JSON-RPC error response of answer_request with code -32603, message internal_error and the RefusalAnswer from translate_failure as data, its id read from the body by the same rule as answer_request.

run_start_sequence: [ORCHESTRATION] MUST call, in exactly this order and each exactly once: load_installation with config_path; check_installed_instances with the loaded Installation; open_store with that Installation's data_directory; probe_sandbox; recover_in_flight_attempts; recover_running_runs (A03 rule 8, A09 rule 1, A14 rule 5, A18).
run_start_sequence: [VALIDATION_ERROR] Every step is required: the first step that raises — InstallationRejectedError, RefusedError from the instance check, a store refusal, SandboxUnavailableError, StopRequiredError or any other exception — stops the sequence there and propagates unchanged to the caller, the same exception with its own reason; before it propagates MUST write the failing step's name — load_installation, check_installed_instances, open_store, probe_sandbox, recover_in_flight_attempts or recover_running_runs — as one line to standard error, so the step is named there and the reason stays the exception's own; no later step runs and nothing is retried or skipped.
