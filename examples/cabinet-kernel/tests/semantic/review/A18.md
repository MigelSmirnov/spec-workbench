## Исправления

### `kernel_a18_value_write_atomic_publish` — исправлен
- Было: проверялись только опубликованный путь и отсутствие случая; мутант «старт не удаляет временные файлы» проходил (прерванная запись в temp-файл не видна по опубликованному пути).
- Стало: после рестарта скан всех файлов `data_directory` — ни один не содержит байтов значения (`b'"a18-atomic-'`); записи нет, поэтому значения нет и в файлах БД.
- Основание: A18 rule 4 «On start, temporary files, value bytes no record names … are removed»; State 5 `store.open_store` Observable effect.

### `kernel_a18_failed_store_call_writes_nothing` — исправлен
- Было: после `internal_error` сразу `page_records`. По `80_notes.md` (`answer_request`: StoreInternalError «propagate to serve_kernel»; `serve_kernel`: «first send that request the internal_error answer … and then end the process with a non-zero exit code») процесс к этому моменту завершён — тест падал на правильном ядре (если фикстура не перезапускает ядро сама).
- Стало: `assert semantic_runtime.restart().started is True` перед чтением; заодно видно, что ничего не зафиксировано и после нового старта.
- Основание: A18 rule 3; State 5 Conventions «Internal error»; 80_notes `serve_kernel`, `answer_request`, `translate_failure`. `restart()` не указан для этого witness в таблице RUNTIME_SURFACE.md — см. «Ограничения».

### `kernel_a18_symlink_in_data_dir_refused` — исправлен (частично)
- Было: после `internal_error` вызов `_cases_of(...)` — на правильном ядре процесс уже завершён, а старт со ссылкой отказывает, т. е. тест не мог пройти.
- Стало: после отказа проверяется, что по ссылке ничего не записано (`not outside.exists()`), ссылка не заменена файлом (`link.is_symlink()`), первый опубликованный файл цел; затем `restart()` отказывает и ссылка всё ещё на месте.
- Основание: A18 rule 2 «a link found at start stops the start, and one found later makes that store call fail with nothing written»; State 5 `put_value_bytes` Errors; 80_notes `put_value_bytes` («On a symbolic link … raise StoreInternalError; nothing is published and no record is written»), `serve_kernel`.

### `kernel_a18_published_file_digest_never_overwritten` — исправлен
- Было: `pytest.raises(Exception)` без кода (любое исключение, в т. ч. ошибка фикстуры, проходило); после первого сбоя процесс завершён, а цикл продолжал вызовы без рестарта.
- Стало: `code == "internal_error"`; проверка `not published.exists()` до рестарта; `restart()` после каждого сбоя; затем снова нет файла и нет случаев.
- Основание: A18 rule 4; 80_notes `put_value_bytes` «On a symbolic link, an I/O failure or a failed re-check after writing MUST remove its temporary file and raise StoreInternalError» (сбой `alter_value_write` вносится после flush, т. е. проваливается повторная проверка, а не начальная — начальная по 80_notes даёт RefusedError); `translate_failure`: StoreInternalError → `internal_error`. `restart()` не указан для этого witness — см. «Ограничения».

### `kernel_a18_store_module_sole_transaction_owner` — исправлен
- Было: (1) любой атрибут `.commit`/`.rollback` считался доступом к БД — правильный модуль `bindings`, читающий манифест как git-объект через `repo.commit(revision)`, падал бы; (2) любая строка, начинающаяся (без учёта регистра) с `BEGIN`/`COMMIT`/…, считалась SQL — докстринг «Begin the run…» или строка `"commit"` (тип git-объекта) давали ложный отказ.
- Стало: `.commit()`/`.rollback()` засчитываются только как вызов без аргументов (как у соединения DB-API); SQL — только целая строка-оператор транзакции в верхнем регистре (`BEGIN [IMMEDIATE] [TRANSACTION]`, `COMMIT`, `ROLLBACK [TO …]`, `SAVEPOINT x`, `RELEASE SAVEPOINT x`, `END TRANSACTION`). Мутанты M1–M4 ловятся по-прежнему (проверено на образцах).
- Основание: A18 rule 3, K-17; 80_notes `read_service_record` (манифест читается как git-объект).

## Ожидаемые значения
- `internal_error` для провалившегося изменения (RT3), ссылки (RT4) и проваленной повторной проверки (RT5): State 5 Conventions «Internal error», таблица кодов; `put_value_bytes` Errors («`internal_error` on a link or I/O failure»); 80_notes `put_value_bytes` (StoreInternalError при ссылке и при проваленной повторной проверке), `translate_failure`. State 5 `put_value_bytes` «`refused` when digest or size do not match» по 80_notes относится к начальной проверке переданных байтов («checked first»), а не к повторной после записи — расхождения нет.
- `compose_flow_version` пишет Flow и FlowVersion одним изменением: State 5 «Named store changes».
- Путь публикации — `value_file(digest)` (RUNTIME_SURFACE.md), дайджест — SHA-256 hex канонических байтов (M21 `value_digest`).
- Модуль-хранилище — `store` (State 3/5 `module:store`), драйвер SQLite — A18 rule 2.
Все ожидаемые значения следуют из A18, State 5 и 80_notes.md; исправлять значения не потребовалось (добавлен код в RT5).

## Оставшиеся формальные / ограничения
- `kernel_a18_symlink_in_data_dir_refused`: «nothing written» для записей (мутант M4 — TrialCase зафиксирован, хотя публикация упала) не наблюдаем: после `internal_error` процесс завершается (80_notes `serve_kernel`), а пока ссылка на месте, любой старт отказывает. Нужна возможность, которой нет в RUNTIME_SURFACE.md: снять поставленную ссылку (например, `faults.remove_symlink(relative_path)`), после чего `restart()` и чтение записей. `store_dump()` не использован: неясно, входят ли имена файлов области значений в дамп (имя ссылки содержит тот же дайджест).
- `restart()` для `kernel_a18_failed_store_call_writes_nothing` и `kernel_a18_published_file_digest_never_overwritten` необходим: после ответа `internal_error` процесс ядра завершается (80_notes `serve_kernel`, `answer_request`), без нового старта записи не прочесть. Отсутствие `restart()` в их строках таблицы «Places the surface cannot reach yet» — явная ошибка RUNTIME_SURFACE.md; строки исправлены (отмечено в SUMMARY.md). `data_directory` для `kernel_a18_value_write_atomic_publish` уже указан там.
- Общий вопрос к фикстуре (не к владельцу): RUNTIME_SURFACE.md «Kernel start» не говорит, перезапускает ли фикстура ядро, завершившееся само; тесты A18 теперь вызывают `restart()` явно, как `test_a03_sandbox.py`.
- RT6 — статическая проверка: доступ к БД через неперечисленные пути (например, `with connection:` у объекта, полученного от `store`, без `.execute`) не ловится.
