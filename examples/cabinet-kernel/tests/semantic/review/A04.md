## Исправления

### `kernel_a04_verdict_set_only_by_kernel` — исправлен
- Было: откат как способ «отменить» вердикт проверялся только от владельца (актор по умолчанию). Но `roll_back_slot` по каталогу State 5 доступен владельцу и автору, и мутант с отменой проверки вердикта для автора проходил.
- Стало: откат к реализации с отказным вердиктом проверяется от `OWNER` и от `AUTHOR` (через `actor=`, конвенция RUNTIME_SURFACE.md «Actor»). Мутант M4 падает на `pytest.raises` / `code == "refused"`.
- Основание: A04 rule 8 «No actor records, edits or waives a verdict»; RT6 «No operation lets the owner or an agent set a verdict»; State 5 каталог: `roll_back_slot` — owner, author.

### `kernel_a04_corpus_order_is_first_added` — исправлен
- Было: проверялось только, что дайджест не меняется после равного случая и меняется после нового. Мутант, считающий дайджест по отсортированному множеству id (или по корпусу в порядке id), проходил. Порядок в repair view ловил порядок по id только при «удачных» хэшах.
- Стало: дайджест сравнивается с идентичностью `CorpusContent` `{"subject_kind": "corpus", "trial_case_ids": [c1, c2, c3]}` — lowercase hex SHA-256 его JCS. В контроле то же для `[c1, c2, c3, c4]`. M3/M4 падают, если только id случайно не отсортированы в порядке добавления и в списке из трёх, и в списке из четырёх (вероятность 1/24; сами id тест выбрать не может).
- Основание: A04 rule 2 «The corpus digest is the content identity (State 6, decision 14) of the list of its `trial_case_id`s in corpus order»; rule 1 «The corpus … is its cases in the order they were first added»; 80_notes `content_identity` (форма объекта, lowercase hex, «trial_case_ids of a corpus (corpus order is meaningful)» не сортируются), `read_corpus`. Хэширование — как в `_jcs_sha256` из `test_a01_identity.py`.

## Ожидаемые значения
- `admitted` / `refused` — AdmissionVerdictKind. `empty_corpus` / `failing_case` — AdmissionRefusalReason. `output_mismatch`, `crashed`, `passed` — TrialOutcome (A04 rule 3).
- `activated_by.kind == "kernel"`, `agent_name is None` — A04 rule 4, State 5 Conventions «Naming records» (активация после допуска — работа ядра), Actor M27.
- Повторная отправка текущей допущенной реализации возвращает существующую Activation — State 5 `submit_implementation` Outputs. Переиспользованный `admitted` активирует нетекущую реализацию — там же, Enforces.
- `refused` для отката — State 5 `roll_back_slot` Errors. `invalid_request` для неизвестной операции и неизвестного поля — State 5, закрытый набор кодов.
- `corpus_position` с 0 — State 5 `add_trial_case` Outputs («counted from 0 in corpus order»).
- Дайджест корпуса — CorpusContent (State 6), 80_notes `content_identity` / `read_corpus`.
- Все ожидаемые значения следуют из A04 и State 5/6; ни одно не менялось.

## Оставшиеся формальные / ограничения
- `kernel_a04_verdict_set_only_by_kernel`: имена «запрещённых» операций угаданы (`record_admission_verdict`, `set_verdict`, `admit_implementation`). Мутант с операцией под другим именем или с полем `verdict`, принятым другой операцией (например, `add_trial_case`), не ловится. Перебрать весь каталог State 5 через `mcp_request` можно, но это уже другой тест; RT6 так не формулирует.
- `kernel_a04_verdict_set_only_by_kernel` использует `installation.owner_token` / `installation.agent_token` (так было и до правки). В таблице «Places the surface cannot reach yet» для этого witness указан только `mcp_request`. Решение за координатором.
- `kernel_a04_refusal_names_first_failing_case`: мутант «порядок по `trial_case_id`» ловится здесь только при неудачных для него хэшах (пропуск 1/6), в `kernel_a04_corpus_order_is_first_added` — с пропуском 1/24. Детерминированная проверка потребовала бы управлять значениями id, а они вычисляются ядром (A01 rule 1).
