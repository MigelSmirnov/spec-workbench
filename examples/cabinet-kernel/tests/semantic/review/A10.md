## Исправления

### `kernel_a10_used_approval_and_grant_do_not_cover_resend` — исправлен
- Было: `assert fresh.attempt_number > 1`. Одобрения читаются через `page_records("approval")` → `RecordPageAnswer.records.approvals: tuple[ShownApproval, ...]`; в ShownApproval (`60_model_closure_operations.json`) поля `attempt_number` нет (оно есть только у доменной EffectApproval M24). При любой реализации фикстуры, возвращающей выходную модель операции (RUNTIME_SURFACE.md, Conventions «Results»), строка падает с AttributeError — ожидание не следует из State 6.
- Стало: «свежесть» проверяется наблюдаемо: `fresh.approval_id != used.approval_id`, первое одобрение остаётся `used`, и `fresh.request_digest == used.request_digest` — запрос не изменился, так что использованное одобрение совпадает по дайджесту и всё же не является полномочием (это отделяет правило «used / после not_applied» от правила «другой дайджест»). Мутант M2 (повтор по `used` одобрению с тем же дайджестом) падает на `len(stub.requests) == 1`; эквивалентность дайджестов исключает объяснение «просто другой запрос».
- Основание: A10 rule 1 «A fresh approval after `not_applied` is one whose `attempt_number` is greater than ...; approvals requested before it never count»; M24 lifecycle «An approval is used at most once»; State 6 ShownApproval.

### `kernel_a10_no_decision_changes_nothing` — исправлен
- Было: одно одобрение, 30 дней, проверка статусов, затем отмена и отказ в решении. Мутант с «ленивым» истечением (одобрение старше N дней отклоняется только в момент решения, статус не трогается) проходил: до отмены решение не пробовалось, а после отмены отказ `refused` ожидается в любом случае.
- Стало: второй прогон той же версии запускается до `clock.advance(days=30)`; после ожидания владелец одобряет его — ожидается `succeeded` и ровно одна отправка с телом `{"title":"decided late"}`. Финальные проверки: у отменённого прогона нет попыток, общий счёт запросов — 1. Мутант M2 падает на контрольном `continue_after_approval`: вызов бросает отказ вместо ответа `succeeded`. Отказ после отмены теперь однозначно следует из завершения прогона.
- Основание: A10 rule 4 «no time limit approves, refuses or ends anything»; RT10 «nothing approves, refuses or ends it»; State 5 `runs.continue_after_approval` Errors «`refused` for an ended run».

## Оставшиеся формальные / ограничения
- Формальных тестов не осталось.
- `attempt_number` одобрения не виден через поверхность (ShownApproval без него), поэтому мутант «после `not_applied` засчитывается `approved` неиспользованное одобрение, запрошенное до разрешения» (A10 rule 1, «approvals requested before it never count») этим тестом не ловится: сценарий потребовал бы старого `approved`-неиспользованного одобрения с совпадающим дайджестом в момент повторной отправки (смена заголовка туда и обратно с двумя рестартами) — это выходит за смысл RT9; отмечаю как непокрытый мутант.
- RT3 («A refused approval ends the run `refused` with no request sent») и RT8 (заголовок `Host`, отказ привязки с `Accept-Encoding`) не несут тега witness — тестов для них в файле нет; добавлять теги/тесты вне рамок этого обзора.
- Способности вне таблицы «Places the surface cannot reach yet» для этого witness (RUNTIME_SURFACE.md не редактировался, решает координатор):
  - `kernel_a10_only_owner_decides_grants_revokes` использует `stub.requests` (таблица перечисляет только `manifest.write_record`, `installation.select_instance`, `stub_service()`, `installation.set_credential`) — использование было и до правок;
  - `kernel_a10_approval_bound_to_request_digest` использует `stub.requests` (в таблице нет) — было до правок;
  - `kernel_a10_no_decision_changes_nothing` использует `stub.requests` (в таблице нет) — было до правок, новый контроль использует его же.
