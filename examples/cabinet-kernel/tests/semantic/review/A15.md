## Исправления

### `kernel_a15_node_execution_immutable` — исправлен
- Было: в сценарии ни одна запись не ссылалась на спуленный файл, поэтому release и стартовое удаление спула ни разу не встречали запись, чей файл они удаляют; мутант «release удаляет SpooledFile-записи / обнуляет outputs, ссылающиеся на файлы» проходил.
- Стало: добавлен функциональный узел `e_photo` (функция `photo`, `PHOTO_CODE`) от входа `word`; он исполняется при старте и спулит файл; проверяется, что его запись показывает `ShownFile` с `spooled_file`; запись входит в `written` и сравнивается поле за полем после resume, резолюции, approve, отказа cancel, capture, release и restart. Множества ключей дополнены `("e_photo", None, 1)`.
- Основание: A15 rule 1 «No operation edits or deletes one»; State 5 `read_spooled_file`: «the record outlives its bytes»; 80_notes `record_change` [SECURITY_BOUNDARY]: node executions и spooled files «are never updated or deleted once written».

### `kernel_a15_failure_detail_bounded_no_secret` — исправлен
- Было: единственный прогон с исключением длиннее `failure_detail_bytes_max`; мутант «detail = исключение, затем stdout, затем обрезка» проходил — обрезка отрезала напечатанный секрет.
- Стало: `LEAK_CODE` на входе `"brief"` печатает тот же секрет и бросает короткое исключение; контрольный прогон проверяет `crashed`, `detail_kind == "text"`, `"detail-marker"` в тексте и отсутствие `SECRET`; проверка `store_dump()` перенесена в конец и покрывает оба прогона.
- Основание: A03 rule 6 «only for the exception type and message, never stdout»; A15 rule 2; RT2.

### `kernel_a15_spool_run_ceiling` — исправлен
- Было: проверялся только случай «на байт больше»; мутант с нестрогим сравнением (`>=`) и мутант, считающий лимит по всем прогонам, проходили; кроме того, ничто не показывало, что `b_two_files` вообще способен успешно спулить два файла (провал мог быть не от лимита).
- Стало: после исходных проверок — контрольный прогон того же потока с `n_last` на 1 меньше: сумма спула ровно `spool_run_bytes_max` (536870901 + 5 + 6 = 536870912); первый прогон не освобождается и держит свои ~512 MiB. Ожидается `succeeded`, `b_two_files` — `[(1, "succeeded")]`, файлы `first` = 5 и `second` = 6 байт.
- Основание: A15 rule 3 «a run whose spooled files together exceed `spool_run_bytes_max`» (равенство — не превышение); формальный инвариант `sum(spool(run)) <= spool_run_bytes_max` — по одному прогону.

## Оставшиеся формальные / ограничения
- `kernel_a15_spool_file_ceiling` — частично: проверка `spool_file_bytes_max` недостижима при ceilings release v1 (`output_bytes` 64 MiB < `spool_file_bytes_max` 128 MiB; для операции `service_response_bytes_max` = `spool_file_bytes_max`, ответ на байт больше отказывается по лимиту ответа). Мутант без проверки `spool_file_bytes_max` проходит. Исправить без новой возможности (понижения ceiling в тестовом релизе) или решения владельца нельзя; RUNTIME_SURFACE.md не правился.
- `kernel_a15_file_outlives_run_only_as_fixture`: не проверяется, что после release байты незахваченного спуленного файла не остались где-либо ещё в сторе (мутант «каждый спуленный файл также публикуется в content-addressed area»). Для этого нужен `store_dump()`, не указанный для этого witness в таблице «Places the surface cannot reach yet», и файл, байты которого не совпадают с входом прогона (вход `word` хранится как StoredValue). Не добавлено; на усмотрение координатора.
- `kernel_a15_failure_detail_bounded_no_secret`: обрезка «слишком коротко» (например, до 100 байт) не ловится — 80_notes `execute_function` [PROVENANCE] требует только «at most» `failure_detail_bytes_max`, так что это не нарушение.
- Новых возможностей вне таблицы для своих witness тесты не используют.

## Вопросы владельцу

1. **RT3 `kernel_a15_spool_file_ceiling` недостижим при release v1.** Цитаты:
   - `02_rules_runs.md`, A15 Required test 3: «A function writing a file one byte over `spool_file_bytes_max` concludes `resource_exhausted` and leaves nothing in the spool.»
   - `02_rules_installation.md`, A20 rule 1: «| `output_bytes` | 67108864 |», «| `spool_file_bytes_max` | 134217728 |», «| `service_response_bytes_max` | 134217728 |», «The first four are the ceilings of the ResourceBounds M04 fields of the same name.»
   - `02_rules_functions.md`, A03 rule 5: «The output count is the sum of the canonical JSON bytes of every `value` output and the bytes of every `file` output … a limit hit (memory, process count, scratch, `output_bytes`) — `resource_exhausted`».

   Функция не может выдать файл больше 64 MiB, поэтому `resource_exhausted` всегда решает `output_bytes`, а проверка `spool_file_bytes_max` не наблюдаема (для операции ответ на байт больше одновременно превышает `service_response_bytes_max`). Нужен выбор: (а) принять текущий тест как свидетеля (исход решает `output_bytes`, проверяется только «nothing in the spool») и переформулировать RT3; (б) понизить `spool_file_bytes_max` ниже `output_bytes` / изменить ceilings; (в) свидетельствовать проверку статически (`release`, `kernel_sources()`) или новой возможностью фикстуры. Ревьюеры State 2 уже поднимали это (`questions/state2/round-50` «Function spool ceiling test», `round-72` «A15 spool-file limit testability», `round-75` «Spool file ceiling»), но решения владельца в 80_notes.md / HANDOFF_20260929.md нет.

Известные вопросы не затрагиваются.
