## Исправления

### `kernel_a19_service_timestamp_not_kernel_time` — исправлен
- Было: сервис без учётных данных. Фикстура ставит ядро «no credential» (RUNTIME_SURFACE.md «Installation»), а A17 rule 2: «A service the installation gives no credential … fails that request's pre-send check `credential_unresolved`» — ничего не отправляется, `len(stub.requests) == 2` и `succeeded` падали бы на правильном ядре. Время ядра прогона B было позже A, поэтому мутант «порядок по времени ядра» давал тот же `[run_b, run_a]`.
- Стало: `_stamp_service` вызывает `installation.set_credential(service_id, "X-Api-Key", CREDENTIAL)`; `t_run_b = T_RUN - 1_000_000` — порядок хранилища противоположен и времени сервиса, и времени ядра.
- Основание: A17 rule 2; A19 rule 3 «The kernel orders its records only by the store's order (K-17)»; A16 rule 6 (новые первыми).

### `kernel_a19_monotonic_reading_never_stored` — исправлен
- Было: та же проблема с учётными данными; искался только сам `sentinel` — сохранённый дедлайн (`sentinel + длительность`) проходил; пустой `store_dump()` давал ложный успех.
- Стало: учётные данные (через `_stamp_service`); `resource_bounds=_bounds()` при выдаче контракта, чтобы дедлайн песочницы был известен; поиск показаний и дедлайнов (`wall_time_ms` контракта, 30000, 60000) в нс/мкс/мс, текстом и 8 байтами; контроль `b'"answered"' in dump`.
- Основание: A19 rule 2 «a monotonic reading is never stored»; 80_notes `monotonic_deadline` «construct a MonotonicDeadline whose expires_at_ns is that reading plus duration_ms converted to nanoseconds … the deadline is held in memory by its caller only and is never stored in any record»; `send_prepared_request` (дедлайн `RELEASE_CEILING_TRANSPORT_TIMEOUT_MS`), `probe_sandbox` (границы = потолки), A20 rule 1; A18 rule 2 (байты значений в области значений).

## Ожидаемые значения
- Метки времени = значение `clock.set` шага, все поля записи одного запроса равны: State 5 Conventions «Time» («every timestamp … from `clock.kernel_now`»); поля и типы — State 6 (`KernelInstant.epoch_us`, `Slot.created_at`, `ContractVersion.issued_at`, `TrialCase.added_at`, `Implementation.submitted_at`, `TrialExecution.executed_at`, `AdmissionVerdict.decided_at`, `Activation.activated_at`, `Flow.created_at`, `FlowVersion.authored_at`, `FlowActivation.activated_at`, `Run.started_at/ended_at`, `NodeExecution.started_at/ended_at`).
- `invalid_request` для неизвестного поля: A16 rule 4, State 5 таблица кодов; запросы контроля соответствуют `*Request` моделям State 6 (проверены поля всех 30 операций, `OwnerDecision` `approve`, `AttemptResolution` `applied`, `AttemptKey`, `SpooledFileKey`).
- Порядок «новые первыми»: A16 rule 6, State 5 `store.page_records`.
- Выход сервиса как значение `'"<stamp>"'`: `ShownProducedOutput.value` → `ShownContent.json_text`.
- 30000 / 60000: A20 rule 1 (`wall_time_ms`, `transport_timeout_ms`).
Все ожидаемые значения следуют из A19, A16, A17, A20 и State 5/6; исправлять значения не потребовалось.

## Оставшиеся формальные / ограничения
- RT3 проверяет «нет поля текущего времени» пробой имён (`now`, `current_time`, `kernel_now` и поле времени создаваемой записи); поле с другим именем статически не перечисляется — схемы State 6 его не содержат, и контроль идёт по полям моделей.
- `installation.set_credential` для `kernel_a19_service_timestamp_not_kernel_time` и `kernel_a19_monotonic_reading_never_stored` необходим (без него по A17 rule 2 ничего не отправляется), `clock.set` в `kernel_a19_monotonic_reading_never_stored` был в тесте до ревью: строки таблицы «Places the surface cannot reach yet» были неполны — явная ошибка, строки исправлены (отмечено в SUMMARY.md). Чтение `installation.owner_token`/`agent_token` в `kernel_a19_request_cannot_supply_time` (было до ревью) — в общем списке расхождений SUMMARY.md, таблица не менялась.
