## How this case is designed

Owner's decision 2026-09-29: Cabinet Flow restarted as a smaller kernel instead of cutting the old design.
Every state is closed by question rounds, not only gates:

```bash
python tools/design_questions.py ask examples/cabinet-kernel --state <N>
python tools/design_questions.py status examples/cabinet-kernel --state <N>
```

- The round asks the Factory's generator model (`gpt-5.3-codex`). The provider key comes from the environment
  or from an env file named in `DESIGN_QUESTIONS_ENV_FILE` / `CODE_FACTORY_ENV_FILE`; do not search for keys.
  In this session rounds ran through the Factory's own env loader (`import llm_config` in the Factory line).
- Closing a question: first ask who uses it (nothing → remove it); then a pointer written where the reader
  looks, data, or the owner's decision with options and a recommendation. A recommendation is recorded as the
  owner's only after the owner confirms it.
- A state is closed when the latest round raises no topic in two reviews and the texts are unchanged.
- Rounds are kept under `questions/state<N>/`. State 1 took four standard rounds (repeated topics 1, 2, 2, 0),
  after ten ad-hoc rounds while the method was being found.

## Assessment of the question tool (end of session, 2026-09-29)

What it showed:

- It sees what gates cannot: before generation it named 86% of the audited unclosed decisions, most in all
  three reviews, while every gate had been green.
- Its forced guess often equals the wrong value the generator later wrote (`"sandbox_execute"` in all three
  reviews).
- It caught the designing agent's own errors: a pointer that never reached the text, contradictions in fresh
  edits, a missing action ("add a trial case") without which acceptance case 2 was impossible.
- A round costs about 60k tokens; one Route B assembly about 650k.
- With the stop rule it converges: State 1 standard rounds repeated 1, 2, 2, 0 topics.
- It does not age like a gate: the generator's model asks about the current text, not about a past incident.

Its limits:

- It does not replace checking the code: where the spec is clear and the generator errs (half of the audit's
  generator misses), there is nothing to ask. That needs the obligation audit after generation, still manual.
- The closure criterion is statistical: an important point can come from one review only ("add a trial case"
  did). Single-review topics must be read, not ignored.
- Its quality depends on the per-state `question_scope`; without a stop rule reviews descend forever.
- It pulls toward adding rules; "who uses it" is written in `QUESTIONS.md` but not enforced by the tool.
- Evidence is thin: 4 modules of one application, judged by models; no noise test on a working application,
  no rounds yet on States 2–5.

Next for the tool:

1. Run it on a working application (e.g. Cabinet_web State 0–2): many questions there mean it asks too much.
2. Make the obligation audit after generation a standard tool — the half this one does not close.
3. Make the round summary require a reading of single-review topics, not only a count of repeats.

## Owner's question: is the kernel needed at all? (recommendation, not a decision)

Asked on 2026-09-29: are schemas, manifests and an agent enough? The agent can already read the platform
manifest, call services through MCP and Cabinet Actions, write and run processing scripts and show the owner
the result before writing — which is what both acceptance cases are. The kernel adds four things only:
guarantees held by code rather than by the prompt (effect only on the exact input seen, no secrets in agent
code, no self-approval); repeatability without an agent; tools that stay repaired; access without the owner.

Recommendation: before State 2, run both acceptance cases with what exists (agent, manifest, MCP, owner in the
conversation) and record where it hurt — an effect the owner did not see, repeated work, a repaired script
breaking again, a need to run without the owner. Build only what that shows, narrowest first — most likely an
effect gateway (approval on the exact input plus idempotency key) or a store of proven tools. The State 0 and
State 1 of this case stay as the map for whichever part turns out to be needed.
