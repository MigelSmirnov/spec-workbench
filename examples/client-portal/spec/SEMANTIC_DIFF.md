## Потерянное поведение, найденное проверкой Route B по `071062af` (2026-11-10; не экспортировано)

**Поведение работающего сервиса (принятый код) не меняется.** Исправляется то, что сгенерированный по `071062af` код сделал иначе, потому что ноты этого не говорили.

## Уборка после проверки Route B по `b3bfb504` (2026-11-10; не экспортировано)

**Поведение работающего сервиса (принятый код) не меняется.** Исправляется то, что сгенерированный по `b3bfb504` код сделал иначе.

## Binary storage settings read through runtime_settings (2026-11-09; не экспортировано)

**Изменение поведения (узкое).** Решение владельца 2026-11-09 (одобрено),
Factory code-factory #201: детерминированный `binary_storage` берёт корень
хранилища и предел чтения через `runtime_settings` (SPEC_STANDARD §6.11).

- **Было (принятая спека `018b2e2e`, работающий сервис):** строки
  `BINARY_STORAGE_ROOT` и `BINARY_MAX_READ_BYTES` таблицы запуска имели
  `target: validation_only`: старт их проверял, а эмитированный
  `binary_storage` (`binary_storage_backend` v1) сам читал обе переменные
  окружения при каждом чтении (`adapters/binary_storage.py`).
- **Стало:** обе строки читаются в поля `RuntimeSettings.binary_storage_root`
  (`str`) и `RuntimeSettings.binary_max_read_bytes` (`int`);
  `binary_storage_backend` schema_version 2 (эмиттер
  `python_filesystem_binary_storage_settings_v1`) называет их в `settings` и
  вызывает `load_runtime_settings` при каждом чтении. Отсутствующая или
  неверная настройка теперь всплывает через `load_runtime_settings`: на старте
  — как и раньше, остановкой старта; при чтении — ошибкой загрузки настроек,
  которую модуль отдаёт как `BinaryStorageError` (раньше — его собственная
  проверка переменной, тот же `BinaryStorageError`). Клиент видит то же.
- **Структура:** ребро `binary_storage → runtime_settings`
  (`imports.module_internal`, `65_imports.json`, `code_outdated` против кода
  `459ac96c`); State 3 `binary_storage` знает `runtime_settings`.

Происхождение: владелец 2026-11-09; A14, A30 (`02_rules.md`), State 3
(`30_modules.md`), State 1 (`01_models.md`), `60_data_closure.json`,
`60_model_closure_contracts.json`; закрывает State 2 r103/r107–r109 (FA019).

## Registry URL read through runtime_settings (2026-11-09; не экспортировано)

**Изменение поведения.** Решение владельца 2026-11-09 (одобрено): адрес
Registry читается только через `runtime_settings` (SPEC_STANDARD §6.11:
второго читателя окружения не бывает).

- **Было (принятая спека `018b2e2e`, работающий сервис):** сервис стартует
  без `REGISTRY_BASE_URL`; шлюз `registry_gateway` сам читает переменную при
  каждом запросе к Registry, и при её отсутствии каждый такой запрос падает
  ошибкой `RegistryBoundaryError` с видом `transport_error` (A6, прежний
  текст A30; код `adapters/registry_gateway.py` `_registry_url`).
- **Стало:** `REGISTRY_BASE_URL` — обязательная строка таблицы запуска
  `config.runtime_environment_variables`, читается в поле
  `RuntimeSettings.registry_base_url`. Отсутствующее или пустое значение
  останавливает старт сервиса (R0-10), а не отдельный запрос. Шлюз берёт
  адрес из настроек, которые возвращает `load_runtime_settings`, и сам
  окружение не читает. Неподходящий адрес (не http/https, с userinfo)
  по-прежнему отклоняется при запросе как `transport_error`.
- **Следствие для команды `staff_bootstrap_cli`:** она тоже читает настройки
  через `load_runtime_settings`, поэтому без `REGISTRY_BASE_URL` теперь не
  запускается и она.
- **Структура:** константа поставщика данных `REGISTRY_BASE_URL_VARIABLE`
  удалена; `runtime_settings` стоит в `module_order` перед
  `registry_gateway`; импорт `load_runtime_settings` в `_registry_url`
  (`65_imports.json`, `code_outdated` против кода `459ac96c`).

Происхождение: владелец 2026-11-09; A6, A30 (`02_rules.md`), State 3
«Configuration» и порядок модулей (`30_modules.md`), State 4
`flow:start_service_and_answer_health` (`40_flows.md`), State 5 `load_runtime_settings` и
`list_active_projects` (`50_public_apis.md`), ноты `registry_gateway`
(`80_notes.md`), `SOURCE.md` «Data placement»; в State 2 раунд r101 T14.

## Построение записей эмиттером `record_builders` (2026-11-08/09; не экспортировано)

Каждую запись, которую модуль, написанный моделью, строит из входов, теперь
строит сгенерированная функция детерминированного модуля `record_builders`
(86 функций). Откуда берётся каждое поле — закрытые данные, а не проза нот.
Для большинства полей значения те же, что даёт работающий сервис. Меняется
поведение в следующих местах:

- **Q12, исправление живой ошибки.** Список активных проектов читается из
  Registry по пути `projects/active`, как его называет State 0, а не
  `projects`. Сейчас сервис запрашивает весь список и отбрасывает
  неактивные сам при разборе (фильтр при разборе остаётся).
- **Q07.** Распределение расхода на раздел показывает имя раздела: название
  плана этого раздела в активной версии бюджета. Нет активной версии или
  нет плана для раздела — имени нет. Для «прочих расходов» имени нет
  всегда. Сейчас имя не показывается никогда.
- **Q09.** Появляется явная граница разбора распознанного документа
  `decode_recognition_publication`: искажённые данные или неподдерживаемая
  версия контракта отклоняются ошибкой проверки расхода.
- **Q10.** Неполный объект публикации (без поля, например `confirmed_at`)
  отклоняется ошибкой проверки до любой записи, а не падает ошибкой
  атрибута.
- **Время подтверждения.** `confirmed_at` с часовым поясом приводится к UTC
  без пояса, как требует правило времени A28 (так уже было для даты фото).
- **Выдача ключа зрителю и сервису.** Идентификатор ключа создаёт операция,
  выдаёт секрет для него и передаёт оба в построение записи; прежняя схема
  данных, в которой построение само создавало идентификатор, не позволила
  бы найти ключ при входе.

Подтверждают работающий сервис (без изменения поведения): Q01–Q04 (кто и когда
изменил расход, документ, распределение, фото), Q06 (строка бюджета не
помечает неразнесённые распределения, только общий счётчик), Q08 (готовность
сервиса — после проверки хранилища). Q05 меняет значение, которое пока не
строит ни одна операция; Q11 открыт.

Спека кейса: sha256 `53ef1682…` до обходов и проверок ниже по ветке.

### 3. Уточнения правил в State 2: записи о повторе, время, уязвимости

Принятая спецификация этих правил не формулировала. В кейсе они записаны
явно, и где поведение уже было таким, оно не меняется.

- **Повтор публикации снимка сметы (A8, A18; INV-020, INV-021).** Повтор с
  тем же содержимым считается идемпотентным повтором. Повтор с другим
  содержимым — конфликт. В обоих случаях снимок и бизнес-данные не
  меняются, но попытка записывается: свой результат импорта со своим
  `import_id` и запись журнала `snapshot.import`. Раньше в тексте
  встречалось «ничего не меняется», и выходило, что попытку не записывают.
- **Время (A28; CLK-001, CLK-002).** Операция читает «сейчас» ровно один
  раз и только через источник времени. Это касается и записи меток, и
  сравнения с сохранённым сроком. Срок действия считается как этот момент
  плюс TTL; присланные извне время и даты сохраняются как есть
  (`document_date`, `payment_date` — календарные даты, а не моменты).
  Длительности (окно попыток входа зрителя) меряются только монотонными
  часами того же источника, по одному чтению на запрос. Они нигде не
  хранятся и не смешиваются с обычным временем. Никакой другой модуль
  системные часы напрямую не читает.
- **Уязвимые зависимости (A32; DEP-001, DEP-002).** Все зависимости
  закреплены через `==`. Источник известных уязвимостей — OSV (PyPI).
  Проверяется каждая библиотека, установленная в образ, а не только прямые
  зависимости. Сервис не запускается из образа, где у какой-либо
  установленной версии есть известная уязвимость. Пересборка с теми же
  пинами, которая прошла проверку, может деплоиться. Как получать и
  проверять снимок OSV и как сопоставлять версии, решает маршрут деплоя
  (Factory PR #188) и его проверка в code-factory #189.

## Структурные изменения (поведение не меняется)

### 4. Один источник времени: `system_clock` (clock v5)

- Новый модуль `system_clock` с двумя функциями: `utc_now()` (время UTC
  без часового пояса, то же значение, что давал `datetime.utcnow()`) и
  `monotonic_seconds()` (`time.monotonic()`).
- Новые правила `rules.system_clock_backend` (v5, детерминированный эмиттер)
  и `rules.time_source_policy`: обычное время и длительности читаются только
  через `system_clock`, одно чтение за вызов, длительности не хранятся.
- 44 операции в двенадцати модулях и `install_transport_guards` берут время
  через этот модуль (44 вызова `utc_now`, один `monotonic_seconds`).
- `rules.clock_policy` сохранено как принятое значение.
- Гейт источника времени Фабрики на живом коде будет блокировать, пока
  Route B не перегенерирует эти модули.

### 5. Таблица исключений и исключения без параметров

- 18 конструкторов `X.__init__` исключений, объявленных в модулях, убраны
  из контрактов вместе с их notes. Генератор пишет каждое такое исключение
  как `class X(Exception): pass`, и оно выбрасывается без аргументов. Живой
  код текст исключения не читает: ошибки переводятся в HTTP-статус по типу.
- Кто какое исключение владеет и что оно значит, записано в
  `60_exception_taxonomy.json` (15 исключений после удаления писем); прежний
  смысл каждого контракта сохранён дословно.
- Остались конструкторы с полями: `RegistryBoundaryError(kind)`,
  `SnapshotContentRejected(reason)`, `PersistenceError` (его задаёт эмиттер)
  и `conceal_authentication_failure() -> AuthenticationRejected`.

### 6. `BootstrapAlreadyCompleted` → `BootstrapAlreadyCompletedError`

Экспорт исключений модуля в Фабрике узнаёт класс только по суффиксу
`Error`. Имя внутреннее: HTTP его не отображает, а команда первичной
настройки ловит его по типу и печатает ту же строку с кодом выхода 3.
Снаружи ничего не меняется.

### 7. Убраны наборы правил без потребителя (FA018)

`rules.audit_action_catalog`, `rules.audit_significant_mutation_actions`,
`rules.revocation_cascades`, `rules.staff_bootstrap_policy` не читает ни
один модуль: по стандарту notes не могут ссылаться на них адресом, а код
держит эти значения в себе. Сами факты остались в решениях (A11, A13, A29),
а значения записаны словами в notes операций, которые их используют.
Поведение то же.

### 8. Единица работы с базой (unit of work)

- Новое правило `rules.sqlite_unit_of_work_backend` (эмиттер
  `python_sqlite_unit_of_work_v1`): `PortalStore`, `PortalTransaction`,
  `PersistenceError` в `portal_store`. Одно соединение на транзакцию. Десять
  репозиториев доступны через транзакцию в фиксированном порядке; хранилище
  первичной настройки — `SqliteStaffBootstrapStore`.
- `portal_store` и `staff_bootstrap_store` теперь строит детерминированный
  эмиттер. Модель их больше не пишет.
- Notes, висевшие на классах `Sqlite*Repository`, перенесены на методы
  портов (`BudgetRepository.*`, `ExpenseRepository.*` и т. д.) и на
  `PortalUnitOfWork.*`. Прикладные модули импортируют `PortalTransaction`.
- Добавлен раздел `implementation_obligations`: шесть интерфейсов и их
  реализации. Этого требует новое правило Фабрики, и без раздела принятая
  спецификация не проходит текущий нормализатор. Следствие для Route B:
  сгенерированные репозитории будут наследовать свой порт. Это форма кода,
  а не поведение.

### 9. Отложенный поставщик данных (data provider)

Не входит в эту миграцию (решение координатора 2026-11-06). В принятой
спецификации notes ссылались на значения адресами `= rules.*` (189 мест);
по действующему стандарту notes такие адреса не принимают. Теперь
значения записаны в notes словами, точно как в принятых `rules`/`config` и
коде: EUR, 2 знака и ROUND_HALF_UP, длина пароля 12–128, TTL сессий 12 ч и
30 дней, пути и таймаут Registry, коды выхода и т. д. Шестнадцать таких
значений перечислены в `SOURCE.md`. Поставщик данных (§6.10) — отдельная
будущая работа: он вновь откроет States 1, 3 и 6.

### 10. Что ещё показывает сравнение

- **Импорты.** Таблица импортов модулей выведена из решений
  (`65_imports.json`) и сверена с кодом. Модули стали импортировать то, что
  действительно используют: `system_clock`, `PortalTransaction`, а
  неиспользуемые модели и функции ушли из импортов. Девять модулей, которые
  пишут в журнал через `append_audit`, теперь импортируют тип
  `AuditRepository`, а `staff_bootstrap_cli` — `StaffBootstrapPort` (FA015):
  эти типы нужны нарезчику Фабрики и Spec Inspector для промпта модуля.
- **Notes.** Их 1090 вместо 851: notes с уровня модулей и классов
  повторены на каждой операции, которую они ограничивают. Добавлены notes
  для эмиттированных портов и времени.
- **Модели и контракты.** Кроме перечисленного выше, ни одна сигнатура
  оставшихся контрактов не изменилась.
- **Маршрутизатор и хранение.** Из `http_router_backend` ушли шесть
  маршрутов и три ошибки писем, из `persistence_backend` — таблица и
  репозиторий доставки писем. Остальное без изменений.
- **Детерминизм.** Ушли две записи (`_build_challenge_issue_view`,
  `_build_email_delivery_request`) вместе с письмами.
- `properties` и `standard_version` совпадают.
