## Modeling conventions

- Identifiers are UUIDs generated by the portal, except identities owned by
  external systems (`project_id` — Registry; `recognized_document_id`,
  `intake_id` — intake boundary; `estimate_id`/`estimate_version` — producer)
  and the retry identities a staff caller supplies with its request
  (`payment_id` of a work payment, `intake_id` of a progress photo; the
  portal never mints either). Until the intake service exists the
  "intake boundary" is the authenticated staff request (R0-17), which
  supplies `recognized_document_id` and `intake_id`.
- Money is `Decimal` with 2 fraction digits, currency always `EUR`; rounding
  policy is a State 2 rule. Negative amounts never appear in stored records;
  negative values exist only in derived balances.
- Timestamps are timezone-aware UTC. Portal-owned event times are distinct
  from source-system times (`captured_at` vs `registry_updated_at` pattern).
- Secrets (viewer access tokens, session tokens, passwords, reset tokens,
  service credentials) are stored **only** in verification form
  (`*_hash`); plaintext of a secret the portal issues exists only in the
  issuing response, and plaintext a caller presents or chooses (a password
  at login, account creation, password change or bootstrap; a session token,
  viewer code or service credential at authentication) exists only in that
  request while it is hashed or verified. No plaintext is ever persisted,
  logged or audited.
- Percentages are integers 0–100 inclusive.
- **Union encoding policy.** `kind: discriminated_union` is not yet a
  materialized Factory capability (see `FACTORY_COMPATIBILITY.md`). Every
  "exactly one of" concept in this domain has 2–3 variants with at most one
  payload field, so each is encoded in the established supported form — a
  closed enum discriminant plus a conditionally-required field enforced by a
  local model validator. This is a semantically equivalent supported
  encoding, not a flattened union; the affected models are marked
  `[closed-choice]` below. If a future model outgrows this shape, the design
  returns to a named union and handoff blocks on the Factory capability.
- Two-state lifecycles with audit needs carry an explicit `status` enum plus
  provenance timestamps; pure expirations (sessions, tokens) derive state
  from `expires_at` / `used_at` / `revoked_at`.

## Model M01 — ClientViewer

### Meaning

- **Kind:** persisted entity.
- **Purpose:** permanent read-only viewer identity of one client who may have
  several projects.
- **Fields:** `viewer_id: UUID`, `display_name: str`,
  `status: ViewerStatus (active | revoked)`, `created_at`, `created_by:
  UUID (staff)`, `revoked_at: datetime | None`, `revoked_by: UUID | None`.
- **Created/modified by:** administrator only (R0-14). `display_name` is
  set at creation and never changes: no operation renames a viewer; the only
  modification is revocation.
- **Lifecycle:** `active → revoked` (terminal). Revocation invalidates all
  viewer sessions and credentials but deletes nothing.
- **Must not contain:** email, password, registration state, profile data,
  Registry customer data.

### Carried changes

"operator or administrator" narrowed to administrator by R0-14 (accepted
`create_viewer`, `revoke_viewer` authorize access management); no rename
operation exists in the accepted spec (owner 2026-11-06: current service
behaviour accepted; technical decisions delegated).

### Identity

entity

### Identity evidence

- Substitution: Two viewers with equal display names are two clients; grants, credentials and audit name one of them.
- Continuity: The same client stays the same viewer while it moves from active to revoked.

### Source of truth

Backend-owned record of the portal.

### Lifecycle candidate

`active → revoked`, terminal (Meaning).

### Persistence candidate

Durable persistence candidate.

## Model M07 — StaffProjectAssignment

### Meaning

- **Kind:** persisted entity.
- **Purpose:** explicit operator scope for one Registry project; operator role
  capability alone never grants access to every project.
- **Fields:** `assignment_id: UUID`, `staff_id: UUID`, `project_id: UUID`,
  `status: GrantStatus (active | revoked)`, `created_at`,
  `created_by: UUID (administrator)`, `revoked_at: datetime | None`,
  `revoked_by: UUID | None`.
- **Rules:** at most one assignment record per `(staff_id, project_id)`,
  active or revoked; a revoked assignment is terminal and the pair cannot be
  assigned again (the second assignment is refused as a persistence
  conflict; no operation reactivates one). Revocation blocks the next
  project-scoped authorization check without changing project records or
  other assignments. In the current documented
  single administrative area, administrators cover all projects through that
  area policy; introducing a second area requires an explicit area model and
  is not simulated with assignments. For an administrator the project scope
  that State 0 invariant 2 names "grant/assignment" is this administrative
  area (State 0, Roles: "within their administrative area"; State 2 A2),
  not a StaffProjectAssignment. The assignment operation accepts any
  existing staff account. An assignment naming an administrator is stored
  and audited like any other, but creating or revoking it neither adds nor
  removes access: authorization never consults assignments for the
  administrator role, whose read and mutation access comes from the
  administrative area whether such an assignment is active, revoked or
  absent. State 0's "an existing grant or assignment … keeps giving read
  access" (R0-24) therefore concerns operator assignments; for an
  administrator the area keeps giving it. Since no role ever changes (M05),
  an assignment never gains or loses effect through a role change.
- **Created/modified by:** administrator only.

### Carried changes

Repaired to the accepted spec: one assignment per pair (note of
`create_staff_access_schema`: UNIQUE `(staff_id, project_id)`; the insert
note: a second assignment for a pair surfaces as a persistence error);
`assign_staff_project` checks only that the account exists (Factory code
`application/staff_identity.py`), and `_require_staff_scope` returns for an
administrator before reading assignments (`application/authorization_guard.py`).
Owner 2026-11-06: current service behaviour accepted; technical decisions
delegated.

### Identity

entity

### Identity evidence

- Substitution: Each assignment scopes one operator to one project and is revoked on its own.
- Continuity: An assignment stays the same record from creation to revocation.

### Source of truth

Backend-owned record of the portal.

### Lifecycle candidate

## Model M13 — ServicePrincipal

### Meaning

- **Kind:** persisted entity.
- **Purpose:** named machine identity for inter-service publication.
- **Fields:** `service_principal_id: UUID`, `name: str`,
  `source_type: ProducerSourceType` (closed catalog; initially
  `estimate_producer`), `status: PrincipalStatus (active | disabled)`,
  `scope_mode: ProducerScopeMode (all_projects | granted_projects)`
  `[closed-choice]`, `created_at`, `created_by`, `disabled_at | None`,
  `disabled_by | None`.
- **Rules:** capability set is static per `source_type` (import-side only:
  `portal.estimate_snapshot.import`,
  `portal.estimate_snapshot.read_import_result`); `all_projects` scope is an
  explicit administrator decision recorded in audit; with `granted_projects`
  every import requires an active `ProducerProjectGrant`. The
  administrator's choice of `all_projects` when creating the principal is
  the "explicitly granted capability" through which State 0 lets a global
  producer exist (recorded in the `principal.create` audit); with it the
  scope mode alone admits an import for any project the Registry reports
  active, and no project grant is consulted.
- **Created/modified by:** administrator. `name`, `source_type` and
  `scope_mode` are set at creation and never change; the only modification
  is the status change `active ↔ disabled` (disabling revokes every
  credential of the principal; re-enabling restores none of them, so a
  re-enabled principal needs a newly issued credential). Disabling sets
  `disabled_at` and `disabled_by`; re-enabling clears both to `None`, so
  they always describe the current disablement only and earlier ones are
  found in the `principal.disable` audit entries. Grants of a `granted_projects` principal
  therefore never meet a scope switch.

### Carried changes

Repaired to the accepted spec: `create_service_principal` persists

## Section linking at activation

The former paragraph after SectionPlan, kept; it spans M21–M23 and the
allocations, so it stands outside one model.

An imported version's plans are built by `source_key` linking:
matched keys reuse the existing `PortalSection` (rename allowed), unmatched
source sections create new `PortalSection` records. Sections of the previous
version absent from the new one keep their identity and history; their
allocations would be *unresolved against the new version* (a derived state,
not a stored flag), so they must be explicitly re-allocated by an operator
before that version can be activated: activation is refused while any is
unresolved (accepted `activate_budget_version`).
`Other expenses` is not a section and is independent of versions.

In the running service no operation creates an imported budget version
(Q11, deferred), so this linking never runs; it describes the design Q11
starts from. Which operation builds an imported version with its plans and
new sections, and that it must do so before activation so that operators
can re-allocate to those sections, is Q11's to design; no operator of the
running service meets this case. The State 0 "explicit mapping" of existing allocations is, in
the running service, the staff re-allocation of an expense (its whole
allocation set replaced by explicit instructions to sections of the
project, M29); activation of a version is refused while any section
allocation would be unresolved against it, and no other mapping operation
exists. Running service recorded (accepted `activate_budget_version`,
`replace_expense_allocations`; owner 2026-11-06: current service behaviour
accepted; technical decisions delegated).

## Projections and answers

Answers a caller reads and transient results between modules. They are values
(Factory `3a72da32`: "inbound commands, read projections, operation outcomes,
compositions around an entity, actor contexts, one-time secret responses"),
named here and shaped in States 5 and 6. The text under each heading is the
former State 1 text.

### Authentication and authorization context

Transient internal/boundary results; never persisted or logged as complete
objects because session/credential plaintext may be present.

- `IssuedSecret` — `plaintext: str`, `verification_hash: str`; created by
  `credential_security`, consumed immediately by an issuing identity module,
  never persisted or logged as a whole object.
- `PresentedSecret` — `record_id: UUID`, `secret: str`; parsed from the opaque
  plaintext envelope. `record_id` is only a lookup selector and grants no
  authority without successful verification against the selected record hash.
- `StaffSessionGrant` — `session_id: UUID`, `staff_id: UUID`,
  `role: StaffRole`, `token: str` (plaintext, returned once),
  `expires_at: datetime`.
- `StaffActorContext` — `session_id: UUID`, `staff_id: UUID`,
  `role: StaffRole`; produced only by resolving a valid active StaffSession.
- `ViewerSessionGrant` — `session_id: UUID`, `viewer_id: UUID`,
  `token: str` (plaintext, returned once), `expires_at: datetime`.
- `ViewerActorContext` — `session_id: UUID`, `viewer_id: UUID`; produced only
  by resolving a valid active ViewerSession.
- `ViewerCredentialIssue` — `credential: ViewerAccessCredential`,
  `secret: str` (plaintext, returned once).
- `ServiceCredentialIssue` — `credential: ServiceCredential`,
  `secret: str` (plaintext, returned once).
- `ServiceActorContext` — `service_principal_id: UUID`,
  `source_type: ProducerSourceType`, `scope_mode: ProducerScopeMode`,
  `key_version: int`. It contains no credential plaintext.
- `AuthorizedProjectContext` — `actor_kind: ActorKind`, `actor_id: UUID`,
  `key_version: int | None` `[required iff actor_kind = service]`,
  `project_id: UUID`, `capability: Capability`,
  `registry_status: RegistryProjectStatus`.

These DTOs are evidence of completed authentication/authorization, not
request claims. The API cannot construct them from role, capability, actor ID,
or project ID fields supplied by a caller.

- `AuthorizedBinaryReference` — trusted internal DTO with
  `project_context: AuthorizedProjectContext`,
  `object_kind: BinaryObjectKind (expense_document | progress_photo)`,
  `object_id: UUID`, `file_ref: str`. It is produced only by the owning
  expense/photo module after visibility and project checks and is the sole
  accepted input reference for `binary_storage`.
- `AuthorizationPrincipalKind` — closed enum: `staff | viewer | service`.
- `ProjectAuthorizationRequest` — internal closed-choice DTO with
  `principal_kind: AuthorizationPrincipalKind`,
  `staff_actor: StaffActorContext | None`,
  `viewer_actor: ViewerActorContext | None`,
  `service_actor: ServiceActorContext | None`, `project_id: UUID`,
  `capability: Capability`, `mutation: bool`.
  Exactly the actor field selected by `principal_kind` is required; the other
  two are absent. Public actor-specific guards are the only producers.

### Derived views (computed, never primary state)

Recomputable at read time from owning records; no stored totals:

- section actual materials (included confirmed allocations to the section);
- `Other expenses` total (included confirmed allocations to
  `other_expenses`);
- remaining materials per section (plan − actual; overspend shown negative,
  never clamped);
- budget totals (sum of active-version plans);
- completed work value per section (`work_planned × completion_percent /
  100`);
- overall progress (weighted by `work_planned` across sections with planned
  work; unavailable when total planned work is zero — never an arithmetic
  mean, never a guess);
- payments total; work balance (`completed work value − payments total`,
  presented as `Completed ahead of payments` / `Unused advance payment`);
- unresolved allocations against the active version (allocations targeting
  sections without a plan in the active version);
- viewer project list (active grants resolved server-side).

State 4 exposed that these observable results need concrete boundary DTOs;
they are added here as a backward correction before flow/API design. None is
persisted, and none contains `file_ref`.

- No `dict`, `Any`, generic `metadata`, or open `status: str` remains
  except `ProjectReference.status`, the Registry's own string (M16); the
  only pass-through strings are external identities, that status and
  provenance references owned by other systems.
- The stable-section design keeps allocations and progress stable across
  budget-version changes, matching the State 0 transition rules.
- Union-shaped concepts use the supported closed-choice encoding
  deliberately; the decision is recorded and reversible per model.
