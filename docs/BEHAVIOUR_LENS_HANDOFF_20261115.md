`run_graph_prompt_depth_20261115`, и предлагает два дополнения к микроскопу

## Главное

1. Микроскоп сегодня сравнивает кандидатов по форме и по символам: линза 0
   статическая, линза 1 — выборка с разбросом размеров и форм, линза 2 —
   цепочка хранения обязательства (`absent` / `unstable` / `stable`).
   Поведение кандидатов он не сравнивает.
2. Эксперимент сравнил поведение и нашёл то, чего линзы 0–2 не показывают:
   нерешённые вопросы, непокрытый приёмкой случай и четыре дыры в наборе
   тестов.
3. Способ обхода графа от глубины промпта не зависит. Поведение зависит от
   записанных решений: без нот не прошёл ни один кандидат.
4. Отсюда два предложения (линзы 3 и 4) и два режима работы: прямой, от
   короткого описания к спеке, и обратный, от готового сервиса к спеке.

## Что из этого следует

Это толкование, а не измерение.

- Ноты `plan_run` несут два груза: решения о поведении и протокол с соседними
  модулями (какой вариант источника представляет константу, порядок
  элементов в ответе). Советов о способе написания кода в них почти нет.
- Расхождение кандидатов показывает нерешённые вопросы. Чем богаче описание,
  тем больше вопросов проявляется: страница A дала 4, ветка C — ещё семь
  групп.
- У способа есть слепое пятно: случаи, где все кандидаты согласны между
  собой и расходятся с намерением. В ветке C таких групп три. Их ловят
  только тесты-свидетели, сценарии владельца и сборка с соседними модулями.
- «232 из 232» не доказывает совпадения поведения там, где набор слеп.
  Самая серьёзная дыра — M08 и M09: нарушение контракта и таймаут функции
  засчитываются как успех, и ни один тест этого не замечает.

## Предложение: линза 3 «расхождение поведения»

Вход: N кандидатов с общим интерфейсом и набор сценариев. Выход: класс
каждого сценария.

| Класс | Условие | Что делать |
|---|---|---|
| `stable` | все кандидаты дают один ответ, и он совпадает с эталоном | ничего |
| `split` | ответы разделились k / N | вопрос владельцу: сценарий, варианты ответа, голоса |
| `agreed_off_reference` | все согласны между собой и расходятся с эталоном | проверить, потеряно ли решение на пути к промпту или эталон случаен |

Эталон — свидетель, принятый модуль или работающий сервис. Классы
продолжают вердикты линзы 2, только предмет наблюдения — поведение на
сценарии, а не использование символа.

Источники сценариев: существующие семантические свидетели, операторские
сценарии, пробные сценарии на граничные случаи. Пробный сценарий
сохраняется, если на нём кандидаты разошлись.

Условие применимости: общий интерфейс. В ветке A его не было, и сравнение
делалось чтением кода.

## Предложение: линза 4 «мутанты приёмки»

Вход: принятый модуль и список одиночных смысловых изменений, каждое —
правдоподобная ошибка генератора. Выход: убит, выжил, эквивалентен; для
выжившего — причина. Определения мутантов эксперимента лежат в
`mutants/mutants.py`.

Назначение: показать, чему из результата линзы 3 и «N из N» можно верить.

## Режим 1, прямой: от короткого описания к спеке

1. State 0, только страница продукта. N генераций в свободной форме,
   сравнение чтением. Даёт грубые вопросы; в эксперименте — четыре.
2. Страница и общий интерфейс: сигнатуры и формы данных, без нот. N
   генераций, линза 3 на пробных сценариях. Вопросы класса `split` идут
   владельцу.
3. Ответ владельца записывается дважды: решением в State 2 и свидетелем.
4. Повтор, пока на пробных сценариях остаётся `split`.

Что это может заменить: часть раундов вопросов на States 0–2. В
cabinet-kernel каталог `questions/` занимает 62 МБ в 5135 файлах.

Что не заменяет: проверку чтением для правил с высокой ценой ошибки
(одобрение эффектов, персональные данные, деньги) и сценарии владельца.

Не измерено: сходится ли цикл за малое число кругов при старте с нуля. В
эксперименте провалы ветки C нашли 232 теста, которые сами получены тяжёлым
процессом.

## Режим 2, обратный: от готового сервиса к спеке

Автоматически извлечь спеку из сервиса микроскоп не может. Работающий
сервис используется как эталон, N = 1.

1. Зафиксировать интерфейс: возможности из `platform/manifest/` или
   HTTP-маршруты.
2. Написать страницу намерения словами владельца, не выводя её из кода.
3. Сгенерировать N кандидатов за тем же интерфейсом. Начинать с чистой
   функции ядра сервиса.
4. Прогнать существующие тесты сервиса и пробные сценарии на эталоне и на
   кандидатах.
5. Класс `agreed_off_reference` здесь становится вопросом «решение или
   случайность»: сервис ведёт себя так, как никто из кандидатов по описанию
   не сделал.
6. Ответы владельца записываются правилами и свидетелями.

Спеку, выведенную из кода напрямую, использовать нельзя: случайное
поведение закрепится как решение.

Первый кандидат: PresuPro, `backend/services/estimates.py`,
`calculate_estimate_totals`. Функция чистая. Известно расхождение: бэкенд
применяет скидку, затем маржу; `frontend/engine.js` — наоборот. Режим на ней
не запускался.

## Ограничения

- Один модуль, одна модель, по 8 генераций на ветку.
- Шлюзы черновика фабрики на кандидатах не запускались.
- Кандидаты ветки A между собой автоматически не сравнивались.
- С отчётом микроскопа эксперимент не сверен: `artifacts/` исключён из git.
- Линз 3 и 4 в коде нет; сравнение и мутанты в эксперименте сделаны вручную.

## Вопросы следующей сессии

1. Где живёт линза 3: в Factory рядом с `generation_microscope.py` или в
   Workbench рядом с конвейером вопросов. `skills/spec-authoring/QUESTIONS.md`
   уже знает слой `generation` для перенесённых тем: «where the microscope
   shows the choice of principle».
2. Как сценарий класса `split` становится темой в `design_questions.py` и
   какой у неё вид.
3. Какой минимальный интерфейс достаточен для генерации до State 6.
4. Кто пишет пробные сценарии и как не зашить в них допущения одного
   кандидата.
5. Сравнить стоимость: N генераций на круг против раундов вопросов.
6. До любых изменений закрыть дыры приёмки ядра: M08 и M09, M02, M14, тест
   на статусы трассы, решение владельца по пустому списку получателей.
