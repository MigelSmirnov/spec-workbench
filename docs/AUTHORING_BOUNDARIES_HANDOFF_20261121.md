# Границы авторинга и возвраты из Factory — handoff и технический долг

Дата: 2026-11-21.
Статус: передача следующей сессии и список незакрытых задач.
Документ не меняет SPEC_STANDARD, authoring_sequence, правила закрытия или состояние кейса.
Предложения ниже не являются новыми обязательными гейтами.

## Коротко для следующего агента

Общая последовательность State 0–7 / Stage 8–9 сохраняется. Главная проблема
наблюдавшихся кругов: найденный выбор реализации превращался в новую
нормативную фразу раннего слоя. Эта фраза порождала следующие вопросы и
несогласованность с уже закрытыми текстами.

Перед исправлением установить владельца вопроса, затем необходимость
различать варианты. Важность вопроса не делает его вопросом текущего слоя.
При возврате из генерации сначала установить, дефект ли это требования,
контракта, заметок, сгенерированного кода или инструмента Factory.

Действовать по текущим AGENTS.md и authoring next. Этот handoff не разрешает
обходить существующие гейты или принимать продукты за владельца.

## State 5: отдельная гипотеза

State 3 назначает ответственность и зависимости; State 4 задаёт сквозные
взаимодействия; State 5 фиксирует публичные обязательства операций между
модулями; State 6 — точные сигнатуры и формы; State 7 — оставшееся поведение
для генерации.

В main question_scope State 5 включает «an operation two modules would
implement differently from its text». Это может втягивать точное
представление и скрытую реализацию в этап публичных операций.

В authoring_sequence.json у State 5 нет layer.owns / layer.carries.
transition.layer возвращает пустые списки; промпт слоя показывает отсутствие
объявленных собственных решений и передаваемых обязательств.

Примеры из выборки:
- round-10: точные поля SourceRead и сериализация результатов правильно
  отправляются в State 6, но продолжают приходить от ревьюеров;
- round-30 T7: точный набор создаваемых при записи папок признан блокирующим;
- round-37 T1: обещание вернуть только допустимые настройки конфликтует с
  назначенной следующей операции проверкой этих же настроек. Это существенно
  для совместной работы модулей и не должно теряться при сужении скоупа.

Снижение числа раундов State 5 пока не измерено.

## Итог Portal Deliverer: что исправлено в нужном слое

По отчёту автора, после явного требования читать стандарт и правила фаз,
без заимствования лишней механики, кейс прошёл до экспорта в Factory;
некоторые фазы закрывались одним раундом. Это наблюдение одного прохода,
не контролируемое сравнение.

При генерации возник вопрос разрешения имени сигнала:
- A8 не изменён;
- в State 6 добавлен _stop_signal(name: str) -> Signals;
- заметки требуют вернуть член перечисления с этим именем без проверки наличия;
  run_service устанавливает обработчик для каждого имени STOP_SIGNALS через контракт;
- State 7 round-12 чистый, Stage 8.1 PASS — по отчёту автора;
- все 12 модулей сгенерированы, гейты и сборка пройдены — по отчёту автора.

Затем линкер сообщил:
`object_connections.py:151 model_field_missing: reads missing field ConnectionEntry.items`.

PR #232 исправляет вывод типа поля: dict[UUID, ConnectionEntry] остаётся
словарём, а не становится типом его элементов. Дифф и тест просмотрены:
добавлена регрессия для контейнеров и сохранена проверка отсутствующего
поля непосредственно у модели. В PR заявлены 92 и 467 успешных локальных
тестов; здесь они не запускались.

На первой проверке четыре Actions имели failure, журнал задания получить
не удалось. Позже PR слит; это не подтверждение успешного CI или завершения
Route B. Успешный повтор линкера, полная проверка поведения и деплой в этой
сессии не подтверждены.

Вывод кейса: недостаток технического контракта исправлен в State 6–7,
ошибка анализатора — в Factory. Основания переписывать State 2 не возникло.

## Технический долг

### TD-01 — Довести эксперимент судьи State 2 до проверенного результата (P1)

Существующая ветка tools/state2-required-results содержит новый критерий,
перенос гарантии через --keeps и диагностический линт. Это кандидат, а не
доказанно работающий новый процесс.

Следующий шаг: проверить diff ветки, затем выполнить сохранённый в отчёте
probe на фиксированных ревизиях. Сначала «чей слой», затем какое обязательство
различает исходы. Наблюдатель сам по себе не доказывает дефект.

Готово, когда сохранены входы/выходы, ревизии и ручная проверка изменённых
вердиктов; измерены снятые лишние требования и сохранённые реальные дефекты.
Отдельно разобрать случай отсутствующего продуктового решения: отсутствие
цитаты не доказывает допустимую свободу. Не терять реальные противоречия и
нарушения стандарта при изменении фильтра пробелов.

### TD-02 — Дать автору инструкцию в момент обработки раунда (P1)

dispose уже существует, CLI показывает ожидаемые диспозиции, повторный раунд
неизменённого текста ограничен. Но добавление очередной фразы меняет текст
и разрешает следующий раунд, сохраняя цикл.

Предложение: прямо в результате раунда напоминать сначала выбрать диспозицию
и владельца решения, а затем решать, нужна ли правка. fixed не должен
привносить решения следующих слоёв. carried сохраняет варианты, последствия
и обязательную гарантию; accepted объясняет допустимую свободу.

Готово, когда правило доходит до новой сессии через штатный вывод/контекст,
а не требует личного напоминания владельца. Это инструкция, не обещание
автоматически проверить смысл. Противоречия и standard_violation по main
не закрываются диспозицией; не предлагать обход.

### TD-03 — Проверять границы самой правки (P1)

Ветка эксперимента уже содержит tools/design_change_vocabulary.py.
Использовать как диагностику, не обязательный запрет по словам.

Готово, когда оценены ложные срабатывания и пропуски на содержательных,
несодержательных и смешанных fixed. Новое имя или «сначала/затем» само по
себе не делает правило недопустимым.

### TD-04 — Сохранять закрытие неизменённого при повторном раунде (P1)

По сообщениям владельца, после изменения A2 round-63 поднял темы A1/A3/A7/A10,
в том числе ранее закрытые и переданные дальше. Полный локальный контекст
этого запуска здесь не проверялся.

Проверить отбор units, referencing, context, передачу --since, применение
preexisting и judged_before. Связь по имени не равна изменению обязательства.

Готово, когда воспроизводимый пример показывает: зависимые тексты могут
служить контекстом, но их прежние темы не переоткрываются без объяснения
влияния изменения. Новое реальное противоречие не скрывается.

### TD-05 — Уточнить границу State 5 и его layer-протокол (P1)

Задать собственные решения и передаваемые обязательства State 5. Проверять,
что вызывающий и вызываемый согласованы по смыслу входов, результатов,
отказов и эффектов; не требовать заранее всю сигнатуру, сериализацию или
скрытую процедуру.

Готово, когда проведён отдельный probe State 5 с сохранением существенных
межмодульных дефектов. Не переносить выводы State 2 на State 5 без измерения.

### TD-06 — Разделить принятые значения и технические привязки A8 (P2)

В A8 смешаны гарантии, настройки, константы, технические пути и представления.
Уже есть pre_contract_structured_data_closure и SPEC_STANDARD 6.10–6.11.

Сначала составить карту существующих владельцев данных и дублирования.
Проверить возможность ранней записи принятых значений с поздней привязкой
к владельцам/контрактам, без второго источника истины. Отдельный State 2.1
и новая схема не приняты. Табличная форма не означает принадлежность State 2.

Готово, когда предложено решение без противоречащих копий в прозе и IR,
не требующее преждевременных модулей и контрактов.

### TD-07 — Ограничить влияние прототипа на авторинг (P1)

По наблюдению владельца и разбору, автор копировал механику прототипа в спеку,
где она конфликтовала со стандартом. Прототип не источник нормативной
архитектуры.

Предложение: не включать его код в обычный контекст автора ранних слоёв.
Если проверяется достижимость гарантии, передавать результат эксперимента,
условия и ограничения; не переносить автоматически вызовы, имена и алгоритмы.
Изменение обещания требует решения владельца.

Готово, когда на пробном авторинге прослеживается происхождение требований,
а случайное устройство прототипа не превращается в обязательство.

### TD-08 — Диагностировать возврат из Factory до выбора слоя правки (P1)

Дополнить применение правила «earliest owning state»: сначала доказать
владельца дефекта. Сбой генерации не доказывает дефект State 2.

Различать требование, структурированные данные/контракт, заметку, сгенерированный
код и инструмент Factory. Сохранять минимальный пример и исходную диагностику.

Готово, когда новая сессия может на примерах сигнала и dict.items выбрать
State 6–7 либо Factory без вмешательства владельца и без расширения A8.

### TD-09 — Продолжить проверку Portal Deliverer после Factory #232 (P1, Factory)

Исправление линкера слито. Сверить checkout Factory с merge-коммитом,
установить причину прежних CI failure и повторить допустимый текущим
Route B механизм продолжения/проверки сохранённой сборки. Не придумывать
команду продолжения и не считать деплой завершённым по одной генерации.

Готово, когда результаты линкера и следующих проверок сохранены, а фактический
итог приложения явно зафиксирован. Этот handoff не инициирует новый прогон.

## Порядок продолжения

1. Разобрать оперативный TD-09 независимо от методологических изменений.
2. Проверить уже подготовленную ветку эксперимента TD-01/03; не реализовывать
   её заново и не считать её слитой в main.
3. TD-02/04/08 — защита от повторения в новой сессии.
4. Отдельный эксперимент TD-05, затем проектирование TD-06 при необходимости.
5. Не перестраивать весь пайплайн и не вводить State 2.1 до результата проверки.

Сравнение вариантов должно иметь исходный вариант. Считать не только число
снятых блокировок, но и пропущенные реальные дефекты, лишние fixed, повторные
вопросы, стоимость раундов и доведение кейса до генерации. Повторная оценка
истории не измеряет исчезнувшие будущие раунды.
