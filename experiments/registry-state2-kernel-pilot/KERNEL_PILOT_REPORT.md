# Пилот: Cabinet Kernel как среда исполнения гипотез State 2

Дата: 2026-10-31.
- Модель: `experiments/registry-state2-investigation/model/sandbox.py` @ `868ce840`.
- Kernel: `code-factory/projects/cabinet_kernel` @ `034b50c` — промоутированное
  дерево OTK-прогона `20261025_204110`.
- Спецификация Kernel: spec-workbench `agent/cabinet-kernel` @ `8798b98f`.

## Коротко

**Kernel владельца не достигнут.** Он работает на ПК владельца на
`127.0.0.1:8830`, а у этой облачной сессии нет подключённой папки
Remote Control (`list_computer_folders` пуст). Поэтому весь путь пройден на
**локальном экземпляре настоящего кода Kernel**: тот же сгенерированный
пакет, настоящая песочница bubblewrap 0.9.0 и настоящий вход MCP. Это не
пользовательский развёрнутый Kernel, и в отчёте он нигде за него не выдаётся.
Команда для прогона на Kernel владельца готова (`REPRODUCE.md`, раздел C).

**Что получилось на этом экземпляре.** Путь «автор готовит гипотезу →
Kernel принимает код и случаи → исполняет → другой агент восстанавливает
результат» прошёл полностью:
- 14 пробных случаев побайтно совпали с локальным исполнением;
- 11 принятых свидетелей допущены Kernel по дайджестам ожидаемых выходов;
- второй агент по одним идентификаторам восстановил результат V5 и
  переисполнил его — с тем же `value_id`.

**Найдены два дефекта Kernel.** Оба с воспроизведением:
- модуль с `dataclasses` и отложенными аннотациями падает в песочнице;
- MCP-метод `tools/list` отвечает `internal_error` и останавливает Kernel.
  Второй дефект дважды уронил Kernel во время передачи работы: второй агент
  вызвал `tools/list`, потому что моя инструкция указала на этот метод.

## 1. Что действительно выполнено и на какой версии?

| что | где | статус |
|---|---|---|
| Kernel владельца (`127.0.0.1:8830`, `~/.cabinet-kernel/`) | ПК владельца | **не достигнут**: нет подключения к компьютеру; адрес слушает только loopback |
| версия развёрнутого Kernel владельца | — | не установлена; известны деплой `cabinet_kernel-20261024T184646Z` (handoff 24.10) и промоут OTK-дерева `034b50c` (25.10); что запущено 31.10, отсюда не видно |
| локальный Kernel из `034b50c` | этот контейнер | запущен: Python 3.12, pydantic 2.13.5, bubblewrap 0.9.0; пустой манифест; три токена (владелец, агент `author` с правом автора, агент `reviewer` без него); проверка песочницы при старте прошла |
| созданные объекты | локальный Kernel | 3 экспериментальных слота, 3 версии контракта, 26 случаев, 6 реализаций, вердикты и активации только в этих слотах (`KERNEL_OBJECTS.md`); потоков, привязок, запусков и эффектов нет |

Фактические возможности сверены по коду и по спецификации
(`02_rules_functions.md` A01–A04, `50_public_apis.md`, `80_notes.md`):

- **функция:** модуль Python, `run(dict) -> dict`, порт на вход и на выход;
  только стандартная библиотека; часы, случайность, сеть и файлы вне
  каталога обмена перехватываются;
- **потолки релиза:** 30 с, 512 МиБ, 8 процессов на исполнение, 1 МиБ на
  сохранённое значение;
- **контракт:** порты со схемами из ограниченного подмножества JSON Schema;
  у входов есть класс раскрытия, у выходов нет; границы ресурсов
  обязательны;
- **пробные случаи:** только автор, только добавление; ожидаемые выходы
  **необязательны**;
- **пробный запуск** (`try_implementation`): любой агент; только по случаям
  корпуса; без вердикта и активации;
- **допуск и активация:** `submit_implementation` всегда запускает допуск
  по всему корпусу и при `admitted` сразу активирует, в том же запросе
  (A04 r4). Разделить их нельзя, поэтому до отправки выбраны новые слоты,
  которые не использует ни один поток;
- **результаты:** выходы класса `open` показываются содержимым (`json_text`);
- **код:** агенту — только код текущей реализации, через `get_repair_view`;
  владельцу — любой, через `get_implementation`;
- **версии:** идентификаторы контракта, реализации, случая и значения —
  содержательные (SHA-256 канонического JSON), вычисляются Kernel.

## 2. Совпали ли результаты с локальной моделью?

Да. Расхождение было одно, и его причина установлена.

| сравнение | результат |
|---|---|
| сборка (`adapter/kernel_function.py`) против исходной модели, 25 входов | 0 расхождений: вердикты шагов, наборы конфликтов, итоговый журнал, находки перебора (`results/local_vs_control.json`) |
| Kernel против локального исполнения сборки, 14 пробных случаев | 14/14 побайтно равны по обоим выходам (`results/comparison_local-034b50c.md`) |
| Kernel: допуск принятого корпуса, 11 случаев с ожидаемыми выходами | `admitted`; Kernel сам сравнил дайджесты |
| второй агент: сохранённое исполнение, повтор в Kernel, свой локальный запуск | все три согласны (`handover/response.txt`) |

**Расхождение.** Первая отправка завершилась `crashed` на всех случаях, а
локально всё работало. Причина: раннер Kernel не регистрирует модуль в
`sys.modules`, и `dataclasses` с отложенными аннотациями падает
(`finding/FINDING_sandbox_module_not_in_sys_modules.md`).

Мой локальный контроль сначала регистрировал модуль и поэтому скрывал это
расхождение. Теперь он загружает модуль так же, как раннер. В сборку
добавлены две строки (адаптация 3); смысл модели не изменился.

Что показали гипотезы, исполненные в Kernel:

| случай | результат гипотезы |
|---|---|
| V0, пустое стирание (исторический дефект) | конфликт `{A15 r6, R0-66}`, `{A15 r6, инвариант A15}` и др. |
| V5, историческое частичное исправление | конфликт `{A14 r5, A15 r6}` |
| H1, сконструированное частичное исправление | конфликт с соседями A14 r3, A14 r5, инвариант A14 |
| V6 | согласован |
| V5 при `own_entry_is_change=True` | согласован — исход зависит от трактовки |
| V6 при буквальном чтении инварианта A14 | конфликт `{A14 invariant}` — тоже зависит от трактовки |
| V3a | неоднозначность: номер #2 или #3 |
| V1 с восстановлением | конфликт с `M09 never reused (global)`, разрешение `state2_mechanism` |

Каждое такое исполнение Kernel записал как `passed`: функция отработала, хотя
гипотеза опровергнута. Ошибка исполнения модели (`crashed`) и конфликт
исследуемых правил (`analysis.classification = conflict`) не смешиваются.

## 3. Что дали версии, корпуса и свидетельства Kernel сверх локального Python?

1. **Неоспоримую идентичность «что исполнялось».** Код, контракт и случаи
   адресуются по содержимому. Второй агент установил реализацию, её код
   (SHA-256), контракт, автора и время только средствами Kernel.
2. **Независимое переисполнение с одинаковым идентификатором результата.**
   Повтор в Kernel дал те же `value_id`. Это сильнее, чем «у меня на машине
   совпало».
3. **Доказательство чистоты модели.** Модель прошла песочницу без
   `sandbox_violation`: в ней нет часов, случайности, сети и файлов. Локально
   это было только предположением.
4. **Регрессию по принятым свидетелям как механизм, а не как дисциплину.**
   Новая реализация модели не будет допущена в слот `accepted`, если
   нарушит хоть одно принятое ожидание V6.
5. **Неотзываемую историю.** Отказ первой реализации (`crashed`) остался
   записью и сам служит свидетельством дефекта.
6. **Два реальных дефекта Kernel**, найденные именно на этом пути.

Чего Kernel не дал (ответ второго агента, `missing_from_kernel`):
- почему правила такие;
- какие тексты стоят за версиями V0–V6;
- верна ли трансляция в предикаты;
- какая ревизия модели исполнялась;
- что означает «конфликт» для спецификации Registry.

## 4. Какие ограничения мешали исследованию гипотез?

- **Неотзываемый корпус.** Случай с ожидаемым выходом становится вечным
  ожиданием. Решение — два слота с разным статусом случаев (`CORPORA.md`):
  в `probe` нет ожиданий никогда, в `accepted` попадают только свидетели,
  принятые в Workbench.
- **Пробный запуск только по случаям корпуса.** Любой вход гипотезы
  становится постоянным случаем. Без потоков нельзя исполнить разовый
  вход. Потоки не использовались: для чистой функции понадобились бы
  `compose`, `prove` и `activate_flow_version` ради одного вычисления.
- **Допуск и активация неразделимы.** Каждый `submit` активирует допущенную
  реализацию; на Kernel владельца это постоянные записи.
- **Код старых реализаций агенту не виден.** Видна только текущая
  реализация; отвергнутую агент не прочтёт (K-12).
- **Ревизия модели не хранится**, если автор не вписал её в код.
- **Обнаружение ломает Kernel.** `tools/list` останавливает его; схемы
  `add_trial_case` и `list_records` не публикуются. Второй агент не смог
  прочитать историю исполнений: 12 отказов `list_records`.
- **Модуль с `dataclasses` и отложенными аннотациями падает** без адаптации.
- **Потолки** (30 с, 1 МиБ на значение): перебор пришлось снизить до
  глубины 4 в случаях. По замерам глубина 6 тоже уложилась бы.
- **Доступ.** До Kernel владельца из облачной сессии не добраться: нужен
  компьютер владельца через Remote Control или сессия на нём самом.

## 5. Помогает ли Kernel передавать работу другому автору?

**Для вопроса «что исполнялось и что вышло» — да, и это проверено.** Второй
агент получил только адрес, путь к токену без права автора и имена слотов.
Он нашёл случай, восстановил код, контракт, входы и результат, переисполнил
случай в Kernel и у себя, и все три результата совпали.

**Для вопроса «почему» — нет.** Основания, цитаты, трактовки, допущения и
решения владельца в Kernel не попадают. Второй агент перечислил ровно это
как недостающее. Нужна связка: идентификаторы Kernel ↔ пакет Workbench.

**Цена ошибки инструментов при передаче высока.** Один штатный вызов
обнаружения остановил Kernel, на котором работает передаваемый результат.

## 6. Минимальный следующий шаг интеграции, если польза подтверждена

Польза подтверждена частично: Kernel хорош как хранилище свидетельств и
независимый исполнитель, но не как среда исследования. Перебор, трактовки и
быстрые итерации удобнее вести локально.

Минимальный следующий шаг:

1. **Устранить два дефекта на стороне Factory/Kernel** — `tools/list` и
   `sys.modules` — по находкам в `finding/`. Это не задача Workbench, и
   здесь ничего не менялось.
2. **В Workbench — одна запись-связка на каждый прогон**, например
   `kernel_runs.json` рядом с экспериментом. В ней:
   - деплой Kernel;
   - слот, `contract_version_id`, `implementation_id`, SHA-256 кода;
   - коммит Workbench и SHA-256 модели;
   - для каждого случая: `trial_case_id` ↔ свидетель или гипотеза, её
     статус и основания.

   `run_kernel.py` уже пишет почти всё это (`kernel/<label>/ids.json`); не
   хватает коммита Workbench и статуса каждого случая.
3. **Встроить в код константу происхождения** (коммит Workbench, SHA-256
   модели), чтобы Kernel сам хранил связь результата с версией модели.
4. **Прогнать тот же пилот на Kernel владельца** с его согласия: команда в
   `REPRODUCE.md`, раздел C. Это создаст два постоянных слота
   `exp_registry_audit_*`.
