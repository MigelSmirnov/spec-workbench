# Spec Authoring

## Purpose

Use this skill to design and assemble a complete `global_spec.json` for an application whose code will later be generated by an external factory.

The factory already validates, normalizes, splits, links, and builds code from a finished specification. This skill does **not** replace those tools and does **not** focus on structural validation of an already completed file.

Its responsibility is earlier:

```text
idea and discussion
→ layered architectural design
→ complete global_spec.json
→ existing code factory
```

The governing format is [SPEC_STANDARD.md](SPEC_STANDARD.md). Treat it as normative.

## Core problem

An LLM can produce a specification that is structurally valid but semantically hollow.

Typical failure mode:

1. The agent writes the specification from top to bottom.
2. It invents contracts before the domain is stable.
3. It fills unknown areas with plausible names and generic DTOs.
4. Static checks pass because all symbols are connected.
5. Code generation produces wrappers, stubs, empty result objects, generic dictionaries, and skeleton modules.

This is the **placeholder problem**.

A placeholder is not only `TODO`, `pass`, or an empty function. It is any apparently finished design element that postpones an unresolved engineering decision while pretending the decision has already been made.

Examples:

- `process(data: dict) -> dict`
- `Result(data: dict, status: str, message: str)`
- a module named `manager`, `processor`, `helpers`, or `utils` without precise ownership
- a note saying `MUST process input correctly`
- an endpoint that orchestrates calls but no module actually owns production of the final result
- `handle errors appropriately`
- `support additional formats in the future`
- a function that can be implemented as `return []`, `return {}`, `return None`, or an empty DTO without contradicting its notes

The skill must prevent these placeholders during authoring, not merely report them after the full specification has been written.

## Working mode

This is a semi-manual design process conducted with the user.

Do not generate a complete specification immediately from a short product idea.

Work in design layers. At each layer:

1. discuss the engineering decisions;
2. record the current result;
3. identify unresolved questions explicitly;
4. test the layer for placeholders;
5. proceed only when the layer is sufficiently stable.

The process may revisit earlier layers. Returning backward is expected and is not a failure.

## Tool-assisted navigation

When a case study is large enough that reading by filename or raw `grep` loses design context, use `tools/design_index.py` as a deterministic navigation aid.

The tool has two deliberately separate views:

- **structural relations** — indexed design items and only explicit `A*` / `OQ-*` references;
- **lexical navigation** — name occurrences with their source line, enclosing decision, and heading path.

A lexical occurrence is never architectural evidence by itself. Do not infer module ownership, responsibility clusters, or semantic relations from `--mentions` output alone.

Useful commands:

```bash
python tools/design_index.py examples/<case> --list --state 2 --kind decision
python tools/design_index.py examples/<case> --get A51
python tools/design_index.py examples/<case> --references A51
python tools/design_index.py examples/<case> --mentions Holded
python tools/design_index.py examples/<case> --context 02_rules.md:240 --radius 5
```

Prefer these commands when they can answer the navigation question before falling back to raw `grep`. The tool is an authoring aid; source Markdown remains normative.

## Primary rule

> Do not design the next layer while unresolved decisions in the current layer are being hidden with generic names, generic types, or vague prose.

A useful operational version:

> If contracts require inventing new models, return to models. If notes require inventing new behavior, return to product rules or module design. If a module needs `utils` to hold unclear responsibilities, return to responsibility design.

## Design states

The states below are ordered by dependency, not by the order of sections in `global_spec.json`.

### State 0 — Product boundary

Establish what the application is before discussing code structure.

Capture:

- product goal;
- users or actors;
- primary user actions;
- inputs entering the system;
- observable outputs;
- persistent data;
- external systems;
- important constraints;
- explicitly unresolved questions.

Do not create:

- Python contracts;
- helper functions;
- module paths;
- implementation algorithms;
- speculative extension points.

Readiness questions:

- Can the main value of the application be stated in one concrete paragraph?
- Is every primary action paired with an observable outcome?
- Are important invalid or failure outcomes known?
- Are unknowns written as unknowns rather than replaced with generic abstractions?

### State 1 — Domain models

Design the concepts and data shapes that the application actually needs.

Start with domain meaning, then define fields and types.

For each model determine:

- why it exists;
- whether it is an entity, command, input DTO, output DTO, decision, event, persisted record, catalog, or intermediate value;
- who creates it;
- who reads it;
- who may modify it;
- whether it persists;
- its lifecycle or states;
- the source of every required field;
- whether partial construction is valid;
- which invariants apply.

Reject model placeholders such as:

```text
data: dict
metadata: dict
payload: Any
status: str
result: object
extra: dict
```

unless the external contract is genuinely open-ended and that openness is itself explicitly required.

Readiness questions:

- Does every required field have a known producer or source?
- Can each model be explained without mentioning future helper functions?
- Are domain states represented explicitly where they affect behavior?
- Are distinct concepts separated because they change for different reasons?
- Are models free from speculative fields added only “for flexibility”?

Expected specification output at this stage:

- draft `models`;
- candidate domain constants and catalogs;
- unresolved model questions.

Do not finalize contracts yet.

### State 2 — Invariants, rules, config, and constants

Separate statements that must always remain true from values that merely configure runtime behavior.

Capture:

- data invariants;
- ownership and access invariants;
- valid state transitions;
- policy decisions;
- thresholds and routing rules;
- fallback policies;
- runtime knobs;
- limits, paths, timeouts, and feature switches;
- stable domain catalogs and enum-like values.

Classify deliberately:

- `config` — runtime or product knobs that may change independently;
- `rules` — read-only domain or policy semantics;
- `models` — schemas, domain taxonomies, and structured catalogs that form contracts;
- `notes` — behavior that uses the above, not the data itself.

#### Navigation while working in State 2

When State 2 spans multiple documents or many accepted decisions, start by listing the indexed decisions instead of scanning files manually:

```bash
python tools/design_index.py examples/<case> --list --state 2 --kind decision
```

Before changing or evaluating one decision, inspect its exact structural record and explicit references:

```bash
python tools/design_index.py examples/<case> --get A51
python tools/design_index.py examples/<case> --references A51
```

When a domain name, model name, external system, or policy term appears to connect several decisions, use lexical navigation to find all occurrences without asserting a relation:

```bash
python tools/design_index.py examples/<case> --mentions <name>
```

For an important occurrence, request source context by the returned file and line:

```bash
python tools/design_index.py examples/<case> --context <path>:<line> --radius 5
```

Use this sequence to decide what to read next. Do not convert shared names into ownership or responsibility links during State 2.

Readiness questions:

- Is every invariant owned by a future responsibility rather than “the whole system”?
- Are state transitions explicit where lifecycle matters?
- Are tables and allow-lists stored outside notes?
- Can a value’s section be justified by why and how it changes?

### State 3 — Module responsibilities

Derive modules from ownership of complexity, rules, and knowledge.

Do not derive modules merely from screens, endpoints, or verbs in the product description.

#### Bridge from State 2

Use the State 2 decision index as evidence inventory, not as an architecture generator.

For each candidate responsibility:

1. inspect the relevant State 2 decision with `--get`;
2. inspect explicit incoming and outgoing decision references with `--references`;
3. use `--mentions` only to discover other places worth reading;
4. open important source locations with `--context`;
5. assign one primary enforcement owner only after reading the normative source.

Example route:

```bash
python tools/design_index.py examples/<case> --get A51
python tools/design_index.py examples/<case> --references A51
python tools/design_index.py examples/<case> --mentions Holded
python tools/design_index.py examples/<case> --context 02_rules.md:240 --radius 5
```

The index must not automatically create module names or responsibility clusters. A State 2 decision title may seed a candidate responsibility name, but State 3 must still justify the ownership boundary from the knowledge and rules the module owns.

For every module define:

- responsibility;
- knowledge it owns;
- decisions it makes;
- details it hides;
- public capabilities it must expose;
- responsibilities it must not own;
- dependencies it may use;
- expected consumers.

Prefer deep modules:

- narrow public API;
- substantial hidden responsibility;
- stable ownership boundary;
- no leakage of internal sequencing to callers.

Treat the following as warning signs:

- `utils`, `helpers`, `common`, `manager`, `processor`, or `service` without a precise domain qualifier and ownership statement;
- router or API modules owning policy, storage, rendering, or domain decisions;
- storage deciding product semantics;
- rendering changing domain state;
- modules that only rename or forward arguments;
- one module per endpoint when several endpoints share one responsibility;
- modules whose public API is nearly identical to all internal functions.

Readiness questions:

- Can each invariant be assigned to one primary enforcement owner?
- Can each model’s creation and mutation be assigned to a responsible module?
- Does each module hide something meaningful?
- Is the public API smaller than the module’s internal behavior?
- Are forbidden responsibilities explicit?

Expected specification output at this stage:

- draft `module_functions` containing model names, constants, and candidate public operations only;
- draft `imports.internal` as public ownership, not final dependency wiring;
- draft `module_order` and `module_paths`;
- responsibility notes outside the final JSON if still under discussion.

### State 4 — Key system flows

Walk through a small number of important end-to-end flows before finalizing APIs.

For each flow identify:

```text
actor or trigger
→ boundary
→ validation or policy
→ domain operation
→ storage or integration
→ observable result
```

At every transition determine:

- which model crosses the boundary;
- which module owns the next decision;
- whether an adapter is needed;
- which errors may occur;
